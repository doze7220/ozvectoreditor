# Survey のタスクの並列実行（実装統括AI手順の補足）

`SKILL.md` の手順2（タスク実行）を、**調査の計画立案型の REQ（`Survey_PlanMake`）に限り**、互いに独立なタスクを同時に複数の実装AIで実行する形に置き換える手順。コードや資料を変える REQ では使わない（前のタスクの差分が次の前提になり、差分監査・検証コマンドもタスクごとに通すため）。

## 使う条件（すべて満たすとき）
* REQ が `Survey_PlanMake` で、ソース・資料の変更を禁じている。
* 計画監査の check2 が、タスクが互いに独立である（他のタスクの調査結果を読まずに実行できる）と判定している。独立でないと挙げられたタスクは、並列に含めず、依存先の後に1つずつ行う。
* 全タスクの後に行う固定タスク（一覧の作成・「相違なし」の明記など）は並列に含めず、最後に1つずつ（`SKILL.md` の手順2のとおり）行う。

条件を満たすかは本体が判断してよい。並列に切り替えるときは、発注者に「タスクn〜mを並列で実行する」と1行で知らせる（返事は待たない）。

## 進め方
1. **試し**：最初の1タスクは、`SKILL.md` の手順2のとおり1つずつ行う（監査は survey モード）。検索で漏れを探すタスクがあれば、それを試しに選ぶ。監査で分かった判定の基準のずれ・足りない検索語を、次の共通指示の「注意事項」に入れる。基準のずれが大きければ、もう1タスク試してよい。
2. **共通指示**：スクラッチパッドの `survey/COMMON.md` に、下の「共通指示の形」で書く。監査の共通指示も `survey/AUDIT.md` に書く。判定の基準（REQ・RES にあるもの＋試しで得たもの）は、**両方に同じ文で**入れる。
3. **起動**：`oz-implementer`（既定の sonnet）を、プロンプトに「共通指示のパス・RES のパス・タスク番号・結果ファイルのパス（`survey/task<n>.md`）」だけを書いて起動する。同時に動かす調査の実装AIは **5個まで**。空きが出てから次を起動する（監査はこの数に含めないが、合わせて7個を超えない）。
4. **監査**：調査が終わったタスクから順に、`oz-auditor` を **survey モード・`model: "sonnet"`** で起動する。渡すのは、監査の共通指示のパス・REQ と RES のパス・タスク番号・結果ファイルのパス。監査は並列でも省かない（差し戻しが多く、監査なしで差し込むのは危険）。
5. **修正**：要修正なら、新規の `oz-implementer` に指摘を文書で渡し、結果ファイルを直させる（1回目は sonnet、2回目は `model: "opus"`）。直したら4をやり直す。2回直して合格しなければ停止条件2。
6. **差し込み**：合格したタスクの結果を、本体が**スクリプトで機械的に** RES へ差し込む（`@@SECTION4` → 4章の当該タスクの欄、`@@SECTION5` → 5章、`@@SECTION6` → 6章、3章のチェックボックスを `[x]`）。文言の加筆・言い換え・要約はしない。1タスク1コミット（メッセージは `RESファイル名（拡張子なし） TASKn`）。
7. **確かめ**：差し込みのたびに（まとめて差し込むときは組ごとに）、`git status` で RES 以外の変更が無いことと、差し込んだ文が結果ファイルと一致していることを確かめる。検証コマンドがあれば、組ごとに実行して合否だけを見る。
8. **途中で基準を足したとき**：走っている実装AIには届かない。`survey/COMMON.md` と `survey/AUDIT.md` の両方に足し、すでに終わった・走っているタスクは監査で照らして直させる。
9. **固定タスク**：並列分がすべて差し込まれた後に、`SKILL.md` の手順2のとおり1つずつ行う（他のタスクの所見と5章の重複・食い違いの突き合わせを含む）。

結果ファイルは、RES に差し込まれた時点で役目を終える。リポジトリには残さない。

## 共通指示の形（`survey/COMMON.md`）
```
# タスク実行の共通指示（並列実行用）

このプロジェクトのルール `./PROJECT_CONSTITUTION.md` を熟読すること。
作業計画書 `<RESのパス>` を読み、**起動時に指定されたタスクのみ** を実行すること。次のタスク・他作業へ移行してはならない。作業に必要な責務情報は、作業計画書の『参照する責務』に記載されている。

## 並列実行のための書き込みの決まり（作業計画書の記載より優先する）
他のタスクが同時に動いているため、**リポジトリ内のファイルは一切変更しない（作業計画書RESも変更しない。チェックボックスも付けない）**。結果は起動時に指定された結果ファイル（リポジトリの外）だけに Write で書く。`git status` に出るRESの変更は他の担当のものなので気にしない。git の書き込みを伴うコマンド（add・commit・stash・checkout 等）は使わない。

結果ファイルの形（見出し行 `@@SECTION4`・`@@SECTION5`・`@@SECTION6` をこの順で必ず置く。見出し行以外に前置きや囲みを書かない）:

@@SECTION4
（作業計画書の4章の当該タスクの欄に入る内容。「調査内容」「事実（実コードの記述）」「推測・所見」）
@@SECTION5
* （タスクN）**（資料のファイルと節・行）**： （資料の記述） → （実コードの実態。`ファイル:行`）
（相違が無ければ空のままにする）
@@SECTION6
* （タスクN）……（判断に迷った点・目視確認を推奨する箇所・注意点。無ければ空のままにする）

## 判定の基準
（REQ・RES にある判定の基準と、試しで得た基準をここに書く。`survey/AUDIT.md` と同じ文にする）

## 注意事項
* 対象を照合し残さない。確認せずに終える主張があれば、理由を書く。「他のタスクで確認済み」とは書かない（自分で確かめる）。
* `ファイル:行` の行番号は、書く前に現在のファイルで開いて確かめる。
* 検索で漏れを探すときは、1つの言い方だけで検索しない。式・言い換えを5種類以上使い、使った式と件数を「調査内容」に残す。
（試しで得た注意事項を足す）

## 完了報告
結果ファイルのパスと、相違の件数・要点だけを短く返す。質問があれば書く。
```

## 監査の共通指示の形（`survey/AUDIT.md`）
```
# 調査タスクの監査の共通指示（並列実行用）
REQ: `<REQのパス>`
RES: `<RESのパス>`（調査要件・『参照する責務』・3章の当該タスクの欄を読む）
並列実行のため、調査の結果はRESではなく、起動時に指定された結果ファイル（`@@SECTION4`＝RES4章へ入る内容、`@@SECTION5`＝5章、`@@SECTION6`＝6章）に書かれている。これが監査の対象で、git diff には出ない。RESの3章のチェックボックス・4章の当該タスクの欄が未実施のままなのは正常。
判定は、エージェント定義の survey モードの観点に従う。リポジトリ内のファイルも結果ファイルも変更しない。
```
