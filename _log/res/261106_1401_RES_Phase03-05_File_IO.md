# RES: 作業計画・作業レポート (Phase 03-05) : ファイル入出力
* 参照元REQ: `./_log/req/261106_1354_REQ_Phase03-05_File_IO.md`

## 1. 作業目的
現状、キャンバスはブラウザ内にのみ保存され、ファイルとして持ち出す・取り込むことができない。本作業では、開いているキャンバスの書き出し、ファイルを新しいキャンバスとして開く操作、ファイルの図形を開いているキャンバスへ追加するインポートを、キャンバスパレットに追加する。あわせて、一般利用者向けの読み込み失敗の通知を整える。

**用語**（REQの定義に従い、本RES・コード内JSDocで統一する）
* **作業データファイル**: 作業データ形式のJSON文字列を内容とするファイル（既定の拡張子`.json`）。
* **書き出し**: 開いているキャンバスの図形一式を作業データファイルとしてダウンロードすること。
* **開く（ファイル）**: 作業データファイルの内容を、キャンバス一覧へ新しいキャンバスとして登録し、開いているキャンバスと入れ替えること。一覧の行を押して開く操作（`CanvasLibrary.openCanvas`）とは区別する。
* **インポート**: 作業データファイルの図形を、開いているキャンバスへ追加すること。
* **ファイル操作**: 書き出し・開く（ファイル）・インポートの総称。
* **ファイル操作の通知**: ファイル操作の失敗・一部失敗を利用者へ示す、キャンバスパレット内の文言（2章要件5。`issue`とは別の状態）。
* キャンバス・キャンバス一覧・キャンバス記録・自動保存・キャンバスパレット・切り替え処理はPhase 03-04、編集操作・履歴はPhase 03-02、作業データ形式・シリアライズ／デシリアライズはPhase 03-01、貼り付けの共通処理（`ShapeInserter`）はPhase 03-03、選択集合・作成中の図形はPhase 02-03、操作モードはPhase 02-01の定義に従う。

**置き場所の判断理由**

* 新しいキャンバスの登録と切り替えの処理本体は`CanvasLibrary`に置く（要件2）。`InputTracker`・`main.js`にはファイル入出力の処理を置かない。

### 要件1: 書き出し
* 処理：`CanvasFileOperations.exportCanvas()`（同期）。受理条件（要件4）を確認し、ファイル操作の通知を消したうえで、`DocumentSerializer.serializeToString(model.getShapes())`の結果と`getState().openCanvasName`を`fileIO.downloadText(text, canvasName)`へ渡す。`try/catch`で例外を捕捉し、`console.warn`＋通知`exportFailed`（アプリを止めない）。戻り値は書き出したか（`boolean`）。
* 図形一式・選択集合・履歴・ビュー変換・操作モード・作成途中の図形に触れない。`applyMode`・`beginEdit`/`commitEdit`を呼ばないため、自動保存の契機にもならない。作成途中の図形は`getShapes()`に含まれない。
* `DocumentFileIO.downloadText(text, canvasName)`：
    1. `new Blob([text], { type: 'application/json' })` → `URL.createObjectURL(blob)`。
    2. `document.createElement('a')`に`href`・`download`（`toFileName(canvasName)`）を設定し、`hidden`で`document.body`へ追加 → `click()` → `remove()`。
    3. オブジェクトURLの解放は`try/finally`で必ず予約する：`setTimeout(() => URL.revokeObjectURL(url), OBJECT_URL_REVOKE_DELAY_MS)`。ブラウザによってはダウンロードの開始がクリックより後になるため、直後には解放せず定数`OBJECT_URL_REVOKE_DELAY_MS = 10000`（10秒。唯一の定義箇所）後に解放する。
    4. 準備中の例外はそのまま呼び出し元へ投げる（捕捉は`CanvasFileOperations`）。
    * リンクは`body`直下のため`WindowManager`の伝播遮断に関わらず、`document`・`window`に`click`の購読は無く（確認済み）、`DragTracker`のclick抑止はキャンバスの`click`ハンドラ内の判定のみのため影響しない。
* **ファイル名の変換**（`DocumentFileIO.toFileName(canvasName)`。JSDocに明記する）：
    1. `\ / : * ? " < > |`と制御文字（正規表現`/[\\/:*?"<>|\p{Cc}]/gu`）を`_`へ置換する。
    2. 前後の空白を除き（`trim()`）、末尾のピリオドと空白を除く（`/[.\s]+$/u`）。
    3. **結果が空なら既定の名前`無題`とする**（定数`DEFAULT_FILE_BASE_NAME`）。計画時の決定：新規キャンバスの接頭辞「無題」と揃え、連番は付けない（キャンバス名の命名規則は`CanvasLibrary`の知識のため持ち込まない）。
    4. 末尾に`.json`（定数`FILE_EXTENSION`）を付ける。キャンバス名が`a.json`なら`a.json.json`となる（開くと`a.json`へ戻るため、往復で名前が変わらない）。

### 要件2: 開く（ファイル）
* 処理：`CanvasFileOperations.openFile(file)`。読み取り→`deserializeFromString`→判定（要件5の表）→読み込めた場合のみ`canvasLibrary.createCanvasFromShapes(fileIO.toCanvasName(fileName), result.shapes)`。
* **`CanvasLibrary`の拡張**（切り替え処理・`#isBusy`の直列化を複製しない）：
    * 新設の公開メソッド`createCanvasFromShapes(rawName, shapes): Promise<boolean>`：受理条件・本体は既存の`createCanvas()`の処理（`#canAcceptOperation()` → `#isBusy = true`・通知 → `#prepareLeave()`（手順1〜2。失敗で`false`）→ `#createAndEnter` → `true`、`catch`で`console.warn`＋`false`、`finally`で`#isBusy = false`・通知）をそのまま移す。
    * `createCanvas()`は`return this.createCanvasFromShapes(null, []);`とする（処理は変わらない）。
    * `#createAndEnter(loadIssue, rawName = null, shapes = [])`へ引数を追加する：名前は`CanvasLibrary.#normalizeName(rawName) || this.#nextUntitledName()`、記録の`document`は`DocumentSerializer.serialize(shapes)`、`#enterCanvas(summary, shapes, issueAfterEnter)`。`#openFirstLoadable`からの`#createAndEnter(hadFailure ? 'loadFailed' : null)`は変更しない。
    * private static`#normalizeName(rawName)`を新設する（文字列でなければ`''`。`Array.from(rawName.trim()).slice(0, CANVAS_NAME_MAX_LENGTH).join('').trimEnd()`）。`renameCanvas`の`trim`〜切り詰めをこの呼び出しへ置き換え（空なら`false`の判定は維持）、規則の定義を1箇所にする。`renameCanvas`のそれ以外は変更しない。
    * `CanvasLibrary`のimport・依存の制約は変わらない（図形は不透明なインスタンスの配列として受け取り、`serialize`と`replaceAllShapes`へ渡すのみ）。
* **通る手順**：手順1〜6すべて。手順3は「新しい記録の書き込み（失敗しても中止せず`'writeFailed'`として開く）」。手順2の失敗で中止した場合は`#summaries`へ登録する前に`false`を返すため、キャンバス一覧へ登録されない。切り替えは編集操作として記録しない（`#enterCanvas`の既存の働き）。
* **キャンバス名**：`DocumentFileIO.toCanvasName(fileName)`が末尾の`.json`（`/\.json$/i`）を除き、`CanvasLibrary`が名前の変更と同じ規則（`#normalizeName`）を適用する。空なら「無題 n」。名前の重複は許す（連番を付けない）。
* **記録の作業データ**：読めた図形を`serialize`したもの（現行版。読めなかった図形は含まれない）。記録の図形のidはファイルのものが未正規化のまま入り得る（`fromJSON`はidを検証しない）が、開くたびに`replaceAllShapes`が正規化するため問題ない。
* **`'partialLoad'`を立てない**：`#createAndEnter`の`loadIssue`に`null`を渡す。手順6の既存の働きにより残っていた`'loadFailed'`/`'partialLoad'`は解除される。一部が読めない旨はファイル操作の通知（`partialRead`）で示す。
* **`createCanvasFromShapes`が`false`の場合**：切り替え前の保存に失敗した場合は`issue`が`'writeFailed'`になっており、それをパレットが表示するためファイル操作の通知は出さない。`issue`が`'writeFailed'`でないのに`false`（不受理・予期しない例外。UI上は到達しない防御）なら通知`readFailed`を出す（`console.warn`のみで終わらせないため）。

### 要件3: インポート
* 処理：`CanvasFileOperations.importFile(file)`。
    1. 受理条件の確認。開始時点の`openCanvasId`を記憶する。
    2. 読み取り→`deserializeFromString`→判定（要件5の表）。`readFailed`・図形0個なら通知を設定して終了（**図形一式・選択集合・履歴・操作モード・作成途中の図形に一切触れない**。`prepareInsert`より前のため図形作成モードも作成途中の図形も残る）。
    3. キャンバスの同一性の確認（下記「読み取り中の扱い」。`canvasLibrary.getState()`の値で判定する）。
    4. `prepareInsert()`（実体`applyMode(OperationMode.SELECT)`。進行中の入力操作の中断と選択モードへの切り替え）。
    5. `inserter.insertDocument(DocumentSerializer.serialize(result.shapes), 0, 0)`（**ファイル内の座標のまま**）。新しいid・最前面への追加・追加した図形のみの選択・1件の編集操作の記録・自動保存（`historyManager.onChange`経路）は`insertDocument`の既存の働きであり、書き直さない。`VectorModel.addShape`は使わない。ビュー変換に触れない。
    6. スキップが1件以上なら通知`partialRead`。
* **`deserialize`を2回通す方式と`console.warn`の重複の回避（計画時の決定）**：`insertDocument`は内部で`deserialize`するため、判定のために先に`deserialize`すると2回通る。元の作業データをそのまま`insertDocument`へ渡すとスキップの`console.warn`が重複するため、**1回目の結果の読めた図形だけを`DocumentSerializer.serialize(result.shapes)`で作業データへ戻して渡す**。2回目の入力は読めた図形だけなのでスキップが発生せず、`console.warn`は1回だけになる。貼り付けと同じ「`serialize`した作業データを`insertDocument`へ渡す」経路であり、旧版のファイルも現行版になった状態で渡る。
* **`ShapeInserter.js`を変更しない理由**：上記のとおり、既存の`insertDocument`の組み合わせで「失敗時に何も変えない」と`console.warn`の重複回避の両方を満たせるため、REQの変更条件に当たらない。`ClipboardController`からの挙動も変わらない。
* **`insertDocument`の結果の防御**：手順5の`ok`が偽、または`insertedIds`が空の場合（`toJSON`/`fromJSON`の往復の契約が破れた場合のみ起こる。到達しない防御）は`console.warn`＋通知`readFailed`とする。スキップの件数は`result.skipped.length + inserted.skipped.length`で数える。
* **読み取り中の扱い（計画時の決定）**：読み取りの開始からファイル操作の完了まで、`CanvasFileOperations`の`#isProcessing`を真にする。`getState().busy`は`canvasLibrary.getState().busy || #isProcessing`を返すため、**キャンバスパレットの全操作（一覧の行・新規作成・名前の変更・削除・書き出し・開く・インポート）が既存の`disabled`の規則で押せなくなり**、読み取りの間にキャンバスの切り替え等は始まらない。さらに防御として、手順3で`canvasLibrary.getState()`の値（`busy`は`#isProcessing`を含まない）について「`openCanvasId`が開始時点と同じ、かつ`loading`・`busy`でない」ことを確認し、外れていれば何も追加せず`console.warn`＋通知`readFailed`とする（UI上は到達しない）。**手順3は`#isProcessing`が真の間に走るため、`CanvasFileOperations.getState()`の合成後の`busy`で判定してはならない**（常に真となり、すべて`readFailed`で終わる）。
    * 読み取りの間も図形の編集（キャンバスの操作・ショートカット）は止めない（切り替え処理の方針と同じ）。インポートの手順4・5は`await`を挟まない同期区間であり、読み取り中に始まったドラッグ・作成途中の図形は手順4で中断される（ドラッグで動かした分は別の1件の編集操作として先に記録される）。

### 要件4: 保存できない環境・処理中の扱い
| 操作 | 押せない条件（`disabled`） | `CanvasFileOperations`の受理条件 |
| --- | --- | --- |
| 書き出し | `loading`または`busy` | 操作の開始時点（`#isProcessing`を真にする前）の`CanvasFileOperations.getState()`の`loading`・`busy`（合成後の値）が偽 |
| インポート | `loading`または`busy` | 同上 |
| 開く（ファイル） | `loading`または`busy`または`!canManage`（新規作成と同じ） | 上に加えて`canManage`（`'unavailable'`でない） |

* パレットの判定を一次、`CanvasFileOperations`の受理判定を二次とする（不受理なら通知を含め何も変えず`false`）。`createCanvasFromShapes`は`CanvasLibrary`の`#canAcceptOperation()`でも判定される。
* 上の表の受理条件は操作の開始時点の判定であり、自身の`#isProcessing`を真にした後の判定（インポートの手順3）には使わない。手順3は要件3のとおり`canvasLibrary.getState()`の値で判定する。
* `'unavailable'`では`scheduleSave`が予約しないため、インポートは編集操作として記録されるが保存されない（通常の編集と同じ）。書き出しの`openCanvasName`はメモリ上の「無題 1」が使える。

### 要件5: 読み込み失敗の通知
* **判定の表**（`CanvasFileOperations`のprivate static`#classifyRead(result)`。JSDocに記載）。`result`は`deserializeFromString`の結果で、読み取り失敗は`null`とする。**「ファイルの`shapes`が1個以上か」は`result.shapes.length + result.skipped.length`で分かるため、作業データ自体の`shapes`を参照しない**（要素の中身にも触れない。判定の置き場所は`CanvasFileOperations`のみ）。`DocumentSerializer`の`error`の文字列は利用者向けの文言に出さない（`console.warn`は`DocumentSerializer`が出す）。JSONの解析は`deserializeFromString`に任せ、`JSON.parse`を書かない。

| 場面 | 判定 | 分類 | 開く | インポート | 通知の種類 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| ファイルを読み取れない・JSONとして解析できない・`ok: false`（形式違い・対応していない版を含む） | `result === null`または`!result.ok` | 読み込み不可 | 何も変えない | 何も変えない | `readFailed` |
| 図形がすべて読めない | `shapes`が0個かつ`skipped`が1件以上 | 読み込み不可 | 何も変えない（新しいキャンバスを作らない） | 何も変えない | `readFailed` |
| 図形が0個の正しいファイル | `shapes`・`skipped`とも0件 | 空 | 空のキャンバスとして開く | 何も変えない | 開く：なし／インポート：`noShapes` |
| 一部の図形が読めない | `shapes`が1個以上かつ`skipped`が1件以上 | 一部 | 読めた図形で開く | 読めた図形を追加する | `partialRead`（件数は`skipped`の数） |
| すべて読めた | `shapes`が1個以上かつ`skipped`が0件 | 全部 | 開く | 追加する | なし |
| 書き出しの失敗 | ダウンロードの準備で例外 | － | － | － | `exportFailed` |

* **通知の持ち方（計画時の決定）**：`CanvasLibrary`の`issue`とは別に、`CanvasFileOperations`が`#notice`（`FileNotice|null`）として保持する。`issue`には種類を足さない（`#setIssue`は`'unavailable'`を上書きせず、`'writeFailed'`・`'partialLoad'`と解除条件も異なるため）。

```js
/**
 * @typedef {Object} FileNotice
 * @property {'readFailed'|'partialRead'|'noShapes'|'exportFailed'} kind 通知の種類
 * @property {string|null} fileName 対象のファイル名（書き出しの失敗はnull）
 * @property {number} skippedCount 読めなかった図形の数（partialRead以外は0）
 */
```
* **両方ある場合の表示（計画時の決定）**：`#canvas-notice`（`issue`）の下に、同じ見た目の`#canvas-file-notice`（ファイル操作の通知）を置き、それぞれ独立に`hidden`を切り替える。互いに隠さない。
* **文言**（`CanvasPalette.js`の`FILE_NOTICE_MESSAGES`。`ISSUE_MESSAGES`と同じくこのファイルが唯一の定義箇所。`textContent`のみで設定）：

| 種類 | 文言 |
| --- | --- |
| `readFailed` | `<ファイル名> を読み込めませんでした。本アプリの作業データファイルか確認してください。` |
| `partialRead` | `<ファイル名> の一部の図形（n個）を読み込めませんでした。` |
| `noShapes` | `<ファイル名> に追加できる図形がありませんでした。` |
| `exportFailed` | `書き出しに失敗しました。` |

* **解除条件**：
    * 次のファイル操作の開始時（書き出しは受理時、開く・インポートは**ファイルが選ばれ受理された時点**。小窓を開いただけ・キャンセルでは消えない（「キャンセルすると何も起きない」を優先））。
    * キャンバスの切り替えの成功時：`CanvasFileOperations`が`canvasLibrary.onChange`の中で`openCanvasId`の変化を検知して消す（`#lastOpenCanvasId`で比較）。開く（ファイル）で一部が読めない場合は、切り替えの完了（`createCanvasFromShapes`の解決）の後に`partialRead`を設定するため、消されずに残る。
    * 成功時（問題なく完了）には通知を出さない。

* **タスク1の補足**: `downloadText`は`link.click()`を内側の`try/finally`で囲み、例外時も`link.remove()`されるようにした（計画の「click→remove」の堅牢化。挙動は同じ）。ダウンロード動作・ファイル名変換はブラウザでの目視確認を推奨（タスク5以降で配線後）。開発資料への新たな影響は判明せず（2章の更新予定のとおり）。
* **タスク3の補足**: (1)`exportCanvas`の「通知を消したとき」の`#notifyChange`は、通知が存在した場合のみ行う（無駄な再描画を避ける）。(2)`openCanvasName`が`null`の場合は空文字を`downloadText`へ渡し、`既定の名前「無題」`になる。(3)`openFile`の受理条件はクラス内の`canAccept`（`state.canManage`）で表現し、共通の`loading`・`busy`判定は`#runReadOperation`に置いた。(4)`fileIO.getFileName`は`#runReadOperation`の`try`内で呼ぶため、例外は`readFailed`になる（ファイル名は空文字）。開発資料への新たな影響は判明せず。目視確認はタスク6完了後に、書き出し→開く／インポート／読み込み失敗通知を推奨。
* **変更対象外のファイル**: REQでの変更対象外のファイル（`ShapeInserter.js`を含む）の変更が不可避となる箇所は、計画時点ではない。
* **タスクの順序**: REQの順序の例（キャンバスパレットの拡張と`index.html`の追加 → `main.js`の配線）に対し、`index.html`（タスク4）→ `main.js`の配線（タスク5）→ `CanvasPalette`の拡張（タスク6）の順とした。拡張後の`CanvasPalette`のコンストラクタは新しいコールバックが関数でなければ`Error`を投げるため、`main.js`より先に変更するとアプリが起動しない時点が生じる。現行のコンストラクタは4コールバックだけを取り出して余分なキーを無視し、`render`も`fileNotice`を読まないため、この順なら各タスク完了時点でアプリが起動・動作する。
* **インポートの2回の変換**: 判定用の`deserializeFromString`と、`insertDocument`内の`deserialize`の間に`serialize`を挟むため、図形の変換が2往復する。`console.warn`の重複回避と`ShapeInserter`を変更しないことを優先した（巨大なファイルの最適化はNon-goals）。性能が問題になった場合は`ShapeInserter`へ図形インスタンスを受け取る入口を設けることを検討する。
* **読み取り中のロックの範囲**: 読み取り中に押せなくなるのはキャンバスパレットの全操作で、キャンバスの編集は止めない。読み取りが長引く環境（低速なネットワークドライブ等）では、完了までパレットが押せない状態が続く（読み取りの中止は設けない）。`?dev`の「JSONから復元」は図形一式を変え得るが、同じキャンバスへの編集操作であり、インポートの手順4・5と同期的に競合しないため止めない。
* **書き出しの失敗の範囲**: 検知できるのはダウンロードの準備（`serializeToString`・`Blob`・オブジェクトURL・リンクの`click`）までの例外である。`click`の後のブラウザ側の失敗（保存の拒否・ディスク容量不足等）は検知できない。ブラウザの設定によっては保存先の確認の小窓が出る場合があり、連続した書き出しでブラウザの確認が出る場合がある。
* **ブラウザによるファイル名の調整**: `toFileName`の変換後も、ブラウザ・OSが予約名（`CON`・`NUL`等）や長さに応じてファイル名をさらに調整する場合がある（本アプリでは扱わない）。
* **開く（ファイル）の新しい記録の書き込みに失敗した場合**: 新規作成と同じくメモリ上の一覧にだけ存在し、次の自動保存が成功した時点で記録が作られる。編集せずに別のキャンバスへ切り替えて再読み込みすると、そのキャンバスは一覧から消える（元のファイルは手元に残る）。
* **記録の図形のid**: ファイルのidがそのまま記録に入る場合がある（不正・重複を含む）。`replaceAllShapes`が読み込みのたびに正規化するため動作には影響せず、次の自動保存で正規化された内容に揃う。
* **`FileNotice`の型定義の二重化**: `CanvasFileOperations.js`と`CanvasPalette.js`（importを持たないため）の両方に定義する。形を変える場合は両方を揃えること。
* **通知の表示の大きさ**: ファイル名が長い場合、通知が複数行に折り返され、パレットの下端が伸びる。画面の高さが低い場合は通知の下部が画面外に出る可能性がある（フロートウィンドウはヘッダーのドラッグで移動できる）。
* **パレットを閉じている間の通知**: 読み取りの完了前にパレットを閉じると、通知は次に開いたときに見える（ファイル操作はパレットを開いた状態からのみ始まるため、実害は小さい）。
* **小窓とスペースパン**: `Space`を押したままファイル選択の小窓を開き、ウィンドウの`blur`が発生しない環境で表示中に離すと、`keyup`を取りこぼして`grab`カーソルが残る可能性がある（次の`Space`の`keyup`・ウィンドウの`blur`で解消。`window.prompt`と同じ扱い）。`InputTracker`は変更しない。
* **`main.js`の行数**: 改修後は約511行の見込み。今回は別モジュール化しないが、`// 7.6.`キャンバス管理ブロックの切り出しは別途のInterruptまたはPhase 3クローズ時の課題として扱うことを推奨する。
* **`CanvasLibrary.js`の規模**: `createCanvasFromShapes`・`#normalizeName`・JSDocの追加で約1000行になる見込み。自動保存と切り替え処理の順序保証の密結合のため分割しない方針（RES `261104_0049` 5章）を維持する。
