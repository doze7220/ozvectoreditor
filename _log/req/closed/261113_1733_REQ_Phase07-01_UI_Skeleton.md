## 【実装要件】
画面を、上端のツールバー・下端のステータスバー・その間のキャンバスの領域・フロートウィンドウのツールパレットへ組み替え、コントロールパネル（`#window-control-panel`）と図形選択パレット（`#window-shape-palette`）のウィンドウをなくす。以後のサブフェイズ（07-02 オプションバー、07-03 定規・表示の切り替え、07-05 スナップ）の置き場所を先に作るのが目的であり、**図形の描き方・選び方・履歴・保存・書き出しなどの働きは変えない**（変わるのは画面の部品の置き場所と、図形のツールを選ぶ手数だけ）。作業データの版・書き出し形式の版はどちらも2のまま。

本REQでいう「ツール」は、ツールパレットに並ぶ7つ（選択・キャンバス移動・直線・曲線・弧・矩形・円）を指す。

### 要件1: 画面の領域（ツールバー・ステータスバー・キャンバス）
* 画面の上端に**ツールバー**、下端に**ステータスバー**を固定で置く（フロートウィンドウではない。ドラッグで動かない。`×`なし）。どちらも`index.html`に静的に置く。
* **高さは常に一定・1行**（2026-11-13 発注者の決定）：ブラウザの幅が狭く項目が収まらないときも折り返さない。収まらない右側の項目は画面の外に切れて見えなくなる（横スクロールバーは出さない）。この決定により、ツールバー・ステータスバーの高さはブラウザのウィンドウの大きさ以外では変わらない。
* **キャンバス**（`#editor-canvas`）は、ツールバーとステータスバーを除いた領域にちょうど収める。ツールバー・ステータスバーの下に図形が隠れないこと。ブラウザのウィンドウの大きさを変えたら追従すること（既存の`window`の`resize` → `canvasManager.resize()` → `renderCurrentState()`の経路を使う。新しい監視の仕組み（`ResizeObserver`等）は、既存の経路で足りないと判断した場合のみ理由を添えて足す）。
* **キャンバスの位置と大きさを決める記述は1か所にまとめる**（例：ツールバー・ステータスバーの高さをCSSのカスタムプロパティで定義し、キャンバス・覆い要素・フロートウィンドウの既定の位置がそれを参照する）。Phase 07-03で、ツールバーの下と画面の左端に定規を足してキャンバスの領域をさらに狭めるため、そのときに直す箇所が1か所で済む構成にすること（具体的な構成は計画時に決めて記載する）。
* **座標がずれないこと**：キャンバス上のクリック・ドラッグ・ホイールでのズームの位置が、カーソルの位置とずれない。マウスの座標は`InputTracker.getScreenCoordinate`がキャンバスの`getBoundingClientRect()`を基準に計算しているため、`InputTracker`の変更は不要な見込みである。計画時に、キャンバスの位置が画面の左上でなくなっても座標の計算・描画（`CanvasManager.resize`の`clientWidth`/`clientHeight`、`DragTracker`）が正しいことを実コードで確かめ、結果を計画書に記載すること。
* **表示のリセット・キーボードでの拡大縮小の中心**：`main.js`の`resetViewToCenter`・`zoomAtCanvasCenter`は`canvas.clientWidth / 2`・`canvas.clientHeight / 2`を使っている。キャンバスの領域が変わった後も、「キャンバスの領域の中心」が基準になる（原点がキャンバスの領域の中央に来る）ことを確かめること（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章B【Phase02-04・低優先】）。
* **読み込み中の覆い要素**（`#canvas-loading-cover`）：キャンバスの領域を覆い、読み込み完了までキャンバスへのマウス入力を遮る働きは変えない。読み込み中も、ツールバー・ステータスバー・フロートウィンドウのボタンは押せる（今のコントロールパネルと同じ扱い）。`index.html`の時点で表示状態から始まること、`.canvas-loading-cover[hidden] { display: none; }`が必須であることは変えない。
* **重なりの順**：キャンバス → 覆い要素 → ツールバー・ステータスバー → フロートウィンドウ（最前面）。フロートウィンドウは、ツールバー・ステータスバーに重なる位置へ動かせ、重ねたときはウィンドウが手前に表示される（2026-11-13 発注者の決定。動かせる範囲の制限は足さない。`WindowManager`は変更しない）。
* ツールバー・ステータスバーの上でのマウス操作（ボタンの押下・何もない所のクリック）が、キャンバスの操作（図形の作成・選択・ドラッグ）として扱われないこと。一方、キャンバスで始めたドラッグ（図形の移動・範囲選択・パン）の途中でカーソルがツールバー・ステータスバーの上へ出ても、従来のフロートウィンドウ外と同じくドラッグが続き、ボタンを離した所で終わること（`DragTracker`は`window`を購読している）。計画時に実コードで確かめ、必要な扱いを記載すること。

  3. やり直し（今の`#history-redo`）
  4. 削除（今の`#selection-delete`）

### 要件4: ツールパレット（フロートウィンドウ）
* 新しいフロートウィンドウ「ツールパレット」を`index.html`に**静的に**置き、常に表示する（`hidden`にしない。`×`ボタンは置かない。開閉の呼び出し口は作らない。`WindowManager`は起動時にDOMにある`.float-window`だけを検知するため、検知の仕組みは足さず静的に置く＝DIRの持ち越し事項への回答）。ヘッダーをドラッグして動かせる（`WindowManager`の既存の仕組みで足りる）。
* **既定の位置は画面の左端、ツールバーのすぐ下**。ボタンは**縦1列**に、上から 選択・キャンバス移動・（区切り）・直線・曲線・弧・矩形・円 の順で並べる（図形の並びは`SHAPE_TYPES`の並び＝数字キー`1`〜`5`の割り当て順のまま）。ウィンドウの幅はアイコンのボタン1列ぶんの細さにする（ヘッダーの見出しの文字は、幅に収まる短いものにするか置かないかを計画時に決める。ドラッグできるヘッダーは必ず置く）。
* **ボタンを押したときの働き**：
  * 「選択」「キャンバス移動」：今の同名のモードボタンと同じ（`applyMode`の経路）。
  * 図形のボタン（直線・曲線・弧・矩形・円）：**1回押すと、その図形を描く状態になる**（今の「図形作成」を押してから図形を選ぶ2回の操作が1回になる）。動きは今の数字キーと同じにする（`main.js`の`KeyboardShortcuts`へ注入している`setShapeType`コールバックと同じ：図形作成モード以外なら`applyMode(OperationMode.CREATE)`、続けて`applyShapeType(type)`）。ボタンと数字キーは**同じ1つの関数を呼ぶ**形にまとめること（同一経路の原則）。
* **内部の状態は変えない**：`InputTracker`の操作モード（`OperationMode`の`SELECT`・`CREATE`・`PAN`の3値）と図形種別（`currentShapeType`）の持ち方、`setMode`・`setShapeType`の働きは変えない。変えるのは画面の部品と`main.js`の配線だけである（`InputTracker.js`のロジックは変更しない）。
* **押し込みの表示**（今どのツールか）：7つのボタンのうち**常にちょうど1つ**が押し込みの表示（`.active`）になる。選択モード → 「選択」、キャンバス移動モード → 「キャンバス移動」、図形作成モード → 現在の図形種別のボタン。表示は、既存どおり`inputTracker.getMode()`・`inputTracker.getShapeType()`で実際の内部状態を読み返して同期する（`applyMode`・`applyShapeType`の経路。専用の同期経路を足さない）。貼り付け・全選択・キャンバスの切り替え・インポート等で操作モードが切り替わったときも、既存の`applyMode`の経路で表示が追従すること。
  * 「操作モードと図形種別から、押し込みにするツールを求める規則」は、DOMに触れない・状態を持たない形で1か所に置き、自動テスト（`node --test`）で確かめる（DIR 4章「`InputTracker`への足し方」と同じ考え方。`main.js`に判定を書かない。置き場所は計画時に決めて記載する。`InputTracker`へは入れない）。
* **半透明にしない・常に押せる**：ツールパレットは、どの操作モードでも半透明にならず、ボタンを押せ、ヘッダーをドラッグして動かせる（`.disabled`を使わない）。
* **キー**（2026-11-13 発注者の決定）：
  * `V`・`H`：従来どおり（選択・キャンバス移動へ切り替え。押し込みの表示が追従する）。
  * 数字キー`1`〜`5`（テンキーを含む）：従来どおり、押すとその図形を描く状態になる（今の実装は、図形作成モード以外なら図形作成モードへ切り替えてから図形種別を変える。変えない）。押し込みの表示が追従する。
  * `P`：従来どおり図形作成モードへ切り替える＝**最後に使っていた図形（起動直後は直線）を描く状態になり、その図形のボタンが押し込みの表示になる**。「図形作成」のボタンはなくなるため、`P`を`title`に書くボタンは無い。
  * `SHORTCUT_BINDINGS`（`js/core/KeyboardShortcuts.js`）の対応表は変えない。
* **UI部品の置き場所**：ツールパレットのDOMの配線は`palette/`のUI部品が担う（既存の`palette/`の原則どおりDOM操作専任で、importを持たず、`VectorModel`・図形データ・選択状態・`InputTracker`に関与しない。受け取るのは注入された値とコールバックのみ）。今の`js/palette/PaletteController.js`（図形選択パレットの配線）を作り替えるか、新しい部品を作って`PaletteController.js`を削除するかは計画時に決めて記載する。いずれの場合も、**使われなくなったコード（`setEnabled`等）・ファイルを残さない**こと。
* **ボタンのidの命名規則**（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章C「初期表示の暗黙の結合」）：今は図形のボタンのidが`palette-${type}`で、`PaletteController`が起動時に`SHAPE_TYPES`と照合し、不整合を`console.warn`で報告している。ツールパレットのボタンのidの規則（選択・キャンバス移動を含む7つ）を計画時に決め、`index.html`と`main.js`（とUI部品）を揃えること。図形種別の一覧とDOMの不整合を起動時に`console.warn`で報告する働きは残すこと。
* **起動時の表示**：`index.html`の初期の静的な記述（JSの読み込み前に見える押し込みの表示）と、`InputTracker`の初期モード（選択）・起動時の`applyMode(OperationMode.SELECT)`による同期を揃えること（同持ち越し事項）。

### 要件6: なくすものと、残すウィンドウの既定の位置
* **なくすもの**：コントロールパネル（`#window-control-panel`）、図形選択パレット（`#window-shape-palette`）、「図形作成」のボタン（`#mode-create`）、およびそれらだけが使っていたCSS・JSのコード（例：フロートウィンドウ全体を非活性にする`.disabled`クラスは、図形選択パレットだけが使っている。計画時に実コードで使用箇所を確かめ、使われなくなるものを計画書に列挙して削除すること）。コントロールパネルの見出しにあったアプリ名「OZ Vector Editor」の表示は置き直さない（ページのタイトルにある）。
* **残すウィンドウ**（中身と働きは変えない）と既定の位置：
  * キャンバスパレット（`#window-canvas-palette`）：画面の右上、ツールバーのすぐ下。`hidden`で始まり、ツールバーのボタンで開閉する（`PaletteLauncher`の働きは変えない）。
  * プロパティパネル（`#window-property-panel`）：開いた状態のキャンバスパレットの左隣、ツールバーのすぐ下。今のまま常に表示し、従来どおり使える（オプションバーへ移すのはPhase 07-02。本サブフェイズでは位置以外を変えない）。
  * `?dev`の確認用ウィンドウ（`#window-dev-panel`）：ツールパレットの右隣、ツールバーのすぐ下。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 依存方向（`main.js → edit → io → core → shapes`の一方向。`core/`は`edit/`・`io/`をimportしない）、`InputTracker`が画面のボタン・DOMのidを知らないこと、`palette/`のUI部品がDOM操作専任で`VectorModel`・図形データ・選択状態に関与しないこと、`main.js`が判定ロジックを持たないこと、再描画・UI同期を既存の経路のみで行うこと（開発資料3章「同期の経路」）、ボタンとショートカットが同じ操作関数を呼ぶこと（同一経路の原則）、`CanvasManager`が状態を持たないことを維持すること。外部フレームワーク・ライブラリ・ビルドツール・CSSファイルの分割を導入せず、スタイルは`index.html`の`<style>`に内包する Vanilla JS の原則を維持すること。
*   **既存の振る舞いの不変** : 図形の描画・当たり判定・作成の手順・選択・移動・変形・削除・結合・描き足し・コピー/貼り付け/複製・重なり順・スタイルの変更・取り消し/やり直し・自動保存・ファイル入出力・書き出しの結果、既存のショートカットの対応表、キャンバスパレット・プロパティパネル・`?dev`の確認用ウィンドウの中身を変えないこと（変わるのは、要件1〜6で定めた画面の構成・ボタンの置き場所と見た目・ウィンドウの既定の位置、図形のボタンを1回押すとその図形を描く状態になること）。既存のエラー文・`console.warn`の文言は、対象の名前が変わるもの（例：図形選択パレット → ツールパレット）を除き変えないこと。
*   **スコープの厳守** : 変更対象の見込みは、`index.html`・`js/main.js`・`js/palette/`（ツールパレットのUI部品の新設または`PaletteController.js`の作り替え・削除、`PaletteLauncher.js`のコメント・JSDoc）、要件4の規則を置くモジュールの新設（置き場所は計画時に決める）とそのテストファイル、`js/core/InputTracker.js`・`js/core/KeyboardShortcuts.js`・`js/core/ShapeFactory.js`の**コメント・JSDocのみ**（要件7）とする（最終タスクの`PROJECT_ARCHITECTURE.md`・`_doc/arch/`の該当ファイルを除く）。`js/core/CanvasManager.js`・`js/core/ViewTransform.js`・`js/core/WindowManager.js`・`js/core/DragTracker.js`・`js/core/VectorModel.js`・`js/core/HistoryManager.js`・`js/core/PointHitRules.js`・`js/io/`・`js/edit/`・`js/shapes/`・`js/check/`・`sprite-check.html`・既存の`test/`のファイル・`js/palette/`のその他のファイル（`CanvasPalette.js`・`DevPanel.js`・`PropertyShapeSection.js`・`PropertyOrderSection.js`）は変更しない見込みである。それ以外の変更（上で「コメント・JSDocのみ」としたファイルのロジックの変更を含む）が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスクの粒度** : 1タスク＝原則1ファイル（ソースの新設・変更は1ファイル、テストは1テストファイル。ただしソースとそのソースを直接確かめるテストを同じタスクにまとめてよい）とする。ただし`index.html`のマークアップ・idの変更と、それを参照する`js/main.js`・UI部品の配線の変更は、片方だけでは起動時に壊れるため、**各タスクの完了時点で`node --test`が全件成功し、かつ画面が壊れていない（起動してこれまでの操作ができ、コンソールにエラーが出ない）状態を保つ順序・まとめ方**を計画時に決めること（例：規則のモジュールとテスト → ツールパレットのUI部品（まだ使わない）→ 画面の領域（ツールバー・ステータスバーの枠とキャンバスの領域。既存のウィンドウは残す）→ ツールバー・ステータスバーへのボタンの移設（idを保てば`main.js`の変更は最小）→ ツールパレットへの切り替えとコントロールパネル・図形選択パレットの削除（`index.html`と`main.js`を同じタスクで揃える）→ コメント・JSDocの修正 → 開発資料の反映）。同じタスクで複数ファイルを変える場合は、その理由を計画書に記載すること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設の全`.js`ファイルの先頭行に、単一責務のJSDoc（3行以内）を記載すること。既存ファイルの責務定義を逸脱するロジックを足さないこと。作り替え・改名するファイルは、責務定義を実態へ改めること。
