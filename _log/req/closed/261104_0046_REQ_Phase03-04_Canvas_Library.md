## 【実装要件】
現状、キャンバスは1枚だけで、ブラウザを再読み込みすると作業内容が失われる。本作業では、ブラウザ内（IndexedDB）に複数のキャンバスを保存し、編集中のキャンバスを自動保存し、一覧から切り替えて開く・新規作成・名前の変更・削除ができるようにする。これらの操作は、コントロールパネルから開閉する専用のパレット（キャンバスパレット）に集約する。

**用語の定義（本REQ・RES・コード内JSDocで統一すること）**
* **キャンバス**: 名前を持ち、ブラウザ内に保存される1つの作品（図形一式）の単位。画面に開くキャンバスは常に1枚。
* **キャンバス一覧**: ブラウザ内に保存されているキャンバスの集まり。
* **開いているキャンバス**: 現在画面に表示され、編集の対象となっているキャンバス。
* **キャンバス記録**: 1つのキャンバスの保存単位。キャンバスの識別子・名前・最終更新日時・作業データ（Phase 03-01の作業データ形式のオブジェクト）からなる（具体的な項目名・形は計画時に決める）。
* **自動保存**: 開いているキャンバスの図形一式が変わったとき、利用者の操作なしにキャンバス記録を更新すること。
* **キャンバスパレット**: キャンバス一覧の表示と、新規作成・名前の変更・削除の操作を担うフロートウィンドウ（本作業で新設）。
* **呼び出し口**: コントロールパネル上の、他のパレットを開閉するボタン（キャンバスパレットが最初の例）。
* 編集操作・履歴・スナップショットの定義はPhase 03-02（REQ `261103_1904`）、作業データ形式・シリアライズ／デシリアライズの定義はPhase 03-01（REQ `261101_2257`）、クリップボードの定義はPhase 03-03（REQ `261103_2355`）、選択集合・作成中の図形の定義はPhase 02-03（REQ `261018_0212`）、操作モードの定義はPhase 02-01に従う。

### 要件1: 保存先と保存内容（発注者決定、2026-11-04）
* 保存先はブラウザの**IndexedDB**とする（`localStorage`は容量約5MBのため使わない）。データベース名・オブジェクトストア名・データベースの版番号は1箇所の定数で定義する。
* 保存する内容は、キャンバスごとのキャンバス記録と、「最後に開いていたキャンバスの識別子」とする。
  * 作業データはPhase 03-01の作業データ形式（`DocumentSerializer.serialize`の戻り値。版番号を含む）で保存する。読み込みは`DocumentSerializer.deserialize`を通し、旧版のマイグレーションはその既存の仕組みに任せる（保存処理側に版の知識を持ち込まない）。
  * **保存しないもの**: Undo/Redoの履歴、選択集合・ホバー・作成中の図形・選択矩形、ビュー変換（倍率・表示位置。発注者決定：保存しない。開く・再読み込みのたびに初期表示）、クリップボード。
* キャンバスの識別子は、図形のid（`VectorModel`内に閉じた`shape-<連番>`形式）とは別体系とし、再読み込み後も他のキャンバスと衝突しないものにする（形式は計画時に決める。形式の知識は保存・キャンバス管理を担う処理の中に閉じること）。
* IndexedDBへのアクセス（開く・読む・書く・消す）は、DOMに触れない専用の処理（新設。置き場所の候補は`js/io/`）に閉じ込め、他のクラスがIndexedDBのAPIを直接呼ばないこと。図形種別の分岐・図形固有のプロパティ名を持たないこと。
* IndexedDBが使えない・保存に失敗した場合（プライベートブラウズ・容量超過等）でも、アプリは停止せず編集は続けられること。保存できていないことが画面上で分かる最小限の表示（例：キャンバスパレット内の短い文言）を計画時に決めて記載すること（`console.warn`のみにしない）。
* 同じアプリを複数のタブで同時に開いた場合の整合は扱わない（後から保存した側が残る。Non-goals）。

### 要件2: 自動保存
* 開いているキャンバスの図形一式が変わったとき（図形の作成・削除・移動・変形・貼り付け・切り取り・複製・取り消し・やり直し、`?dev`の確認用ウィンドウからの復元）に、キャンバス記録の作業データと最終更新日時を自動で更新する。
  * 変更の検知経路は計画時に決める。第一候補は既存の`historyManager.onChange`（編集操作の記録・取り消し・やり直しで通知される）であり、選択の変更・ホバー・パン・ズームだけでは保存しないこと。`model.onChange`ごとに保存する設計にする場合は、その理由と保存回数の見込みを計画書に記載すること。
* 保存のタイミングは、変更のたびに**少し間をおいてまとめて保存する**（最後の変更から約0.5秒。待ち時間は1箇所の定数で定義する。ドラッグ中の途中経過は編集操作として確定しないため保存されない）。
* ページを閉じる・再読み込みする直前に未保存の変更が残っていても失われにくいよう、ページが非表示になる時点（`visibilitychange`／`pagehide`等）で保留中の保存を直ちに行うこと（方式は計画時に決める）。
* 名前の変更は、その時点でキャンバス記録の名前を保存する（最終更新日時の扱いは計画時に決めて記載すること）。
* 保存処理は非同期になる。保存の完了を待たずに次の編集・キャンバスの切り替えが行われても、別のキャンバスの記録へ誤って書き込まないこと（例：キャンバスAの保留中の保存が、Bへ切り替えた後にBの内容でAを上書きしない／Bの記録へAの内容を書かない）。切り替え時は、切り替え前のキャンバスの保留中の保存を先に確定させること。

### 要件3: 起動時の復元
* 起動時、「最後に開いていたキャンバス」をその状態で開く（図形一式。ビュー変換は初期表示、操作モードは選択モード、履歴は空）。
* 最後に開いていたキャンバスが見つからない場合（削除済み等）は、キャンバス一覧のうち最終更新日時が最も新しいものを開く。キャンバスが1枚もない場合（初回起動）は、新しい空のキャンバスを作成して開く。
* IndexedDBからの読み込みは非同期のため、読み込み完了前の利用者の操作が、読み込んだ内容で消される・別のキャンバスに保存される等の不整合を起こさないこと（読み込み完了までの扱いを計画時に決めて記載すること）。
* キャンバス記録の作業データが壊れている・読み込めない図形を含む場合は、アプリを停止させない。全体が読み込めない場合の扱い（そのキャンバスを開かない等）、一部の図形のスキップの扱いを計画時に決めて記載すること（自動保存でスキップした図形が記録から消えることに注意。少なくとも`console.warn`を残すこと。一般利用者向けの読み込み失敗通知UIはPhase 03-05で見直す）。

### 要件4: キャンバスを開く・新規作成（共通の切り替え処理）
* キャンバスパレットの一覧から別のキャンバスを選ぶと、開いているキャンバスと入れ替わる（画面に開くキャンバスは常に1枚）。開いているキャンバス自身を選んだ場合は何もしない。
* 「新規作成」で、空のキャンバスを作成してキャンバス一覧に加え、それを開く。新しいキャンバスの名前は「無題 1」「無題 2」…と、既存の名前と重ならない連番で自動で付ける（発注者決定）。
* 開く・新規作成のどちらも、次を行う共通の切り替え処理を通すこと（処理の置き場所は計画時に決める。順序を計画書に記載すること）。
  1. 進行中の入力操作の中断（作成途中の図形の破棄。ドラッグ中の扱いは計画時に決める）と、選択モードへの切り替え（`applyMode`の経路）。
  2. 切り替え前のキャンバスの保留中の保存の確定（要件2）。
  3. 図形一式の入れ替え（`VectorModel.replaceAllShapes`。図形のidは記録されたものを保持する既存仕様に従う）。
  4. **履歴のリセット**（`historyManager.clear()`。`_doc/COWORK_STATUS.md` 2章P3【03-04へ・03-02由来】）。切り替えそのものは編集操作として記録しない（取り消しで前のキャンバスへ戻らないこと）。
  5. ビュー変換を初期表示へ戻す（`viewTransform.reset()`）。
  6. 「最後に開いていたキャンバスの識別子」の保存と、画面上のキャンバス名の表示の更新。
* **クリップボードは切り替えで消えない**（Phase 03-03の設計どおり。`ClipboardController`のインスタンスはキャンバスごとに作り直さない）。別のキャンバスでの貼り付けが、通常の貼り付けと同じ規則（新しいid・ずらし量・追加した図形だけを選択・1件の編集操作）で働くこと。貼り付けの段数を切り替えでリセットするか否かを計画時に決めて記載すること。

### 要件5: 名前の変更・削除（発注者決定、2026-11-04：ブラウザ標準の小窓を使う）
* 名前の変更は、キャンバスパレットの操作からブラウザ標準の入力用の小窓（`window.prompt`）で行う。初期値は現在の名前。キャンセル・空文字（前後の空白を除いて空）の場合は名前を変えない。名前の重複は許す。名前の最大文字数を設けるか否かを計画時に決めて記載すること。
* 削除は、ブラウザ標準の確認用の小窓（`window.confirm`。文言にキャンバス名を含める）で「OK」を選んだ場合のみ行う。
* 名前の変更・削除の対象は、開いているキャンバスだけでなく一覧の任意のキャンバスにできることを第一候補とする（一覧の各行に操作を置くか、開いているキャンバスのみを対象にするかは、パレットの使いやすさと実装量から計画時に決めて記載すること）。
* **開いているキャンバスを削除した場合**（発注者決定、2026-11-04）: 残りのキャンバスのうち最終更新日時が最も新しいものを開く（要件4の共通の切り替え処理を通す）。1枚も残らない場合は、新しい空のキャンバスを作成して開く。削除したキャンバスの保留中の自動保存が、削除後に記録を復活させないこと。
* 開いていないキャンバスの削除は、開いているキャンバス・履歴に影響しないこと。
* `window.prompt`／`window.confirm`の表示中はページのキー入力・マウス操作が止まるが、小窓を閉じた後に修飾キーの押下状態の取り違え・スペースパンの状態の残留等が起きないかを計画時に確認し、懸念があれば計画書に記載すること。

### 要件6: キャンバスパレットと呼び出し口（発注者決定、2026-11-04：開閉式）
* コントロールパネルに、キャンバスパレットを開閉するボタン（呼び出し口。例：`📁 キャンバス`）を追加する。押すとパレットが開き、開いている状態で押すと閉じる。開いている間はボタンが押された状態の見た目（既存の`.tool-btn.active`等）になる。
* キャンバスパレットのDOMは`index.html`に静的に置き、表示・非表示を切り替える（`WindowManager`の動的追加ウィンドウ非対応（`_doc/COWORK_STATUS.md` 2章C）に抵触しないため）。起動時は閉じた状態とする。表示中はヘッダーでドラッグ移動できること（既存の`.float-window`規格）。
* キャンバスパレットのヘッダーの`×`ボタンでパレットを閉じられる（呼び出し口のボタンの見た目も閉じた状態に戻る）。他のウィンドウ（コントロールパネル・図形パレット・`?dev`の確認用ウィンドウ）の`×`ボタンは無機能のまま変えない（全ウィンドウ共通の閉じる機能はNon-goals。`_doc/COWORK_STATUS.md` 2章P3【03-04へ】C-46は持ち越し）。
* 呼び出し口は、後続Phaseでプロパティパネル等の別のパレットを同じ形で追加しやすい構造にすること（例：ボタンのidとパレットのidの対応を1箇所で持ち、開閉処理を共通化する。具体的な形は計画時に決める）。
* キャンバスパレットの内容は次を含む（配置・見た目は計画時に決めてよい）。
  * キャンバス一覧（最終更新日時の新しい順。各行にキャンバス名。開いているキャンバスの行が分かる見た目）。行を押すとそのキャンバスを開く。キャンバス数が多い場合はパレット内でスクロールできること。
  * 「新規作成」「名前の変更」「削除」の操作（要件4・5）。
  * 保存できていないことの表示（要件1）。
* キャンバスパレットの初期位置は、コントロールパネル・図形パレットと重ならない位置とする（例：コントロールパネルの左隣）。`?dev`の確認用ウィンドウ（左上）とも重ならないことが望ましい。
* キャンバスパレットはDOM操作を担うUI部品とし（置き場所の候補は`js/palette/`）、`VectorModel`・図形データ・IndexedDBに直接依存しないこと（一覧の表示内容と操作の実行は、`main.js`等からの注入で受け取る）。
* コントロールパネルにボタン行を追加すると図形パレットと重なるため（`_doc/COWORK_STATUS.md` 2章C）、`#window-shape-palette`の`top`を調整し、余白24px以上を確保すること（計算根拠を計画書に記載すること）。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `CanvasManager`（描画層）に状態を持たせない、`VectorModel`・`InputTracker`・`DocumentSerializer`・`HistoryManager`・保存処理（新設）・キャンバス一覧の管理（新設）がDOMに触れない、UI部品（キャンバスパレット）が`VectorModel`・図形データ・IndexedDBに直接依存しない、という責務分離を維持すること。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **図形種別分岐の局所化維持** : 図形種別による分岐・対応づけは`ShapeFactory.js`の対応表のみとし、保存処理・キャンバス一覧の管理・キャンバスパレット・`main.js`に図形種別のif/switch分岐や図形固有のプロパティ名（`x1`・`points`・`startAngle`等）を持ち込まないこと。作業データは不透明なオブジェクトとして受け渡すこと。
*   **id形式の局所化維持** : 図形のid形式（`shape-<連番>`）の知識は`VectorModel.js`内に閉じること。キャンバスの識別子の形式は、それを採番する新設クラス内に閉じること。
*   **IndexedDBアクセスの局所化** : IndexedDBのAPI呼び出しは新設の保存処理1ファイルに閉じること。
*   **履歴の扱い** : キャンバスの切り替え・新規作成・削除・名前の変更は編集操作として記録しないこと。履歴のリセットは既存の`historyManager.clear()`を呼ぶこと。`HistoryManager`の仕様変更を行わないこと。
*   **UI同期経路の一元化** : 再描画・削除ボタン・取り消し/やり直しボタンの同期は、既存の`model.onChange`経路と`historyManager.onChange`経路のみで行い、キャンバス切り替えごとに別の再描画・同期処理を書かないこと（キャンバス名の表示・一覧の表示の同期は、新設クラスの変更通知等の1経路にまとめること）。
*   **グローバル変数の禁止** : `window`への公開を行わないこと（`window.prompt`／`window.confirm`／`document.title`の利用は可）。
*   **スコープの厳守** : 変更対象は`index.html`（キャンバスパレットのDOM・スタイル、コントロールパネルの呼び出し口とキャンバス名の表示、`#window-shape-palette`の`top`調整）、`js/main.js`（配線、スナップショット処理の切り出しに伴う置き換え）、新設の保存処理ファイル、新設のキャンバス一覧の管理ファイル、新設のキャンバスパレットファイル、新設のスナップショット処理ファイル、および呼び出し口の開閉処理を置くファイル（新設または`js/palette/`配下。計画時に決める）とする（最終タスクの`PROJECT_ARCHITECTURE.md`を除く）。`js/core/WindowManager.js`は、静的に置いた非表示のウィンドウのドラッグ移動・前面化が既存実装で働かない場合に限り変更してよい（必要とする理由を計画書に記載）。それ以外のファイル（`CanvasManager.js`／`ShapeFactory.js`／`ViewTransform.js`／`DragTracker.js`／`InputTracker.js`／`KeyboardShortcuts.js`／`VectorModel.js`／`HistoryManager.js`／`DocumentSerializer.js`／`PaletteController.js`／`DevPanel.js`／`ClipboardController.js`／`ShapeInserter.js`／`shapes/`の4ファイル）は変更しないこと。計画立案中にこれらの変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスク順序** : 新しいタスクは、その実行時点で存在しないファイル・メソッドを参照しないこと（例：スナップショット処理の切り出し → 保存処理の新設 → キャンバス一覧の管理の新設 → キャンバスパレットと呼び出し口の新設 → `main.js`の配線、の順）。各タスク完了時点でアプリが起動・動作する状態を保つ順序とすること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設ファイルを含む改修対象の全`.js`ファイルは、先頭行の単一責務JSDoc（3行以内）が改修後の実態と一致していることを確認し、必要なら更新すること。
