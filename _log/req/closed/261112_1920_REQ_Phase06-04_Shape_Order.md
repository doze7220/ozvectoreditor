## 【実装要件】
選択中の図形の重なり順（描画順）を「最前面へ」「前へ」「後ろへ」「最背面へ」の4つの操作で変えられるようにする（機体の絵で円を多角形より手前に描くため）。図形データの形・作業データの版・書き出し形式の版・描画・当たり分類の規則は変えない。

本REQでいう「重なり順」は`VectorModel`の図形の並び（`model.getShapes()`。先頭＝最も奥、末尾＝最も手前）を指す。これは作業データの`shapes`の並び・書き出しの`elements`の並び・描画順・当たり分類の「手前優先」の順と同じであり、**並びを変えるだけで保存・書き出し・描画・クリックで選ばれる図形のすべてが追従する**（専用の保存・書き出しの処理は足さない）。

### 要件1: 並べ替えの規則（2026-11-12 発注者の決定）
* **最前面へ**：選択中の図形をすべて並びの末尾（最も手前）へ移す。選択中の図形どうしの相対的な順は保つ。選択されていない図形どうしの相対的な順も保つ。
* **最背面へ**：選択中の図形をすべて並びの先頭（最も奥）へ移す。相対的な順の扱いは最前面へと同じ。
* **前へ**：選択中の各図形を、**並びの上で隣の図形1つ分だけ**手前へ移す（重なっているかどうかは見ない）。選択中の図形どうしの相対的な順は保ち、**離れている図形はまとめず、それぞれが1つずつ動く**。選択中の図形の手前隣が選択中の図形であれば、その図形は前の図形と一緒に動くか、動けなければ動かない（例：並び`[A, B*, C, D*, E]`（*＝選択）で前へ → `[A, C, B*, E, D*]`。`[A, B*, C*]`で前へ → 変わらない。`[A*, B, C*]`で前へ → `[B, A*, C*]`）。
* **後ろへ**：前へと対称（奥へ隣の図形1つ分）。
* 4つの操作とも、選択されていない図形どうしの相対的な順を保ち、図形のインスタンス・id・頂点・スタイルを変えない。並び以外は何も変えない。
* 規則は1か所に**状態を持たずDOMに触れない関数**として表し、`node --test`で確かめられるようにする。置き場所（`edit/`の新しい規則のモジュール等）と、`VectorModel`へ渡す形（新しい並び全体を渡す・操作の種類を渡す等）は計画時に決めて理由を記載すること。規則をボタン・キー・押せる/押せないの判定で二重に書かないこと（押せる/押せないも同じ規則から求める）。

### 要件2: モデルの変更と履歴
* 図形の並びを変える公開操作を`VectorModel`に足す（現在、並びを変えられる公開操作は無い。`replaceAllShapes`は選択集合等をクリアするため使わない）。**選択集合・ホバー・作成中の図形・選択矩形・吸い付きの表示の点・直前に使った値・idの採番には触れない**（並べ替え後も同じ図形が選ばれたまま）。並びが実際に変わった場合のみ`model.onChange`を通知する（1回）。図形の一覧のPhaseで、一覧のドラッグによる並べ替えからも使う見込みのため、特定のボタンの操作に結びつかない形を検討すること（計画時に決めて記載）。
* 1回の操作（ボタン1回・キー1回）を1件の編集操作として履歴に記録し、**Undo1回で元の並びに戻り、Redo1回でやり直せる**（DIRの実装要件）。記録は既存の`HistoryManager.beginEdit()`/`commitEdit()`で挟む方式に従う（開発資料3章6.）。スナップショットの作業データは並び順を含むため、取り消しで並びが戻る。並びが変わらない操作は記録しない（作業データの比較で自動的に記録されないことを含めてよい。どう保証するかを計画時に記載）。
* 手順（受理の判定・履歴の記録・モデルの呼び出し）は`edit/`の新しいクラス等に置き（`PathJoiner`と同じ位置づけ。`editRecorder`の注入等）、`InputTracker`へは入れない（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章C「`InputTracker`の肥大化防止」）。`main.js`は配線だけを行い、判定・並べ替えを持たない。
* **何もしない場合**（DIRの実装要件）：何も選んでいない（選択モード以外を含む）、すでに最前面（最背面）にある図形を同じ方向へ動かす等で並びが変わらないとき、アプリは停止せず、図形・選択集合・履歴は変わらない。
* **ドラッグ中**（`inputTracker.isDragging()`が真）は受理しない（`main.js`の`performJoin()`と同じ扱い。ボタンとキーの共通の入口で判定する）。キャンバスの読み込み中は選択集合が空のため何もしない（専用の判定は不要。開発資料3章1.）。

### 要件3: 操作の置き場所（2026-11-12 発注者の決定：プロパティパネルの新しい段）
* 「プロパティ」ウィンドウ（`index.html`の`#window-property-panel`）の「図形」の段の下に、新しい段「重なり順」を足し、「最前面へ」「前へ」「後ろへ」「最背面へ」の4つのボタンを置く（並べ方は2×2等、幅220pxに収まる形を計画時に決める）。開発資料3章13.「2段構成（段の足し方）」に従い、`index.html`に段の`<section class="property-section">`（見出し付き）、`palette/`にその段のUI部品1つ、`main.js`にその段の配線ブロック1つを足す。`PropertyShapeSection`・「図形」の段・その配線ブロックは変えない。要素idは段ごとの接頭辞で重複させない（接頭辞は計画時に決める）。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 依存方向（`main.js → edit → io → core → shapes`の一方向。`core/`は`edit/`・`io/`をimportしない。`palette/`のUI部品はimportを持たない）、`InputTracker`に重なり順の操作を入れないこと、`main.js`が判定・並べ替えのロジックを持たないこと、UI部品が表示とコールバックへの通知だけを行うこと、並べ替えの規則を1か所に置くこと、再描画・UI同期を既存の経路のみで行うこと（開発資料3章「同期の経路」）、プロパティパネルの段の足し方（3章13.）に従うこと。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **既存の振る舞いの不変** : 図形の描画・当たり分類・範囲選択・ハンドル・作成・移動・変形・削除・結合・描き足し・端点への吸い付き・コピー/貼り付け/複製・取り消し/やり直し・自動保存・ファイル入出力・書き出し・プロパティパネルの「図形」の段・既存のショートカットの結果を変えないこと。既存のエラー文は変えないこと。
*   **スコープの厳守** : 変更対象の見込みは、`js/core/VectorModel.js`（並べ替えの公開操作）、`js/core/KeyboardShortcuts.js`（対応表）、`js/main.js`（配線）、`index.html`（段・ボタン・スタイル）、`js/palette/`の新しいUI部品、`js/edit/`の新しいモジュール（規則・手順）、`test/`の新設・既存のテストファイルとする（最終タスクの`PROJECT_ARCHITECTURE.md`・`_doc/arch/`の該当ファイルを除く）。`js/shapes/`・`js/io/`・`js/check/`・`js/core/InputTracker.js`・`js/core/PointHitRules.js`・`js/palette/PropertyShapeSection.js`・`js/edit/`の既存のファイル・`sprite-check.html`は変更しない見込みである。それ以外の変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスクの粒度** : 1タスク＝原則1ファイル（ソースの新設・変更は1ファイル、テストは1テストファイル。ただしソースとそのソースを直接確かめるテストを同じタスクにまとめてよい）とし、各タスクの完了時点で`node --test`が全件成功し、かつ画面が壊れていない（起動してこれまでの操作ができる）状態を保つ順序とすること（例：並べ替えの規則とテスト → `VectorModel`の公開操作とテスト → 手順のクラスとテスト → UI部品と`index.html` → `KeyboardShortcuts` → `main.js`の配線 → 開発資料の反映）。`KeyboardShortcuts`の対応表にactionを足すと、`main.js`が同名のコールバックを渡すまで起動時に例外になる（コンストラクタが対応表の全action名を要求する）ため、両者の順序または同じタスクにまとめるかを計画時に決めること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設の全`.js`ファイルの先頭行に、単一責務のJSDoc（3行以内）を記載すること。既存ファイルの責務定義を逸脱するロジックを足さないこと。
