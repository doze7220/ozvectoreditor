## 【実装要件】
塗られた図形（矩形・円・閉じたパス）の内側をクリックして選べるようにする。図形データの形・作業データの版・書き出し形式の版・描画は変えない。

本REQでいう「塗られている」は、図形の`draw`が塗りを描く条件（`this.isFillable() && typeof this.fillColor === 'string'`。`_doc/arch/12_shapes.md`「`draw`の描き方」）と同じ条件を満たすことを指す。「輪郭の当たり」は今の`hitTest(x, y, tolerance)`（輪郭線から画面上5pxの許容誤差以内）、「内側の当たり」は本REQで足す塗った内側の判定を指す。

### 要件1: 内側の当たり判定（図形クラス）
* **内側の判定は`hitTest`に含めず、新しい公開メソッドとして共通メソッド契約に足す**（14メソッド → 15メソッド）。名前は`hitTestFill(x, y)`とし、引数はワールド座標、戻り値は真偽値とする。`Line`・`Curve`・`Rect`・`Ellipse`・`Path`の5クラスすべてに実装し、5クラスのクラスJSDocの契約の列挙を揃えること（`hitTest`と分けるのは、要件2で「選択集合の図形の輪郭」と「内側」を別の優先順位で扱うため）。
* `hitTestFill`が真になるのは、**塗られている図形**で、かつ点が塗られている範囲の内側にあるときだけ。塗れるかの判定は必ず`isFillable()`を通し、規則を二重に書かないこと。`fillColor`が`null`の図形、塗れない形の図形（直線・曲線・弧・開いたパス。`fillColor`に色の文字列を持っていても）は常に偽。
* **自分自身と交差する閉じたパスは、Canvasの標準（nonzero）の規則で塗られている部分だけを内側とする**（DIRの決定）。`Rect`も`setVertex`で頂点を動かせるため、軸に平行・凸・自己交差なしを前提にせず、4頂点の多角形として同じ規則で判定すること。`Path`の内側は`draw`（`#tracePath`）と同じ頂点の並び（閉じる区間を含む）で判定する。曲線の区間を足すとき（パスの編集のPhase）に分岐を足す場所が分かるよう、JSDocに書くこと。
* **円の内側**は楕円の式（`(dx/rx)^2 + (dy/ry)^2 ≤ 1`）で厳密に判定する。`rx < 1 || ry < 1`等のつぶれた円で0除算・`NaN`・`Infinity`による誤判定（画面全体で当たる等）が起きないこと（つぶれた円の内側の扱いは計画時に決めて記載する。輪郭の当たりで選べるため、偽としてよい）。
* **内側の判定には許容誤差を使わない**（輪郭の外側の5pxは、今の輪郭の当たりが受け持つ）。境界上の点の扱い（含むか）は計画時に決め、JSDocに書くこと。
* **多角形の内側の判定（nonzero）は共通モジュール`js/shapes/ShapeGeometry.js`に状態を持たない関数として足し**、`Rect`・`Path`から呼ぶ（図形クラスへ複製しない。`_doc/arch/12_shapes.md`「共通モジュール」）。
* **変えないもの**：`hitTest`（輪郭の当たり）・`intersectsRect`（範囲選択）・`draw`・`toDrawElement`・`toJSON`/`fromJSON`の結果。
* **`Ellipse.hitTest`の平均半径による近似**（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章C「当たり判定」）：本サブフェイズでは**見直さない**（現場設計AIの決定）。内側は厳密な式、輪郭は今の近似のままとする。両者の和が円の内側から輪郭の外側の許容幅までを隙間なく覆うこと（内側と輪郭の当たりの間に、どちらにも当たらない帯ができないこと）を計画時に確かめて記載すること。
* **JSDocの食い違いの修正**（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章D）：`js/shapes/ShapeDataValidation.js:18`の`DEFAULT_STROKE_WIDTH`のJSDocの括弧内「（新しく描く図形の太さ）」を実態に合わせて直す（新しく描く図形の太さは`core/VectorModel.js`の`DEFAULT_NEW_SHAPE_STYLE`が決め、図形クラスのコンストラクタの既定値は引数を省略したときの値。正しい位置づけは`PROJECT_ARCHITECTURE.md`2章「線の太さ2pxの4つの定義と位置づけ」）。JSDocのみの変更で、コードは変えない。

### 要件2: どの図形が選ばれるか（当たり分類の優先順位）
クリック・押下・ホバー・カーソルの形が共通に使う当たり分類（`InputTracker`の`#classifyPoint`。`PointHit`の`bodyId`）の「本体」の決め方を、次の規則に変える（**2026-11-12 発注者の決定：見た目どおり**）。ハンドルの規則は変えない。
1. **選択集合の図形のハンドル**：今のまま（図形配列の後ろ＝手前から`hitTestHandle`。`handle`に入る）。
2. **選択集合の図形の輪郭の当たり**：今のまま優先する（選んでいる図形をつかんで動かすため）。選択集合の図形が複数当たる場合は、**図形配列の後ろ（手前）にある図形**を採る（今は図形配列の先頭＝奥。下の3と向きを揃える）。
3. **それ以外**：図形配列の後ろ（手前）から順に調べ、**輪郭の当たりまたは内側の当たりが真になった最初の図形**を採る（線の近くか塗った内側かを区別しない）。選択集合の図形の内側もこの順番の中で扱い、**選択集合だからといって内側を優先しない**（大きな塗りの図形を選んだままでも、その手前にある小さな図形をクリックで選べるようにするため）。
* 結果として次が起きること：
  * 塗った図形の内側をクリックすると、その図形が選ばれる。塗った図形が重なっている所では、手前に描かれている図形が選ばれる（DIRの実装要件）。
  * 手前の塗った図形に隠れている奥の図形の輪郭の近くをクリックすると、手前の塗った図形が選ばれる（奥の図形が選択集合に入っていて、その輪郭の近くなら奥の図形。上の2）。
  * **既存の振る舞いの変化（発注者了承済み）**：塗りのない図形どうしの輪郭が重なる所をクリックすると、今は奥の図形が選ばれるが、手前の図形が選ばれるようになる。計画書・作業レポートにこの変化を明記すること。
  * 塗りなしの図形の内側、塗れない形の図形の内側（`fillColor`を持っていても）は、今どおり空白（範囲選択の開始・選択の解除）として扱われる。
* 押下・クリックの分岐の表（`handleMouseDown`・`handleClick`のJSDoc）は変えない。塗った内側も「本体」として扱われるため：選択集合内の図形の内側で押してドラッグ → 選択集合の移動。**選択集合外の図形の内側で押してそのままドラッグしても動かない（1回クリックで選んでからドラッグする）**（2026-11-12 発注者の決定：今の仕様に揃える）。塗った内側で押しても範囲選択は始まらない。
* ホバーの強調・カーソルの形は、同じ当たり分類の結果で今と同じ扱いになる（塗った内側にカーソルを乗せると、その図形のホバーの強調が出る）。
* **規則の置き場所**：`InputTracker`は図形種別を知らず、`hitTest`・`hitTestFill`・`hitTestHandle`・`isSelected`のポリモーフィックな呼び出しだけで判定すること（`isFillable()`・`fillColor`を`InputTracker`で読まない）。本体の優先順位の規則は、`node --test`で確かめられるよう**DOMに触れない関数**として表すことを基本とし、置き場所（`InputTracker.js`の非公開メソッドのままにするか、`core/`の新しいモジュール・`InputTracker.js`のexportする関数として切り出すか）は計画時に決めて理由を記載すること。`InputTracker`の再分離（状態の所有者設計）はDIRの「やらないこと」（精度のPhase）であり、切り出す場合も当たり分類の規則だけに限ること。`#classifyPoint`・`PointHit`のJSDoc、`InputTracker`のクラスJSDocの当たり分類の記述を新しい規則に揃えること。

### 要件3: 見えない図形の選び方
* **今のまま変えない**（2026-11-12 発注者の決定）。見えない図形（線なしで塗れない形、または線も塗りもない図形）は、輪郭付近のクリック・範囲選択・全選択で選べ、カーソルを乗せるとホバーの強調が出て、選ぶとハンドルが出る。見えない図形は塗られていないため内側の当たりは常に偽で、要件2の規則のもとでも輪郭の当たりだけで選ばれる。
* **線なしで塗られた図形の輪郭付近**：輪郭の当たり（輪郭線から画面上5px以内。塗りの外側の5pxを含む）も今どおり有効とする（現場設計AIの決定。線なしにしても選びやすさを変えないため）。

### 要件4: 範囲選択
* 範囲選択（ドラッグの矩形）は今のまま輪郭線だけで判定する（`intersectsRect`を変えない）。塗った内側が矩形にかかっても選ばれない（DIRの「やらないこと」）。

### 要件5: 書き出しとの整合
* 内側の当たりが真になる条件（塗られている図形）は、`draw`の`shouldFill`と、書き出し側（`io/CodeExporter.js`の`DRAW_SOURCE`の「`fillColor`が文字列で`polyline`/`ellipse`かつ`closed === true`」）と同じ結果になること（DIRの持ち越し事項。`_doc/COWORK_STATUS.md` 2章D）。`io/`は変更しない。

### 要件6: 自動テスト
開発資料`_doc/arch/16_test.md`の規則（置き場所と命名・`node:test`と`node:assert/strict`のみ・公開APIのみを通す・テストのためにソースを書き換えない・画面の操作や描画のテストは行わない）に従う。
* **多角形の内側の判定（`ShapeGeometry.js`）**：凸・凹の多角形の内側／外側、境界上の点（計画時に決めた扱い）、**五芒星（頂点を1つおきに結んだ自己交差する星形）の中心が内側になる**こと（nonzeroでは塗られ、evenoddでは塗られない位置）、**巻き数が0になる部分**（例：外側を一方向に回り、内側を逆方向に回る多角形の内側の穴）が内側にならないこと、頂点が3未満・面積0の多角形で例外や誤判定が起きないこと。
* **各図形クラスの`hitTestFill`**（`test/shapes/<クラス名>.test.js`）：塗られた矩形・円・閉じたパスの内側で真・外側で偽、`fillColor`が`null`なら偽、塗れない形（直線・曲線・弧・開いたパス）は`fillColor`が色の文字列でも偽、線なし（`strokeColor: null`）でも塗られていれば真、頂点を動かした矩形（軸に平行でない・凹・自己交差）、凹型の閉じたパス（`ship.js`の機体のような4頂点）のくぼみが偽、つぶれた円で例外・誤判定が起きないこと、`translate`後・`toJSON`→`fromJSON`の往復後も同じ結果になること。`hitTest`・`intersectsRect`の既存のテストは変えずに通ること（輪郭の当たり・範囲選択が変わらないことの確認）。
* **当たり分類の優先順位**（DOMに触れない関数として切り出した場合）：要件2の1〜3の各規則、少なくとも「選択中の奥の大きな塗った図形の上にある手前の図形の内側で、手前の図形が選ばれる」「選択集合の図形の輪郭が、手前の選択されていない塗った図形の内側より優先される」「塗りのない図形どうしの輪郭の重なりで手前が選ばれる」「塗りなしの図形の内側は何も当たらない」「見えない図形が輪郭の当たりで選ばれる」「選択集合の図形が複数当たるとき手前が選ばれる」。切り出さない場合は、その理由を計画書に記載し、これらをテストプレイの確認項目に含めること。

*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。
*   実装中に判断に迷った点、目視確認を推奨する箇所、将来この箇所を修正する際に注意すべき点（曲線の区間を足すときの`Path.hitTestFill`、弧の塗り・`Ellipse`の回転を入れるときの`Ellipse.hitTestFill`等）があれば、RESの「懸念事項・要確認ポイント」欄に記述する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。本作業では要件8により、`PROJECT_ARCHITECTURE.md`1章〜3章と`_doc/arch/12_shapes.md`・`_doc/arch/06_InputTracker.md`・`_doc/arch/16_test.md`の更新は必須と想定してタスク化すること（他は変更内容に応じて含める）。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 依存方向（`main.js → edit → io → core → shapes`の一方向。`core/`は`edit/`・`io/`をimportしない。`shapes/`は`core/`・`io/`をimportしない。共通モジュールは`shapes/`の外および互いをimportしない）、各図形クラスが共通メソッド契約を自律実装し共通の基底クラスを持たない設計、塗れるかの規則を`isFillable()`だけに置くこと、`InputTracker`が図形種別を知らないこと（if/switch分岐を持たず、ポリモーフィックな呼び出しのみ）、`ShapeFactory`の表引きのみの振り分け、`main.js`が判定ロジックを持たないこと、再描画・UI同期を既存の経路のみで行うこと（開発資料3章「同期の経路」）。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **既存の振る舞いの不変** : 図形の描画・輪郭の当たり（`hitTest`）・範囲選択（`intersectsRect`）・ハンドルの当たりと優先順位・作成・移動・変形・削除・結合・描き足し・端点への吸い付き・コピー/貼り付け/複製・取り消し/やり直し・自動保存・ファイル入出力・書き出し・プロパティパネル・ショートカットの結果を変えないこと（要件2の当たり分類の優先順位の変更を除く）。既存のエラー文は変えないこと。
*   **スコープの厳守** : 変更対象の見込みは、`js/shapes/`の図形クラス5つ（`Line.js`・`Curve.js`・`Rect.js`・`Ellipse.js`・`Path.js`）、`js/shapes/ShapeGeometry.js`、`js/shapes/ShapeDataValidation.js`（要件1のJSDocのみ）、`js/core/InputTracker.js`（当たり分類）、当たり分類の規則を切り出す場合の`js/core/`の新しいモジュール、`test/`の新設・既存のテストファイルとする（最終タスクの`PROJECT_ARCHITECTURE.md`・`_doc/arch/`の該当ファイルを除く）。`js/io/`・`js/edit/`・`js/palette/`・`js/check/`・`js/main.js`・`index.html`・`sprite-check.html`・`js/core/`のうち`InputTracker.js`以外の既存のファイル・`js/shapes/PathJoinRules.js`・`js/shapes/EndpointSnapRules.js`は変更しない見込みである。それ以外の変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスクの粒度** : 1タスク＝原則1ファイル（ソースの新設・変更は1ファイル、テストは1テストファイル。ただしソースとそのソースを直接確かめるテストを同じタスクにまとめてよい。5クラスのクラスJSDocの契約の列挙を揃える作業は、各クラスのタスクで行うか1タスクにまとめるかを計画時に決める）とし、各タスクの完了時点で`node --test`が全件成功し、かつ画面が壊れていない（起動してこれまでの操作ができる）状態を保つ順序とすること（例：`ShapeGeometry.js`の内側の判定とテスト → 各図形クラスの`hitTestFill`とテスト → 当たり分類の規則 → 開発資料の反映）。`InputTracker`が`hitTestFill`を呼ぶのは、5クラスすべてに`hitTestFill`が実装された後のタスクにすること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設の全`.js`ファイルの先頭行に、単一責務のJSDoc（3行以内）を記載すること。既存ファイルの責務定義を逸脱するロジックを足さないこと（`ShapeGeometry.js`の先頭の責務の記述に、足す計算を含めること）。
