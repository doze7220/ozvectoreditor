## 【実装要件】
現状、コントロールパネルの「直線ツール」ボタンと図形パレットの「直線」ボタンが同一の`tool='line'`を指しており、「操作モード」と「作成する図形種別」という2つの異なる概念が`InputTracker.currentTool`という1つの状態に混在している。本作業では、コントロールパネルを「現在の操作モード」を切り替える場所として再定義し、図形パレットを「図形作成モード中に作成する図形種別」を選ぶ場所として分離する。あわせて、キャンバス上でのカーソル形状による視覚フィードバックを導入する。

なお、次のサブフェイズ（Phase 02-02）でコントロールパネルに「キャンバス移動（パン）」モードボタンを同列に追加する予定である。本作業はその追加を見越し、**操作モードの種別を容易に増やせる構造**にしておくことを主眼とする（パンモード自体は本作業では実装しない）。

### 要件1: 操作モードと図形種別の分離
* 操作モードは「選択」「図形作成」の2種とする。内部識別子は`'select'`／`'create'`とする。
* 「作成する図形種別」（`'line'`／`'curve'`／`'arc'`／`'rect'`／`'circle'`）は、操作モードとは独立した状態として保持する。
* 図形作成モード中にキャンバスをクリックした際は、現在選ばれている図形種別で図形を作成する（作成フロー自体＝`VectorModel.startDraft(x, y, type)`以降の挙動はPhase 1から変更しない）。
* 図形作成モードへ切り替えた直後は、**前回図形作成モードで最後に選んでいた図形種別**が選ばれた状態に復帰する。アプリ起動後、一度も選んでいない場合は`'line'`とする。
* 図形作成モード中に図形パレットで別の図形種別を選んだ場合は、図形種別のみを切り替え、操作モードは`'create'`のまま維持する。作成途中（`DRAWING`状態）の図形があれば破棄してIDLEへ戻す。
* 操作モード切り替え時の既存の挙動（選択・ホバー状態のクリア、進行中の作成／ドラッグ操作の破棄とIDLE復帰）は維持する。
* 操作モードの切り替えAPIには引数バリデーションを設け、未知の値が渡された場合に内部状態を壊さないこと（無視して`console.warn`を出す等。方式は計画時に決めてよい）。図形種別の切り替えAPIも同様とする。
* 状態の保持先は計画時に決めてよいが、操作モード・図形種別はいずれも図形データではないため`VectorModel`には持たせないこと。現状`currentTool`を保持している`InputTracker`に置くことを第一候補とする。

### 要件2: コントロールパネルの操作モードボタン
* `index.html`のコントロールパネルに「選択」「図形作成」の2ボタンを並べる。現行の「🖱 選択ツール」（`#tool-select`）／「／ 直線ツール」（`#tool-line`）は、それぞれ「選択」「図形作成」ボタンへ置き換える（DOM id・アイコン文字は計画時に決めてよい）。
* 押したボタンだけがハイライト（`.active`）される。
* コントロールパネルのボタンの`.active`は**操作モードのみ**を反映し、図形パレットのボタンの`.active`は**図形種別のみ**を反映する。両者が同じ意味で同時にハイライトされる状態は解消すること。
* 図形パレットは、選択モード中は現状どおり非活性（`.disabled`）、図形作成モード中は活性とし、現在の図形種別のボタン1つだけがハイライトされる。
* `main.js`の`toolButtons`（コントロールパネル側ボタン表）は、Phase 02-02でモードボタンを1つ追加する際に「`index.html`へのボタン追加」と「表へのエントリ追加」だけで済む構造を維持・徹底すること（ループ処理本体やモード判定の`if`/`else`連鎖を書き換える必要がない設計）。
* `toolButtons`へエントリを追加する際は、対応するDOM要素を`index.html`側に先に用意すること（`document.getElementById(...)`が`null`を返すと`.classList`アクセスで`TypeError`になるため）。計画書のタスク順序もこれに従うこと。

### 要件3: カーソル形状による視覚フィードバック
キャンバス（`#editor-canvas`）上のマウスカーソル形状を、以下のとおり切り替える。

| 状況                                                           | カーソル（CSS `cursor`値） |
| -------------------------------------------------------------- | -------------------------- |
| 図形作成モード中（作成途中を含む）                             | `crosshair`                |
| 選択モード中、選択中図形のハンドル上（ハンドルドラッグ中を含む） | `move`                     |
| 選択モード中、図形の上（ホバー判定に該当）                     | `pointer`                  |
| 選択モード中、上記以外                                         | `default`                  |

* 判定の優先順位は「ハンドル上」＞「図形の上」＞「それ以外」とする。
* ハンドル上の判定は、選択中図形に対する`shape.hitTestHandle(...)`のポリモーフィック呼び出しで行う。図形種別ごとの`if`/`switch`分岐を持ち込まないこと。ハンドル種別ごとにカーソルを変える（リサイズ系カーソル等）必要はない。
* 操作モードを切り替えた直後（マウスを動かす前）でも、図形作成モードであれば`crosshair`になっていること。
* カーソル形状の設定をどのモジュールが担うかは計画時に決めてよいが、`CanvasManager`（状態を持たないレンダラー）には持たせないこと。

### 要件4: 既存の持ち越し事項の解消
* `InputTracker`の`handleMouseMove`／`handleMouseDown`のJSDoc説明文に、`currentTool`（本作業後は操作モード）によるガード条件が反映されていない記載漏れがあるため、本作業で該当メソッドを改修する際にあわせて修正すること。
* `InputTracker`内の`@param`／`@type`のツール種別の型注釈（`'select'|'line'`）を、本作業後の実態に合わせて更新すること。
* `keydown`による`Delete`/`Backspace`削除は、現状どおり選択モード中のみ有効とする（挙動は変更しない）。

### 要件5: コントロールパネルのヘッダードラッグ（回帰防止）
* フロートウィンドウ（コントロールパネル・図形パレット）のヘッダーをドラッグしてウィンドウを移動する機能は、`WindowManager`で実装済みである。**新規実装は不要**とし、本作業の変更でこの機能を回帰させないこと（`WindowManager.js`は変更対象外）。

### Non-goals（本作業では行わないこと）
* キャンバス移動（パン）モード・ズーム・グリッドの実装（Phase 02-02で行う）。
* 範囲選択・複数選択（Phase 02-03で行う）。
* 削除ボタン・キーボードショートカット・テキスト入力欄フォーカス時の誤爆対策（Phase 02-04で行う）。
* 図形クラス（`js/shapes/`配下）の変更、図形の作成・編集挙動そのものの変更。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。
*   実装中に判断に迷った点、目視確認を推奨する箇所、将来この箇所を修正する際に注意すべき点があれば、RESの「懸念事項・要確認ポイント」欄に記述する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。本作業では`main.js`（`applyTool`／`toolButtons`の意味づけ）、`InputTracker.js`（`currentTool`の分離・カーソル制御）、`PaletteController.js`（`setActiveTool`の意味づけ）の責務記述に影響が出る想定のため、更新は必須と想定してタスク化すること。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `CanvasManager`（描画層）に`VectorModel`（データ・状態）や操作モード・カーソル状態を持たせるなどの責務違反を起こす設計をしてはならない。また、外部フレームワークを導入しない Vanilla JS の原則を維持すること。
*   **概念の分離** : 「操作モード」と「図形種別」を1つの変数・1つの引数に混在させないこと。コントロールパネルは操作モードのみ、図形パレットは図形種別のみを扱う。
*   **拡張容易性（開閉原則）** : 操作モードを1種追加する際に、`main.js`のボタン走査ループ・`.active`切り替え処理の本体を書き換える必要がない設計とすること。モード判定のために個別ボタンごとの`if`/`else`分岐を新たに増やさないこと。
*   **図形種別分岐の局所化維持** : `ShapeFactory`内の`type`判定を唯一の例外とし、`VectorModel`/`CanvasManager`/`InputTracker`に図形種別のif/switch分岐を新たに持ち込まないこと（カーソル判定も`hitTest`/`hitTestHandle`のポリモーフィック呼び出しで行う）。
*   **UI部品の疎結合維持** : `PaletteController`は`InputTracker`へ直接依存せず、コールバック経由で`main.js`と接続する現在の構造を維持すること。`PaletteController`の公開APIを変更・追加する場合は、パレット本体の活性/非活性と5ボタンの`.active`制御というDOM操作専任の責務を逸脱しないこと。
*   **スコープの厳守** : 変更対象は`index.html`、`js/main.js`、`js/core/InputTracker.js`、`js/palette/PaletteController.js`の4ファイルとし（最終タスクの`PROJECT_ARCHITECTURE.md`を除く）、それ以外のファイル（`VectorModel.js`／`CanvasManager.js`／`WindowManager.js`／`ShapeFactory.js`／`js/shapes/`配下）は変更しないこと。計画立案中にこれらの変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 改修対象の全`.js`ファイルは、先頭行の単一責務JSDoc（3行以内）が改修後の実態と一致していることを確認し、必要なら更新すること。責務に合わない機能は当該ファイルに追記せず、別ファイルへの分離を検討すること。
