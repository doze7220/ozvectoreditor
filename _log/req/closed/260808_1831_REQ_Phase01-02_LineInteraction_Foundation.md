#### 【実装要件】
Phase01-01で構築したMVC最小骨格（`VectorModel` / `CanvasManager` / `InputTracker` / `shapes/Line.js`）を土台に、**LINE（直線）1種類のみ**を対象として、「入力」「描画」「座標の統一」の基盤を完全に固める。パレット（P1-3）は未実装のため、ツールモードの切り替えは「空白クリック＝新規作成」「既存図形クリック＝選択」という暗黙の分岐で行う。

##### 操作フロー仕様（確定済み・そのまま実現すること）
1.  **作成**：①空白キャンバスのクリックで「始点」が確定する ②マウス移動中、始点から現在のカーソル位置まで直線のプレビューが描画される ③再度のクリックで「終点」が確定し、直線が確定登録される。
2.  **選択**：①作成済みLINEにマウスカーソルをホバーさせると強調表示される（視覚仕様は本計画のスコープ外、暫定実装でよい） ②ホバー中にクリックすると、そのLINEが選択される ③選択中は「始点ハンドル」「終点ハンドル」「オブジェクト移動ハンドル」の3種が表示される ④選択中に空白部分をクリックすると選択解除される。
3.  **再編集**：①始点・終点ハンドルをドラッグすることで、その端点の位置を個別に再調整できる ②オブジェクト移動ハンドル（線分の中点に配置）をドラッグすることで、直線全体を平行移動できる。

##### 設計方針（Step 0にて確定済み。RESの「2. アーキテクチャ設計」にそのまま反映すること）

**1. `shapes/Line.js` の責務拡張**
*   コミット時に一意な `id` を付与できるようにする（採番は`VectorModel`側の責務とする）。
*   `hitTest(x, y, tolerance)`：線分本体への当たり判定（ホバー・選択判定用）を追加する。
*   `hitTestHandle(x, y, tolerance)`：`'start' | 'end' | 'move' | null` を返すハンドル当たり判定を追加する。`move`ハンドルは線分の中点に配置する。
*   `drawHandles(ctx)`：選択中に3種のハンドルを描画する。始点・終点ハンドルと、オブジェクト移動ハンドルは視覚的に区別できる描き分けにすること（具体的なデザインは本計画のスコープ外、暫定実装でよい）。
*   `drawHover(ctx)`：ホバー時の強調表示を描画する（暫定実装でよい。視覚仕様は別途Interruptで詰める）。
*   当たり判定・ハンドル描画のロジックは必ず`Line`自身に閉じ込め、`InputTracker` / `VectorModel` / `CanvasManager` 側に図形種別ごとのif/switch分岐を一切持ち込まないこと（将来の曲線・円・楕円の追加時に、既存コードを変更せず新規Shapeファイルの追加のみで対応できる拡張性を担保するため）。

**2. `core/VectorModel.js` の状態拡張**
*   既存の`#shapes`に加え、`#selectedId`（選択中図形のid）、`#hoveredId`（ホバー中図形のid）、`#draftLine`（作成中の未確定直線）を新設する。
*   `selectShape(id)` / `clearSelection()` / `getSelectedId()` を追加する。
*   `setHovered(id)` / `clearHovered()` / `getHoveredId()` を追加する。
*   `startDraft(x, y)`（始点確定・仮Line生成） / `updateDraft(x, y)`（終点をカーソルに追従） / `commitDraft()`（idを付与し`#shapes`へ確定・draft破棄） / `cancelDraft()`（将来のキャンセル操作用に用意するのみでよく、呼び出し元の実装は本計画のスコープ外）を追加する。
*   `updateVertex(id, vertexIndex, x, y)`：絶対座標による端点の更新。
*   `moveShape(id, dx, dy)`：相対差分による図形全体の平行移動。
*   上記すべての状態変更は、既存の`#notifyChange()`パターンに乗せ、「Model = 描画データと選択状態を保持する単一の真実（SSOT）」の原則を維持すること。

**3. `core/CanvasManager.js` の拡張**
*   `render(shapes, { hoveredId, selectedId, draftLine })` のようにシグネチャを拡張する。
*   通常描画（各`shape.draw(ctx)`）に加え、`hoveredId`に一致する図形は`drawHover(ctx)`を、`selectedId`に一致する図形は`drawHandles(ctx)`を追加で呼び出し、`draftLine`が存在する場合は最後に重ねて描画する。
*   `CanvasManager`自体は状態を一切持たず、渡された引数をそのまま描画するだけの純粋レンダラーの原則を崩さないこと。

**4. `core/InputTracker.js` への状態遷移マシン導入**
*   内部状態として `IDLE` / `DRAWING` / `DRAGGING_HANDLE` の3状態を持たせる。
*   **IDLE**：`mousemove`で常時ホバー判定を行い`model.setHovered` / `clearHovered`を呼ぶ。空白部分のクリックで`model.startDraft(x, y)`を呼び`DRAWING`へ遷移する。ホバー中の図形のクリックで`model.selectShape(id)`を呼ぶ。選択中図形のハンドル上での`mousedown`で、掴んだハンドル種別（start/end/move）を記憶した上で`DRAGGING_HANDLE`へ遷移する。選択中に空白部分をクリックした場合は`model.clearSelection()`を呼ぶ。
*   **DRAWING**：`mousemove`で`model.updateDraft(x, y)`を呼ぶ。クリックで`model.commitDraft()`を呼び`IDLE`へ戻る。
*   **DRAGGING_HANDLE**：`mousemove`時、start/endハンドルの場合は現在の論理座標をそのまま`updateVertex`へ渡し、moveハンドルの場合は直前のカーソル位置との差分(dx, dy)を`moveShape`へ渡す（ドラッグ中は直前のカーソル座標をInputTracker内に一時保持すること）。`mouseup`で`IDLE`へ戻る。
*   座標変換は既存の`getLogicalCoordinate`メソッドをそのまま流用すること（DPI対応・CSSズーム吸収のロジックに手を加える必要はない）。

##### スコープ外（本計画に絶対に含めないこと）
*   パレット・ツール切り替えUI（P1-3で対応）
*   LINE以外の図形（曲線・矩形・円・楕円、P1-4/P1-5で対応）
*   ホバー強調表示・3種ハンドルの具体的な視覚デザインの作り込み（暫定実装で可。デザイン確定は別途Interruptで対応予定）
*   Escapeキー等による作成中断・キャンセルのイベント実装（`cancelDraft`メソッドの用意のみでよい）
*   複数選択（マルチセレクト）

#### 【計画立案時の絶対遵守ルール (Constraints)】
*  **MVCの厳守（防衛線の維持）**：`VectorModel`を唯一のSSOTとし、「Model ➡️ 変更通知 ➡️ CanvasManager再描画」というPull型の関係を100%維持すること。`InputTracker`から`CanvasManager`を直接呼び出す設計にしないこと。
*  **図形種別分岐の排除**：当たり判定・ハンドル描画・ホバー描画など図形固有のロジックは、すべて`Line.js`側に閉じ込めること。`VectorModel` / `CanvasManager` / `InputTracker`のいずれにも、図形種別を判定するif/switch分岐を書かないこと。将来の曲線・円・楕円の追加時に、既存の`core/`配下のファイルを変更せず新規Shapeファイルの追加のみで対応できることを、設計の妥当性の判断基準とすること。
*  **既存座標変換ロジックの保護**：`InputTracker.getLogicalCoordinate`のDPI対応・CSSズーム吸収ロジックを壊さないこと。
