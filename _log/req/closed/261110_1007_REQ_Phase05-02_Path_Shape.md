### 要件1: パスの図形データの形（発注者の決定）
* 図形データは次の形とする（キー順もこの順）。図形データの共通の形`{ type, id, points, strokeColor, strokeWidth }`に`closed`と`segments`を足したもの。
  ```
  { type: 'path', id, points: [{ x, y }, ...], closed: <真偽値>, segments: [{ kind: 'line' }, ...], strokeColor, strokeWidth }
  ```
  * `points`：頂点の並び。始点から終点の順。
  * `closed`：閉じているか（`true`／`false`の真偽値のみ受理）。閉じたパスは終点から始点へも区間を持つ。
  * `segments`：区間の並び。`segments[i]`は`points[i]`から`points[i+1]`への区間、閉じたパスの最後の要素は`points[n-1]`から`points[0]`への区間。要素数は、開いたパスなら`points.length - 1`、閉じたパスなら`points.length`。
  * 区間の要素はオブジェクトで、区間の種類を`kind`に持つ。本サブフェイズで受理する種類は直線`'line'`のみ。曲線の区間はパスの編集のPhaseで、`kind`の値と区間の要素のキー（例：制御点）を足す形で拡張する（本作業では足さない。区間の要素の余分なキーは無視してよい）。
* 頂点数の下限：開いたパスは2点以上、閉じたパスは3点以上。上限は設けない。同じ座標の頂点が続く（長さ0の区間）ことは許す。
* `fromJSON`の検証：共通項目（オブジェクトか・`type`が`'path'`か・`points`・各頂点・`strokeColor`・`strokeWidth`）は`js/shapes/ShapeDataValidation.js`の`validateShapeData`で行い、パス固有の項目（`closed`が真偽値か・閉じたパスの頂点数・`segments`の配列と要素数・各要素がオブジェクトで`kind`が受理する種類か）は`Path`側で検証する。エラー文は`Path.fromJSON: <理由>`の形式とし、全文と検査の順序を計画書に記載すること。
* `validateShapeData`は現在、頂点数を固定の数（`pointCount`）でしか受け取れない（Phase 05-01からの持ち越し事項）。頂点数の下限（「2点以上」）を渡せるように引数を拡張する。拡張の形は計画時に決めて記載すること。**既存の4クラス（`Line`・`Curve`・`Rect`・`Ellipse`）の呼び出し方・エラー文・検査の順序は1文字も変えないこと**（既存の`test/shapes/`のエラー文のテストがそのまま通ること。4クラスのファイルを変更せずに済む形が望ましい）。
* 作業データの版（`version`）は上げない（DIRの決定。新しい図形の種類を足すだけで移行関数が要らないため）。古いエディタで開くとパスは未知の図形種別としてスキップされる（許容）。

### 要件2: `Path`クラス（13メソッド契約）
* `js/shapes/`に`Path.js`を新設し、13メソッド契約（`_doc/arch/12_shapes.md`）を自分で実装する。共通の基底クラス・継承は使わない。幾何の計算は`js/shapes/ShapeGeometry.js`の`distanceToSegment`・`segmentIntersectsRect`を使い、図形クラスへ複製しない。
* 各メソッドの振る舞い：
  * `draw`：`beginPath` → `moveTo(points[0])` → `lineTo(points[1]…points[n-1])` → 閉じていれば`closePath` → `strokeStyle` → `lineWidth` → `stroke()`。区間の種類による分岐の置き場所は計画時に決めてよいが、本作業で描けるのは直線の区間のみ。
  * `drawHandles`：全頂点に、既存の図形と同じ見た目（白塗り・青枠・画面上で一辺8pxの正方形）のハンドルを描く。
  * `drawHover`：`draw`と同じ形に、既存の図形と同じ強調（半透明の太線）を重ねる。
  * `hitTest`：すべての区間（閉じたパスは終点→始点の区間を含む）について点と線分の距離を求め、いずれかが許容誤差以内なら当たり。`strokeWidth`は許容誤差に足さない（`Line`・`Rect`と同じ）。塗り内部は判定しない。
  * `intersectsRect`：すべての区間（同上）のいずれかが範囲選択の矩形に掛かれば`true`（境界を含む）。塗り内部だけを囲む場合は`false`。
  * `hitTestHandle`：頂点のハンドルを番号の小さい順に調べ、先着1件のハンドル名を返す。`'move'`ハンドルは持たない（本体のドラッグで移動する）。ハンドル名の形は計画時に決めること（開発資料「ハンドル名の契約」：`getVertexIndexForHandle`で頂点の番号へ解決できること）。
  * `getVertexIndexForHandle`・`setVertex`：ハンドル名を頂点の番号へ解決し、その頂点を動かす。範囲外の番号・解決できない名前では何もしない（例外を投げない）。
  * `translate`：全頂点を平行移動する。
  * `updateDraftEnd`：本サブフェイズでは呼ばれない（パスは作成中の図形にならない）。契約を満たすため、終点（最後の頂点）を動かす実装とする。
  * `toDrawElement`：既存の描画要素`polyline`で表す（要件4）。
  * `toJSON`・`static fromJSON`：要件1の形。どちらの方向でも配列・頂点・区間の要素を共有しない（`data`内の配列・オブジェクトも流用しない）。`id`は検証せずそのまま保持する。余分なプロパティは無視する。往復で図形データの内容と描画・当たり判定の結果が一致する。
* コンストラクタの引数の形は計画時に決めてよい（`ShapeFactory.create`の始点・終点の4引数の形に合わせる必要はない。要件3）。

### 要件3: 読み込みの振り分けへの登録（図形パレット・数字キーには出さない）
* `ShapeFactory.fromJSON`が`type: 'path'`の図形データを`Path.fromJSON`へ振り分けるようにする。これにより、作業データファイルの「開く（ファイル）」「インポート」・`?dev`の復元・Undo/Redo・複製/コピー＆ペースト・書き出したスプライトJSの読み込みで、パスが復元される（これらはすべて`DocumentSerializer.deserialize` → `ShapeFactory.fromJSON`を通る）。
* **`SHAPE_TYPES`（図形パレットのボタン・数字キーの割り当て・作成できる図形種別の一覧）は変えない**（5種・現在の並びのまま）。パスは画面上で作る操作がないため、図形パレットにボタンを置かず、数字キーも割り当てず、`ShapeFactory.create`でも作れない（`'path'`を渡すと従来どおり未知の種別の`Error`）。現在の`SHAPE_REGISTRY`は「作れる種別」と「読める種別」を1つの表で兼ねているため、読めるが作れない種別をどう表すかを計画時に設計し、記載すること（`ShapeFactory`の「対応づけは表引きのみ・if/switch分岐を持たない」「種別一覧の正本は1箇所」の原則を保つこと。`InputTracker`・`KeyboardShortcuts`・`PaletteController`・`main.js`・`index.html`は変更しない）。

### 要件4: スプライトJSの書き出し（`formatVersion`は上げない）
* パスの`toDrawElement`は、書き出し形式の版1の`polyline`（`{ kind: 'polyline', id, points, closed, strokeColor, strokeWidth }`、頂点数の制限なし）を返す。区間の種類は描画要素に出さない（本作業の区間はすべて直線のため、`polyline`の`moveTo`→`lineTo`→（閉じていれば）`closePath`と同じ形になる）。
* これにより、書き出したJSの描画処理（`js/io/CodeExporter.js`の`DRAW_SOURCE`）・外枠の計算（`js/io/SpriteSerializer.js`）は変更せずに済み、書き出し形式の版（`formatVersion`）も上げない見込みである。計画時に実コードで、パスの`draw`と`DRAW_SOURCE`の`polyline`の描画命令・引数・順序が一致すること、外枠の計算が`polyline`の全頂点で正しく求まることを確かめ、計画書に記載すること。**もし`io/`の変更または`formatVersion`の版上げが必要と判断した場合は、計画を進めずに理由を計画書の懸念事項に書いて報告すること**（エンジンとの約束(c)により連絡票が要るため、設計指針の変更提案に当たる）。
* 曲線の区間を足すとき（パスの編集のPhase）に`polyline`で表せなくなること（新しい`kind`と版の判断が要ること）を、計画書の懸念事項に記録すること。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
