## 【実装要件】
現状、キャンバスはブラウザ内にのみ保存され、ファイルとして持ち出す・取り込むことができない。本作業では、開いているキャンバスの書き出し、ファイルを新しいキャンバスとして開く操作、ファイルの図形を開いているキャンバスへ追加するインポートを、キャンバスパレットに追加する。あわせて、一般利用者向けの読み込み失敗の通知を整える。

**用語の定義（本REQ・RES・コード内JSDocで統一すること）**
* **作業データファイル**: 作業データ形式のJSON文字列を内容とするファイル（既定の拡張子`.json`）。
* **書き出し**: 開いているキャンバスの図形一式を作業データファイルとしてダウンロードすること。
* **開く（ファイル）**: 作業データファイルの内容を、キャンバス一覧へ新しいキャンバスとして登録し、開いているキャンバスと入れ替えること。一覧の行を押して開く操作（`CanvasLibrary.openCanvas`）とは区別する。
* **インポート**: 作業データファイルの図形を、開いているキャンバスへ追加すること。
* キャンバス・キャンバス一覧・キャンバス記録・自動保存・キャンバスパレット・切り替え処理の定義はPhase 03-04（REQ `261104_0046`・RES `261104_0049`）、編集操作・履歴の定義はPhase 03-02（REQ `261103_1904`）、作業データ形式・シリアライズ／デシリアライズの定義はPhase 03-01（REQ `261101_2257`）、貼り付けの共通処理（`ShapeInserter`）の定義はPhase 03-03（REQ `261103_2355`）、選択集合・作成中の図形の定義はPhase 02-03（REQ `261018_0212`）、操作モードの定義はPhase 02-01に従う。

### 要件1: 書き出し（発注者決定、2026-11-06：拡張子`.json`、ファイル名＝キャンバス名）
* キャンバスパレットの操作で、開いているキャンバスを作業データファイルとしてダウンロードする。ファイルの内容は`DocumentSerializer.serializeToString(model.getShapes())`の結果とする（作業データ形式は変更しない。確定済みの図形のみを含み、作成途中の図形は含まない）。
* ファイル名は`<キャンバス名>.json`とする。キャンバス名のうちファイル名に使えない文字（`\ / : * ? " < > |`と制御文字）は`_`へ置換し、前後の空白と末尾のピリオドを除く。結果が空になる場合の既定の名前を計画時に決めて記載すること。
* 図形が0個のキャンバスも書き出せる（書き出したファイルは「開く」で空のキャンバスとして開ける）。
* 書き出しは図形一式・選択集合・履歴・ビュー変換・操作モード・作成途中の図形を変えず、自動保存の契機にもならない（編集操作ではない）。
* サーバー側の処理を必要とせず、`Blob`とダウンロード用のリンク等でブラウザ内で完結させる（生成したオブジェクトURLの解放を行うこと）。
* 書き出しに失敗した場合はアプリを停止させず、要件5の通知で分かるようにする。

### 要件2: 開く（ファイル）
* キャンバスパレットの操作でファイル選択の小窓（`input type="file"`。`.json`で絞り込むが、利用者は他のファイルも選べる）を出し、選んだファイルを読み込む。キャンセルした場合は何も起きない。同じファイルを続けて選んでも毎回処理されること（`input`の値のリセット等）。
* 読み込めた場合、新しいキャンバスとしてキャンバス一覧へ登録し、開いているキャンバスと入れ替える。`CanvasLibrary`の切り替え処理（手順1〜6。進行中の入力操作の中断・選択モードへの切り替え・切り替え前のキャンバスの保存の確定・図形一式の入れ替え・履歴のリセット・ビュー変換の初期化・最後に開いていたキャンバスの記録）を再利用し、切り替え処理の順序の保証を別途書き直さないこと。切り替えそのものは編集操作として記録しない。
* キャンバス名（発注者決定、2026-11-06：ファイル名＝キャンバス名）は、ファイル名の末尾の`.json`（大文字小文字を問わない）を除き、名前の変更と同じ規則（前後の空白を除く・`CANVAS_NAME_MAX_LENGTH`で切り詰める）を適用したものとする。空になる場合は新規キャンバスの命名規則（「無題 n」）に従う。既存のキャンバスと名前が重なっても連番を付けない（名前の重複を許すPhase 03-04の仕様どおり）。
* 新しいキャンバス記録の作業データは、読み込めた図形を現行版で`serialize`したものとする（旧版のファイルも現行版で記録される。読み込めなかった図形は記録に含まれない）。
* 切り替え前のキャンバスの保存に失敗した場合は、新規作成と同じく切り替えを中止し、開いているキャンバスに留まる（キャンバス一覧へ登録しない。Phase 03-04の方針）。新しい記録の書き込みに失敗した場合の扱いも新規作成と同じとする（中止せず`'writeFailed'`として開く）。
* `CanvasLibrary`の受理条件（読み込み中・処理中・`'unavailable'`では受け付けない）に従う。パレットの「開く」の押せる/押せない状態は新規作成と同じとする。

### 要件3: インポート（発注者決定、2026-11-06：元の座標のまま）
* キャンバスパレットの操作でファイル選択の小窓を出し、選んだファイルの図形を開いているキャンバスの最前面へ追加する。既存の図形はそのまま残る。**配置はファイル内の座標のまま**とする（`ShapeInserter.insertDocument(documentData, 0, 0)`。ずらさない）。ビュー変換は変えない（追加した図形が画面外に入ることがあるが、仕様とする）。
* 追加した図形には新しいidを振り、追加した図形だけを選択状態にする。インポートは1件の編集操作として`Ctrl`+`Z`／`Ctrl`+`Y`・ボタンで取り消し・やり直しできる。自動保存の対象になる（既存の`historyManager.onChange`経路のまま）。これらは`ShapeInserter.insertDocument`の既存の働きであり、別途書き直さないこと。図形の追加に`VectorModel.addShape`を使わないこと。
* 図形を追加する直前に、進行中の入力操作の中断と選択モードへの切り替え（`applyMode`の経路）を行うこと（`ShapeInserter`は操作モードを知らない。選択集合は選択モード以外では常に空の不変条件を保つ）。
* **読み込みに失敗した場合、および追加できる図形が無い場合は、図形一式・選択集合・履歴・操作モード・作成途中の図形を一切変えないこと**（図形作成モードのまま、作成途中の図形も残る）。この判定のために`deserialize`を複数回通す場合はスキップの`console.warn`が重複する点に注意し、方式を計画時に決めて記載すること。
* ファイルの読み取りは非同期である。読み取りの間にキャンバスの切り替え等が行われても、利用者が意図しないキャンバスへ図形が追加されないこと、および切り替え処理と競合して状態が壊れないこと（読み取り中の扱いを計画時に決めて記載すること）。
* 操作の受理条件は要件4に従う。

### 要件4: 保存できない環境・処理中の扱い
* `'unavailable'`（ブラウザ内に保存できない状態）でも、**書き出しとインポートは使える**（保存できない環境で作業を持ち出す・持ち込む唯一の手段のため）。開く（ファイル）は要件2のとおり使えない。
* 読み込み中・処理中（`loading`・`busy`）は、書き出し・開く・インポートのいずれも押せない状態にする（切り替えの途中でキャンバス名と図形一式が食い違った内容を書き出さないため）。
* パレットのボタンの押せない状態は、既存の`disabled`属性（`.tool-btn:disabled`）で表す。

### 要件5: 読み込み失敗の通知（発注者決定、2026-11-06：パレット内の文言。`_doc/COWORK_STATUS.md` 2章P3【03-05へ】）
* 通知の表示先はキャンバスパレット内の文言とする（既存の`#canvas-notice`と同じ見た目。ブラウザ標準の小窓は使わない）。文言の対応表は既存の`ISSUE_MESSAGES`と同じく`CanvasPalette.js`に置く。ファイル名を含める場合は`textContent`のみで設定し、`innerHTML`を使わないこと。
* 判定と文言は次のとおりとする（文言の細部は計画時に調整してよい）。

| 場面 | 判定 | 動作 | 文言の例 |
| ---- | ---- | ---- | -------- |
| 壊れたファイル・本アプリの形式でないファイル・対応していない版（新しすぎる版を含む）・読み取り失敗 | `deserialize`が`ok: false`、JSONとして解析できない、ファイルを読み取れない | 開く・インポートとも何も変えない | 「<ファイル名> を読み込めませんでした。本アプリの作業データファイルか確認してください。」 |
| 図形がすべて読めない | `ok: true`で、ファイルの`shapes`が1個以上あるのに読めた図形が0個 | 開く・インポートとも何も変えない（新しいキャンバスを作らない） | 上と同じ |
| 一部の図形が読めない | `ok: true`で読めた図形が1個以上、`skipped`が1件以上 | 読めた図形で開く／追加する | 「<ファイル名> の一部の図形（n個）を読み込めませんでした。」 |
| 図形が0個の正しいファイル（開く） | `ok: true`で`shapes`が空 | 空のキャンバスとして開く（通知なし） | なし |
| 図形が0個の正しいファイル（インポート） | 同上 | 何も変えない | 「<ファイル名> に追加できる図形がありませんでした。」 |
| 書き出しの失敗 | ダウンロードの準備で例外 | 何も変えない | 「書き出しに失敗しました。」 |

* `DocumentSerializer.deserialize`の「全図形スキップでも`ok: true`」の仕様（C-6）は変更せず、上の判定は呼び出し側で行う。スキップ1件ごとの`console.warn`（C-34）は開発者向けとしてそのまま残す。`DocumentSerializer`の`error`の文字列（開発者向け）は利用者向けの文言に出さない（`version: "1"`の見分けにくさ（C-32）は通知に現れなくなるため、対応不要として扱う）。
* **ファイル操作の通知が、保存の問題の表示を隠したり、隠されたりしないこと。** `CanvasLibrary.#setIssue`は`'unavailable'`を上書きしないため、`issue`へ単純に種類を足すと`'unavailable'`の状態でインポートに失敗しても通知が出ない。また`'writeFailed'`（次の自動保存の成功で解除）・`'partialLoad'`（編集で保存から失われる旨の予告）の解除条件とファイル操作の通知の解除条件は異なる。ファイル操作の通知の持ち方（`issue`とは別の状態にする等）と、両方ある場合の表示方法を計画時に決めて記載すること。
* ファイル操作の通知は、次のファイル操作の開始時またはキャンバスの切り替えの成功時に消える。成功時（書き出し・開く・インポートが問題なく完了）には通知を出さない。
* `'partialLoad'`の文言（「編集すると、その図形は保存から失われます」）は、ブラウザ内の記録を開いた場合の予告であり、開く（ファイル）には当てはまらない（ファイル側の記録には読めた図形しか入らず、元のファイルは手元に残るため）。開く（ファイル）で一部が読めない場合に`'partialLoad'`を立てないこと。
* `console.warn`のみの通知にしないこと。読み込み失敗でアプリを停止させないこと（例外を漏らさない）。

### 要件6: キャンバスパレットの操作の追加
* キャンバスパレット（`#window-canvas-palette`。DOMは`index.html`に静的に置く）へ「書き出し」「開く」「インポート」の3つのボタンを追加する（配置・アイコン・`title`の文言は計画時に決めてよい。何をする操作か分かる文言にすること）。ファイル選択の`input type="file"`は画面に出さず、ボタンから呼び出す。
* `CanvasPalette`はDOM操作を担うUI部品のまま、`CanvasLibrary`・`VectorModel`・図形データ・IndexedDBへ直接依存しないこと。操作の実行は注入コールバックへ委譲する（既存の`CanvasPaletteActions`の形を拡張する）。ファイルの中身の解釈・読み込みの判定をパレットに置かないこと。
* 押されたボタン・ファイル選択を閉じた後にフォーカスが残って`Enter`／`Space`で再度押されないこと（既存の`blur()`の扱いに揃える）。ファイル選択の小窓を閉じた後に、キーボードショートカット・スペースパン・修飾キーの状態が壊れないことを計画時に確認し、懸念があれば計画書に記載すること。`input type="file"`にフォーカスが残った場合の`isTextInputElement`の判定（テキスト入力扱いにならないこと）も確認すること。RES `261031_2121` 5章「将来テキスト入力欄を追加した際の確認項目」のうち該当するものを確認すること。
* パレットの行が増えてもコントロールパネル・図形パレットと重ならないこと（キャンバスパレットはコントロールパネルの左隣のため、図形パレットの`top`の調整は不要の見込み。計画時に確認すること）。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `CanvasManager`（描画層）に状態を持たせない、`VectorModel`・`InputTracker`・`DocumentSerializer`・`HistoryManager`・`CanvasLibrary`・`CanvasStorage`・本作業で新設する組み立てのクラスがDOMに触れない、UI部品（キャンバスパレット）が`VectorModel`・図形データ・IndexedDB・`CanvasLibrary`に直接依存しない、という責務分離を維持すること。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **図形種別分岐の局所化維持** : 図形種別による分岐・対応づけは`ShapeFactory.js`の対応表のみとし、ファイル入出力処理・キャンバス一覧の管理・キャンバスパレット・`main.js`に図形種別のif/switch分岐や図形固有のプロパティ名（`x1`・`points`・`startAngle`等）を持ち込まないこと。作業データは不透明なオブジェクトとして受け渡すこと（`shapes`配列の要素数の判定が必要な場合は、最上位の`shapes`のみを参照し、その要素の中身に触れないこと。判定の置き場所を計画時に決めて記載すること）。
*   **id形式の局所化維持** : 図形のid形式（`shape-<連番>`）の知識は`VectorModel.js`内に、キャンバスの識別子の形式は`CanvasLibrary.js`内に閉じること。
*   **履歴の扱い** : 書き出し・開く（ファイル）は編集操作として記録しないこと。インポートのみ`ShapeInserter`の経路で1件の編集操作として記録すること。`HistoryManager`の仕様変更を行わないこと。
*   **UI同期経路の一元化** : 再描画・削除ボタン・取り消し/やり直しボタンの同期は、既存の`model.onChange`経路と`historyManager.onChange`経路のみで行い、ファイル操作ごとに別の再描画・同期処理を書かないこと。
*   **グローバル変数の禁止** : `window`への公開を行わないこと。
*   **スコープの厳守** : 変更対象は`index.html`（キャンバスパレットの操作の追加・スタイル）、`js/main.js`（配線）、`js/palette/CanvasPalette.js`、`js/edit/CanvasLibrary.js`、新設のファイルの読み書きのファイル（候補は`js/io/`）、新設の組み立てのファイル（候補は`js/edit/`）とする（最終タスクの`PROJECT_ARCHITECTURE.md`・`_doc/arch/`の該当ファイルを除く）。`js/edit/ShapeInserter.js`は、要件3の「失敗時に何も変えない」を既存の`insertDocument`の組み合わせで満たせない場合に限り変更してよい（必要とする理由を計画書に記載。`ClipboardController`からの呼び出しの挙動を変えないこと）。それ以外のファイル（`CanvasManager.js`／`ShapeFactory.js`／`ViewTransform.js`／`DragTracker.js`／`InputTracker.js`／`KeyboardShortcuts.js`／`VectorModel.js`／`HistoryManager.js`／`WindowManager.js`／`DocumentSerializer.js`／`CanvasStorage.js`／`SnapshotAdapter.js`／`PaletteController.js`／`PaletteLauncher.js`／`DevPanel.js`／`ClipboardController.js`／`shapes/`の4ファイル）は変更しないこと。計画立案中にこれらの変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスク順序** : 新しいタスクは、その実行時点で存在しないファイル・メソッドを参照しないこと（例：ファイルの読み書きの新設 → `CanvasLibrary`の拡張 → 組み立てのクラスの新設 → キャンバスパレットの拡張と`index.html`の追加 → `main.js`の配線、の順）。各タスク完了時点でアプリが起動・動作する状態を保つ順序とすること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設ファイルを含む改修対象の全`.js`ファイルは、先頭行の単一責務JSDoc（3行以内）が改修後の実態と一致していることを確認し、必要なら更新すること。
