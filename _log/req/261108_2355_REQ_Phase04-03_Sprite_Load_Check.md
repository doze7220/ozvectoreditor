### 要件1: 確認用ページ（発注者決定：別のHTMLファイル）
* プロジェクトのルートに、`index.html`とは別のHTMLファイル**`sprite-check.html`**を置く。`index.html`と同じ開き方（同じフォルダのHTMLをブラウザで開く）で開ける。ビルドの手順・外部ライブラリを増やさない（憲法3章）。エディタ本体（`index.html`・`js/main.js`）の起動処理・画面には手を入れない（確認用ページへのリンクも置かない）。
* **画面の構成**：
  * ファイルを選ぶボタン（1回に1ファイル。`.js`・`.json`を選べる）。
  * 描画領域（Canvas）。**原点(0, 0)を描画領域の中央**に置き、**等倍**（スプライトの1pxを画面の1pxとして）で描く。拡大縮小・移動の操作は作らない。描画領域の大きさ（ウィンドウに合わせるか固定か）は計画時に決める。
  * 情報欄：選んだファイル名、書き出し形式の版（`formatVersion`）、作業データの版（`source.version`。無ければ無いと分かる表示）、描画要素の数、外枠の値（`minX`・`minY`・`maxX`・`maxY`と幅・高さ。`bounds`が`null`なら「外枠なし（図形0個）」）。
  * 注意書き：「選んだJSファイルはこのページで実行される。自分で出力したファイルだけを選ぶこと」が分かる短い文。
* **描くもの**：
  * スプライトの絵：**JSを選んだ場合は、選んだファイルを実際に`import`し、その既定のexportの`draw(ctx)`で描く**（ゲームが使うのと同じ経路で描けることを確かめるのが目的のため、ファイルを実行する。発注者了承済み）。ブラウザ内での`import`の方法（`Blob`のURLを使った動的`import`等）と、使い終わったURLの解放は計画時に決める。
  * **JSONを選んだ場合も同じように描く**。描き方は計画時に決めるが、**JSの`draw`と別の描画処理を新たに書き起こさない**こと（例：`CodeExporter`がJSへ埋め込む描画処理と同じものを使う。描画処理が2系統に分かれて食い違うことを防ぐため）。
  * 原点(0, 0)の印（十字など）と、外枠（`bounds`の値をそのまま使った矩形。確認用ページで外枠を計算し直さない）。スプライトの線と見分けがつく色・線種にする。重ね順は計画時に決める（スプライトの絵が印・外枠に隠れて確かめられなくならないこと）。
* **本アプリのスプライトかの判定**：
  * JSON：JSONとして解析でき、`format`が`"oz-vector-editor-sprite"`、`formatVersion`が1以上・現行版以下の整数であること。
  * JS：`import`でき、既定のexportがオブジェクトで、`format`・`formatVersion`が上と同じ条件を満たし、`draw`が関数であること。
  * 条件の定数（識別子・現行版）は既存の唯一の定義箇所（`SpriteSerializer.js`）を使い、確認用ページに重複して書かない（公開の方法は計画時に決める）。
* **読み込めなかった場合**（本アプリが書き出したものではないJS・JSON、作業データファイル、壊れたファイル、`import`中・`draw`中の例外、対応していない版）：ページは停止せず、前の表示を消して「読み込めませんでした」と理由の大まか（JSONとして読めない／本アプリのスプライトではない／対応していない版／読み込み・描画中にエラー、等。区分は計画時に決める）を表示する。続けて別のファイルを選び直せること。
* 確認用ページのJSの置き場所・ファイルの分け方は計画時に決める（`PROJECT_ARCHITECTURE.md` 1章のフォルダ構造・分割の方針に追加する）。確認用ページのJSはエディタの状態を持つモジュール（`core/`の`VectorModel`等、`edit/`、`palette/`）を`import`しない。DOMに依存しない判定部分は、可能なら自動テストできる形に分ける。

### 要件2: エディタの「開く」「インポート」でスプライトを開く（発注者決定：JSは実行しない）
* 「開く」「インポート」のファイル選択（`index.html`の`accept`）で、スプライトのJS（`.js`）も選べるようにする（作業データファイル`.ozve.json`・`.json`は引き続き選べること）。
* 選んだファイルの種類は**ファイルの中身で判定する**（拡張子に頼らない）：
  * 作業データ形式（`format: "oz-vector-editor"`）→ これまでどおり。
  * スプライトのJSON・JS（`format: "oz-vector-editor-sprite"`）→ 同梱の作業データ`source`を取り出し、**作業データファイルを開くときと同じ処理**（`DocumentSerializer.deserialize`。旧版からの変換を含む）へ渡す。`elements`・`bounds`は読み込みに使わない（図形は`source`だけから作る）。
* **エディタではJSを実行しない**（`import`・`eval`・`Function`等を使わない）。JSのテキストから、本アプリが書き出したJSの形（`CodeExporter.toModuleText`の出力。`const spriteData = <JSON>;`の部分）に従ってスプライトデータのJSONを文字として取り出し、`JSON.parse`する。取り出しの知識（JSの形）は、JSの形を組み立てている側と1箇所にまとめ、組み立てと取り出しが食い違わないようにすること（置き場所は計画時に決める）。改行コードが`CRLF`に変わったJS（ファイルのコピー・Gitの設定等で起こり得る）でも取り出せること。
* 受け付ける書き出し形式の版は、1以上・現行版以下の整数。`format`が違う・`source`が無い・版が範囲外・取り出しや解析に失敗、のいずれも**読み込み不可**（既存の通知`readFailed`。アプリは停止しない）として扱う。`source`を取り出せた後の判定（空・一部・全部、通知`partialRead`・`noShapes`）は、作業データファイルを読んだときの既存の判定の表（`CanvasFileOperations`のJSDoc）のまま。
* 「開く」で作るキャンバス名：末尾の`.js`も除く（`ship.js` → `ship`。`ship.json` → `ship`は既存のまま）。拡張子を除くのは1回だけで、作業データファイルの往復で名前が変わらない既存の性質（開発資料2章「ファイル名の規則」）を壊さないこと。
* スプライト形式の判別と`source`の取り出しは**DOMに依存しない`io/`の部分**に置き、自動テストできる形にする。`DocumentSerializer`にスプライト形式の知識を持ち込まない（`io/`内の依存は既存の`SpriteSerializer → DocumentSerializer`の向きを保ち、循環させない）。`CanvasFileOperations`が呼ぶ読み込みの入口をどう変えるか（読み込みの判定の表・通知の種類は増やさない）は計画時に決める。
* 「開く」「インポート」ボタンの`title`の文言を、スプライト（`.js`・`.json`）も選べることが分かるように直すかを計画時に判断する。
* これにより、Phase 04-02からの持ち越し2件（スプライトのJSONが`readFailed`になる／ファイル選択が`.json`のみ）を解消する。

### 要件3: 組み立て用のJSが動くことの自動テスト（発注者決定）
* P7のキャラ合成の形（組み立て用のJSが、パーツのJSを**ファイル名で**`import`し、原点(0, 0)を基準に位置をずらして描く）が、現在の書き出しの形のまま動くことを、`node --test`の自動テストで確かめる。画面（確認用ページ）では試さない。
* テストの内容：
  1. 2つの図形一式からパーツのJSのテキストを`CodeExporter.toModuleText`で組み立て、一時フォルダへ`body.js`・`head.js`として書く。
  2. 開発資料2章の例と同じ形の組み立て用のJS`_hero.js`（`import body from './body.js'`・`import head from './head.js'`、`ctx.save()`→`ctx.translate(…)`→`head.draw(ctx)`→`ctx.restore()`）を、テストファイル内の固定のテキストとして同じ一時フォルダへ書く。
  3. `_hero.js`を実際のファイルのパスで`import`し、描画命令を記録する偽の`ctx`で`draw(ctx)`を呼ぶ。
  4. 記録が「`body`の描画命令 → `translate`を挟んで`head`の描画命令」の順になり、各パーツの描画命令がそれぞれを単体で`draw`したときと一致すること、2つのパーツが互いのデータで描かれない（名前が衝突しない）ことを確かめる。
* このテストに限り、`node:fs`・`node:os`・`node:path`・`node:url`を使ってよい（一時フォルダはOSの一時フォルダの中に作り、テストの終了時に必ず削除する。`test/`の中にテスト以外の`.js`を作らない規則は守る）。開発資料4章`test/`（`_doc/arch/16_test.md`）の「`node:test`・`node:assert/strict`のみ使う」の記述に、この例外を追記する。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 依存方向`main.js → edit → io → core → shapes`を守ること。`palette/`はスプライトデータ・作業データの中身を知らない。`DocumentSerializer`はスプライト形式を知らない（作業データの版の移行の知識は`DocumentSerializer`に閉じたまま）。確認用ページのJSは、エディタの状態を持つモジュール（`core/`の状態・`edit/`・`palette/`）を`import`しない。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **ビルドなしの維持（憲法3章）** : 確認用ページもエディタ本体と同じくHTMLファイルをブラウザで開くだけで動くこと。Node.jsはテストの実行にのみ使う。
*   **JSの実行の範囲** : 選んだJSを実行するのは確認用ページだけとし、エディタ本体（`index.html`）では実行しない（要件2）。
*   **単一の定義箇所** : スプライト形式の識別子・現行版・JSの形（埋め込みと取り出し）・ファイル名の拡張子の規則は、それぞれ1箇所で定義すること。確認用ページで描画処理を書き起こさないこと（要件1）。
*   **スコープの明示** : 変更対象のファイル（新設を含む）を計画書に列挙すること。想定は`sprite-check.html`（新設）と確認用ページのJS（新設）、`js/io/`（既存・新設）、`js/edit/CanvasFileOperations.js`、`index.html`（`accept`・`title`のみ）、`js/palette/CanvasPalette.js`（文言を直す場合のみ）、`test/`（新設・既存）、および最終タスクの開発資料。`js/main.js`・`js/core/`・`js/shapes/`を変更する計画にする場合は、その理由を明記すること。
*   **タスクの粒度** : 変更単位は極力ファイル単位とし、DOMに依存しない判別・取り出しとそのテスト → エディタの読み込みの入口とファイル選択 → 組み立て用のJSのテスト → 確認用ページ → 開発資料の反映、のように、各タスクの完了時点で`node --test`が全件成功し、エディタが動く状態を保つ順序とすること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設の全`.js`ファイルの先頭行に、単一責務のJSDoc（3行以内）を記載すること。既存ファイルに機能を足す場合は、先頭の責務定義を逸脱しないこと（逸脱する場合は別ファイルに分けるか、責務定義の変更として計画書に明記する）。
