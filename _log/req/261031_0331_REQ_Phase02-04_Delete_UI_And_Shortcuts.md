## 【実装要件】
現状、図形の削除は選択モードでの`Delete`/`Backspace`キーでのみ可能でUI上に手段がなく、発見しにくい。また操作モード・図形種別の切り替え、倍率リセットはマウスでのボタン操作のみである。本作業では、コントロールパネルへの削除ボタンの追加、主要操作のキーボードショートカットの導入、テキスト入力中のキー誤作動防止の判定を実装する。

**用語の定義（本REQ・RES・コード内JSDocで統一すること）**
* **ショートカット**: 本作業で導入する、キー押下による操作（操作モード切替・図形種別切替・ビュー操作・`Esc`・全選択・削除）。スペースパン（Phase 02-02）はショートカットに含めず、既存の扱いを維持する。
* **テキスト入力中**: `document.activeElement`が、文字入力を受け付ける要素である状態（判定は要件4）。
* **ドラッグ中**: `InputTracker`が所有する`DragTracker`のセッション中（パン・左ドラッグ。閾値以前を含む）。
* 選択集合・範囲選択・本体ドラッグの定義はPhase 02-03（REQ `261018_0212`）、ワールド座標・スクリーン座標・ビュー変換の定義はPhase 02-02（REQ `261008_2031`）に従う。

### 要件1: 削除ボタン（コントロールパネル）
* コントロールパネル（`#window-control-panel`）の`.window-body`内に、選択集合の全図形を削除するボタン（表記例：「🗑 削除」）を1つ追加する。配置はモードボタン群と倍率行の間を推奨する（計画時に決めてよい）。モードボタンではないため、`main.js`の`modeButtons`には含めないこと（`.active`の対象外）。
* **押せる/押せない状態**: 選択集合が空のときは押せない状態とする。HTMLの`disabled`属性で表現し、見た目でも押せないことが分かるようにする（`.tool-btn`に`:disabled`のスタイルを追加してよい）。フロートウィンドウ用の`.disabled`クラス（`pointer-events: none`をウィンドウ全体に掛ける）は流用しないこと。
* **同期経路**: 押せる/押せない状態は、`model.onChange`へ登録した同期関数で`model.getSelectedIds()`が空かどうかから決めること（倍率表示の`syncZoomDisplay`と同じ考え方。DOM更新は`main.js`が担い、`VectorModel`・`InputTracker`はDOMに触れない）。起動時にも明示的に1回同期すること（通知の有無に依存しない）。
* **削除処理の経路の一本化**: ボタン押下と`Delete`/`Backspace`キーは、**同一の削除処理**（例：`InputTracker`の公開メソッド`deleteSelection()`）を呼ぶこと。受理条件（選択モード・`IDLE`状態・ドラッグ中でない・選択集合が空でない）はその1箇所で判定し、ボタン側・キー側で重複して書かないこと。削除は`VectorModel.deleteShapes(ids)`（変更通知1回）で行う。`main.js`から`model.deleteShapes`を直接呼ばないこと。
* 選択集合は操作モード切替時にクリアされるため、図形作成・キャンバス移動モード中は常に押せない状態になる（追加の分岐は不要。この前提を計画書に記載すること）。

### 要件2: キーボードショートカット
以下のキー割り当てとする（発注者決定、2026-10-31。Illustrator風の割り当てを基本とし、Illustratorに定番キーのない図形種別は数字キーとする）。

| キー | 操作 | 備考 |
| --- | --- | --- |
| `V` | 選択モードへ切替 | |
| `P` | 図形作成モードへ切替 | 図形種別は現在記憶しているもの |
| `H` | キャンバス移動モードへ切替 | |
| `1`〜`5` | 図形種別を 直線／曲線／弧／矩形／円 に切替 | パレットの並び順。**図形作成モード以外では図形作成モードへも切り替える** |
| `Ctrl`+`0` | ビュー変換のリセット（倍率100%・初期表示位置） | リセットボタンと同じ処理 |
| `Ctrl`+`=`（`+`） | 拡大 | 表示中キャンバスの中心を基準とする |
| `Ctrl`+`-` | 縮小 | 同上 |
| `Esc` | 作成途中の図形の破棄／選択解除 | 詳細は下記 |
| `Ctrl`+`A` | 全図形を選択 | 詳細は下記 |
| `Delete`/`Backspace` | 選択集合の全図形を削除 | 既存。要件1の削除処理へ一本化 |

* **macOS対応**: `Ctrl`を用いる操作は、`Meta`（⌘）でも同じく動作させること。
* **修飾キーの扱い**: 修飾キーなしの操作（`V`/`P`/`H`/`1`〜`5`/`Esc`/`Delete`/`Backspace`）は、`Ctrl`・`Meta`・`Alt`のいずれかが押されている場合は反応しないこと（ブラウザ・OSのショートカットを奪わないため）。`Shift`の扱いは計画時に決めてよい（`Shift`+`V`等で反応させるか）が、決めた規則を計画書とJSDocに記載すること。
* **キーの識別**: 英字・数字キーは、IMEの状態・大文字小文字・キーボード配列の影響を受けにくい方法（`event.code`の`KeyV`/`Digit1`等）で識別することを推奨する。採用した識別方法と理由を計画書に記載すること。テンキーの`1`〜`5`を受け付けるかは計画時に決めてよい。
* **日本語（JIS）キーボードへの配慮**: 発注者の環境はJISキーボードを想定する。JIS配列では`+`は`Shift`+`;`の位置にあるため、拡大は`Ctrl`+`=`（US配列）・`Ctrl`+`;`／`Ctrl`+`Shift`+`;`（JIS配列の`+`キー）・テンキーの`+`のいずれでも動作すること。縮小は`Ctrl`+`-`・テンキーの`-`で動作すること。`Ctrl`+`0`はテンキーの`0`でも動作してよい。
* **ブラウザ動作の抑止**: 受理したショートカットは`preventDefault()`し、ブラウザ標準動作（`Ctrl`+`0`/`=`/`-`のブラウザズーム、`Ctrl`+`A`のページ全選択、`Backspace`の戻る等）を起こさないこと。**受理しなかったキーは`preventDefault()`しないこと**（テキスト入力中・ドラッグ中で無視した場合を含む）。
* **キーリピート**: 押しっぱなしによるキーリピート（`event.repeat`）は、拡大・縮小のみ受け付け、それ以外のショートカットは無視することを推奨する（計画時に決めてよい）。
* **操作モード・図形種別の切替**: ボタン押下と同じ結果になること。すなわち、`main.js`の`applyMode(mode)`／`applyShapeType(type)`と同一の経路を通り、コントロールパネルのボタンの`.active`、図形パレットの活性/非活性・ハイライトがボタン操作時と同じく同期されること。数字キーで図形作成モードへ自動で切り替える場合も同様（モード切替→種別切替の両方の表示同期が行われること）。作成途中の図形がある場合の扱い（破棄される）もボタン操作と同じでよい。
* **拡大・縮小**: 倍率の変化量はホイール1刻みと同じ（`WHEEL_ZOOM_STEP`）とする。ズーム中心は表示中キャンバスの中心（スクリーン座標）とし、`ViewTransform.zoomAt(sx, sy, factor)`へ委譲すること（変換式・クランプを新たに書かないこと）。刻み幅の定数を2箇所に重複定義しないこと（共有の方法は計画時に決めてよい）。
* **リセット**: リセットボタンと同じく`viewTransform.reset()`を呼ぶのみ。操作モード・選択集合には触れない。
* **`Esc`**:
  * 図形作成モードで作成途中の図形がある（`DRAWING`状態）場合は、その図形を破棄して`IDLE`へ戻す（`model.cancelDraft()`）。
  * 選択モードで選択集合が空でない場合は、選択をすべて解除する。
  * 上記以外では何もしない（`preventDefault()`もしない）。
* **`Ctrl`+`A`**: 全図形を選択集合とする（`VectorModel.setSelection(ids)`で1回の変更通知）。選択モード以外では、まず選択モードへ切り替え（`applyMode`と同一経路でUI同期）、その後に全選択すること。図形が0個の場合も`preventDefault()`し、ページの全選択を起こさないこと。
* **ドラッグ中の扱い**: ドラッグ中（パン・左ドラッグ。閾値以前を含む）は、`Delete`/`Backspace`と同様に**すべてのショートカットを受け付けない**こと（現行の「ドラッグ中は削除を受け付けない」方針に揃える。ドラッグ途中のモード切替による状態の不整合を避けるため）。スペースパンの`Space`キーの扱いは変更しない。
* **ボタンへのキー表示**: 発見しやすさのため、コントロールパネルのモードボタン・削除ボタン・リセットボタン、図形パレットの5ボタンに、対応するキーを示す`title`属性（ツールチップ。例：`選択 (V)`、`直線 (1)`）を`index.html`で付与すること。ボタンの表示文字列は変更しなくてよい（変更する場合はレイアウト崩れがないこと）。

### 要件3: ショートカットの責務配置
* `InputTracker.js`はPhase 02-03完了時点で約960行に肥大化している（`_doc/COWORK_STATUS.md` 2章）。ショートカットのキー解釈（キー→操作の対応表と受理判定）は、**`InputTracker`に追加せず、`js/core/`配下の新設クラス**（名称例：`KeyboardShortcuts.js`）へ置くことを第一候補とする。`InputTracker`に置く場合は、その理由を計画書に記載すること。
* 新設クラスは**キー→操作の対応づけと受理判定のみ**を責務とし、操作の実体（モード切替・種別切替・ビュー変換・削除・選択）は`main.js`から注入されたコールバック、または`InputTracker`の公開メソッドを呼んで実行すること。新設クラスが`VectorModel`・`ViewTransform`・DOMのボタン要素を直接操作して、`applyMode`等のUI同期経路を迂回してはならない。
* `InputTracker`は`main.js`の`applyMode`/`applyShapeType`を呼ばないこと（依存方向は`main.js`→`InputTracker`のまま維持する）。`InputTracker`に追加する公開メソッドは、`InputTracker`の状態（`InputState`・ドラッグ中か・作成途中の図形）に依存する操作（例：`deleteSelection()`、`Esc`の処理、ドラッグ中かの問い合わせ）に限ること。
* **キーの二重解釈の禁止**: `keydown`は現在`InputTracker`が`document`へ購読している。新設クラスも`document`の`keydown`を購読する場合、同一キーを両者が解釈しないよう、担当するキーを排他的に分けること（例：`Space`は`InputTracker`、それ以外のショートカットは新設クラス）。`Delete`/`Backspace`の処理を新設クラスへ移す場合は、`InputTracker.handleKeyDown`側から確実に取り除くこと。最終的な担当分けを計画書に表で記載すること。
* 対応表（キー→操作）は1箇所で定義し、新しいショートカットの追加が対応表へのエントリ追加で済む構造を推奨する（`modeButtons`と同様の考え方）。キー識別・修飾キー判定のif分岐を操作ごとに重複させないこと。

### 要件4: テキスト入力中の誤作動防止
* テキスト入力中は、**すべてのショートカット（`Delete`/`Backspace`を含む）とスペースパン**が動作せず、`preventDefault()`もしないこと（文字入力・カーソル移動・文字削除を妨げない）。
* 判定は、Phase 02-02で用意した`InputTracker.js`のexport関数`isTextInputElement(element)`を再利用すること（判定ロジックを複製しないこと）。新設クラスから利用する場合のimport元・配置（`InputTracker.js`に置いたままか、共有の配置へ移すか）は計画時に決めてよいが、移す場合は全参照元を同一タスク内で追従させること。
* **`input`要素の`type`別の扱いの再検討**: 現状は`input`要素を`type`を問わずテキスト入力扱いとする保守的判定である。本作業で、文字入力を受け付ける`type`（`type`属性なし・`text`・`search`・`email`・`url`・`tel`・`password`・`number`等）のみをテキスト入力とし、`checkbox`・`radio`・`range`・`color`・`button`・`submit`・`reset`・`file`等はテキスト入力としない判定へ変更することを推奨する（着色Phaseで`color`・`range`・`checkbox`を置いた際に、フォーカス後にショートカットが効かなくなることを避けるため）。採否と、テキスト入力扱いとする`type`の一覧を計画書とJSDocに記載すること。`select`要素・`textarea`・`contenteditable`の扱いは現行どおりでよい。
* `index.html`には現時点でテキスト入力欄が存在しないため、本作業では**確認用の入力欄を置かない**（発注者決定、2026-10-31）。判定の確認は、将来の入力欄追加時に行う。計画書の「懸念事項・要確認ポイント」欄に、入力欄追加時に確認すべき項目（入力中に`V`・数字・`Space`・`Delete`・`Backspace`・`Ctrl`+`A`が文字入力として働くこと等）を列挙しておくこと。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : `CanvasManager`（描画層）に状態を持たせない、`VectorModel`・`ViewTransform`・`InputTracker`がDOM（ボタン要素）に触れない、という既存の責務分離を維持すること。外部フレームワークを導入しない Vanilla JS の原則を維持すること。
*   **UI同期経路の一元化** : 操作モード・図形種別の切替は`main.js`の`applyMode`/`applyShapeType`、ビュー変換の表示同期は`viewTransform.onChange`、選択集合に依存する表示（削除ボタンの状態）は`model.onChange`を唯一の経路とし、ショートカット用に別のUI同期処理を書かないこと。再描画は`renderCurrentState()`のみで行い、再描画トリガーの重複定義を作らないこと。
*   **座標系の分離** : キーボードズームの中心はスクリーン座標で求め、`ViewTransform.zoomAt`へ委譲すること。スクリーン⇔ワールドの変換式を新たに書かないこと。
*   **図形種別分岐の局所化維持** : 数字キーと図形種別の対応は対応表のデータとして持ち、図形種別ごとのif/switch分岐を新たに持ち込まないこと。図形種別の文字列は既存の`SHAPE_TYPES`（`InputTracker.js`）の値と一致させること（図形種別一覧の多重管理は`_doc/COWORK_STATUS.md`記載の既知の課題であり、本作業で管理箇所をさらに増やす場合はその旨を懸念事項に記載すること）。
*   **UI部品の疎結合維持** : `PaletteController`・`WindowManager`は本作業で変更しないこと。
*   **スコープの厳守** : 変更対象は`index.html`（削除ボタン・`:disabled`スタイル・`title`属性）、`js/main.js`、`js/core/InputTracker.js`、および要件3で採用した場合の新設クラス（`js/core/`配下）とする（最終タスクの`PROJECT_ARCHITECTURE.md`を除く）。それ以外のファイル（`VectorModel.js`／`CanvasManager.js`／`ViewTransform.js`／`DragTracker.js`／`ShapeFactory.js`／`WindowManager.js`／`PaletteController.js`／`js/shapes/`配下）は変更しないこと。計画立案中にこれらの変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスク順序** : 新しいタスクは、その実行時点で存在しないファイル・メソッドを参照しないこと（例：`InputTracker`の公開メソッド（削除処理等）の追加を、それを呼ぶ削除ボタン・新設クラスの配線より先に置く）。各タスク完了時点でアプリが起動・動作する状態を保つ順序とすること（特に、`Delete`/`Backspace`の処理を`InputTracker.handleKeyDown`から新設クラスへ移す場合、削除キーが一時的に効かない、または二重に処理される中間状態を作らないこと）。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設ファイルを含む改修対象の全`.js`ファイルは、先頭行の単一責務JSDoc（3行以内）が改修後の実態と一致していることを確認し、必要なら更新すること。
