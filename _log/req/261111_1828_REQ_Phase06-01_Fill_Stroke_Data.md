## 【実装要件】
図形データに塗り（`fillColor`）と「線なし」（`strokeColor: null`）を足し、エディタの描画・作業データの保存と読み込み・スプライトJSの書き出しを対応させる。**画面から色を変える操作は作らない**（Phase 06-02）。本サブフェイズで塗り・線なしの図形が現れるのは、作業データ（作業データファイル・`?dev`の「JSONから復元」・書き出したスプライトJSの`source`）から読み込んだときと、それらの図形を結合・描き足ししたときだけである。新しく描く図形は従来どおり線あり（`'#000000'`・2px）・塗りなし（`fillColor: null`）とする。

既存の選択・移動・ハンドル操作・削除・複製/コピー＆ペースト・Undo/Redo・自動保存は、作業データ（`toJSON`/`fromJSON`）を通る限り塗りも運ぶため、`core/`（`ShapeFactory`を除く）・`edit/`・`palette/`・`main.js`・`index.html`・`check/`は変更しない見込みである。変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄に理由を明記すること。

### 要件1: 図形データの形と検証（作業データの版2）
* **`fillColor`**：全図形（`line`・`curve`・`arc`・`rect`・`circle`・`path`）の図形データに足す。値は色の文字列、または`null`（塗りなし）。キーの位置は**`strokeWidth`の後（最後）**とする。
  * 例：`{ type: 'rect', id, points, strokeColor, strokeWidth, fillColor }`、`{ type: 'path', id, points, closed, segments, strokeColor, strokeWidth, fillColor }`
  * 塗れない形（要件2）の図形でも`fillColor`を消さずに保持する（DIR「塗りを保持して、塗れる形のときだけ描く」）。`toJSON`は保持している値をそのまま出力する。
* **`fromJSON`の検証の変更**（共通項目の検証`js/shapes/ShapeDataValidation.js`の`validateShapeData`、またはそこへ足す共通の関数で行い、図形クラスへ複製しない）：
  * `strokeColor`：文字列または`null`を受理する。それ以外（キーが無い・`undefined`・数値等）は従来どおり不正。エラー文は理由に`null`も受理することが分かる文面へ改めてよい（全文を計画書に記載）。
  * `strokeWidth`：**キーが無い（値が`undefined`）場合は線の太さ2pxとして読み込む**（DIRの持ち越し事項。これまでは不正としてスキップされていた）。値があって有限の数値でない・0以下（`null`・文字列・`NaN`・0・負の数）は従来どおり不正とし、エラー文も変えない。
  * `fillColor`：文字列または`null`を受理する。**キーが無い（値が`undefined`）場合は`null`（塗りなし）として読み込む**。それ以外（数値・真偽値・オブジェクト等）は不正。エラー文の全文を計画書に記載すること。
  * 検査の順序は、従来の順序（オブジェクトか → `type` → `points`の要素数 → 各頂点 → `strokeColor` → `strokeWidth`）の後に`fillColor`を足す。パス固有の項目（`closed`・`segments`）の検査の位置は変えない。
  * 2pxの既定値は`shapes/`の中で1箇所に定義すること（`shapes/`は`io/`をimportできないため、`io/SpriteSerializer.js`の`DEFAULT_STROKE_WIDTH`は使えない。2つの定義が同じ値であるべきことをJSDocに書く）。
* **作業データの版を2に上げる**（DIRの決定）：`js/io/DocumentSerializer.js`の`CURRENT_DOCUMENT_VERSION`を2にし、`MIGRATIONS`に版1→版2の関数を足す。
  * 版1→版2：新しい作業データを返し、`shapes`の各要素のうちプレーンオブジェクトであるものに`fillColor: null`を設定した新しいオブジェクトに置き換える（版1に`fillColor`の意味はないため、要素が`fillColor`を持っていても`null`にする）。プレーンオブジェクトでない要素はそのまま残す（後の図形単位の検証でスキップされる）。`shapes`が配列でない場合はそのまま返す（後の「`shapes`が配列ではありません」の全体失敗に任せる）。引数を書き換えない。
  * これにより、版1の作業データファイル（これまでのファイル）は、すべての図形が塗りなしとして読み込まれ、見た目はこれまでと変わらない。
  * 版2の作業データを古いエディタで開くと「対応していない版」として全体が断られる（DIRの決定どおり。許容）。

### 要件2: 塗れる形と描画（エディタ）
* **塗れる形**：矩形（`rect`）・円（`circle`）・閉じたパス（`path`で`closed: true`）の3つ。直線（`line`）・曲線（`curve`）・弧（`arc`）・開いたパスは塗れない。塗れるかどうかは形から決まる値であり、データに保存しない。
* 各図形クラスに「塗れる形か」を返す**公開メソッドを足し、図形クラスの共通メソッド契約に加える**（13メソッド → 14メソッド。全6種＝5クラスで自律実装する。名前は計画時に決めて記載すること）。Phase 06-02（塗りの欄を無効の表示にする）・06-03（内側の当たり判定）で外から使う予定のため。`draw`・`toDrawElement`もこのメソッドと同じ判定を使い、規則を二重に書かないこと。
* **`draw`の描き方**（全図形共通の順序。`DRAW_SOURCE`（要件4）と同じ命令・同じ順にする）：
  1. 塗るか＝「塗れる形」かつ「`fillColor`が文字列」。線を描くか＝「`strokeColor`が文字列」。
  2. どちらも偽なら、何も呼ばずに終わる（`beginPath`も呼ばない）。
  3. 形のパスを組み立てる（従来と同じ命令：`beginPath` → … → 閉じる形なら`closePath`）。
  4. 塗るなら`fillStyle = fillColor` → `fill()`（引数なし＝Canvasの標準のnonzeroの規則。自分自身と交差する閉じたパスもこの規則で塗る）。
  5. 線を描くなら`strokeStyle` → `lineWidth` → `stroke()`（従来と同じ）。
  * 塗り→線の順に描くため、線は塗りの上に重なる。
* `drawHandles`・`drawHover`は変えない（線なしの図形でもホバーの強調・ハンドルは従来どおり表示される）。`hitTest`・`intersectsRect`・`hitTestHandle`も変えない（塗った内側の当たり判定はPhase 06-03）。
* **線なしで塗れない形の図形**（線なしの直線等）は画面に何も描かれないが、本サブフェイズではデータとして受理する（スキップしない）。輪郭付近のクリック・範囲選択では従来どおり選べ、ホバーの強調・ハンドルも出る。画面上での扱いはPhase 06-02・06-03で決める。
* **コンストラクタ**：各図形クラスのコンストラクタに塗りの引数（既定値`null`）を足す。既存の引数の位置・既定値は変えない（`ShapeFactory.create`・既存のテストの呼び出しがそのまま動くこと）。`ShapeFactory`を変更する必要があるかは計画時に確かめ、必要ならJSDocの図形データの形の記述の更新に留めること。

### 要件3: 結合・描き足し・閉じるの塗り（`js/shapes/PathJoinRules.js`）
* 結果のパスの塗り（`fillColor`）は、線の色・太さと同じく**基準の線A（重なり順で奥）のもの**にする（DIRの決定）。描き足し・閉じる（1本を閉じたパスにする）は元の線のものを保つ。
* 開いたパスを結合で閉じると、そのパスが持っていた塗りが現れる（閉じたパスは塗れる形のため）。直線（`line`）には塗りの値が保持されていても塗られないが、結合の結果のパスにAの`fillColor`として引き継がれる。
* 結果を組み立てる箇所（`buildClosedPath`・`assembleOpenPath`等、`new Path(...)`を呼ぶすべての箇所）で漏れなく渡すこと。`edit/`（`PathJoiner`・`EndpointSnapper`）は変更しない見込み。

### 要件4: スプライトJSの書き出し（書き出し形式の版2）
* **書き出し形式の版を2に上げる**（DIRの決定）：`js/io/SpriteSerializer.js`の`SPRITE_FORMAT_VERSION`を2にする。`checkFormat`は1以上・現行版以下を受理するため、版1のJS（これまでに書き出したJS）もエディタで開け（`source`を使う）、確認用ページでも表示できる（確認用ページはそのJS自身の`draw`を呼ぶ）。
* **描画要素の塗り**：全`kind`（`polyline`・`quadratic`・`ellipse`）の描画要素に共通のキー`fillColor`を足す。キーの位置は**`strokeWidth`の後（最後）**。値は、**塗れる形なら図形の`fillColor`、塗れない形なら`null`**（描画要素は「描かれるもの」を表す。保持している値は`source`の作業データに残る）。`strokeColor`は`null`も含めそのまま入れる（従来どおり検証・補完しない）。
* **読む側の規則**に次を足す（書き出したJSの`draw`もこれに従う）：
  * `fillColor`が文字列で、かつ`kind`が`polyline`または`ellipse`で`closed`が`true`の要素だけを塗る。`quadratic`は塗らない。`closed`が`true`でない要素は塗らない（パスの開閉が後から増えても書き出し形式の版を上げずに済むため。DIRの決定）。`fillColor`が無い・文字列でない要素は塗らない。
  * 塗りは形のパスを組み立てた後、線より先に`fillStyle` → `fill()`（nonzero）。
  * 「`strokeColor`が文字列でない要素は線を描かない」は従来どおり線についての規則であり、塗りには影響しない。
  * 塗りも線も描かない要素は、パスも組み立てない（何も呼ばない）。形の項目が足りない要素・未知の`kind`の要素は、塗りも線も描かない（従来どおり描かない）。
* **`js/io/CodeExporter.js`の`DRAW_SOURCE`**を上の規則に合わせて書き直す（現在は`strokeColor`が文字列でなければ冒頭で`return`しているため、塗りだけの要素が描かれない）。図形の`draw`と命令・引数・順序が一致すること（DIRの持ち越し事項。`test/io/CodeExporter.test.js`の一致テストを通す）。`draw(ctx)`で明示する設定（`lineCap`等）に塗りの分は足さない（`fillStyle`は要素ごとに代入し、塗りの規則は`fill()`の引数で決まり`ctx`の状態ではないため）。
* **外枠（`bounds`）**：線を描かない要素（`strokeColor`が文字列でない）は、**線の太さの半分だけ広げない**（形の範囲のまま）。線を描く要素は従来どおり広げる。塗りは形の範囲の内側に収まるため外枠の求め方を変えない。線なしで塗れない要素も、従来どおり形の範囲を外枠に含める。
* エンジンは`draw(ctx)`を呼ぶだけなので変更は不要。連絡票はPhase 06-05で出す（本サブフェイズでは書かない）。

* `edit/`・`palette/`・`main.js`・`index.html`・`core/`（`ShapeFactory`を除く）・`check/`・`sprite-check.html`の変更。
* テストプレイ用の作業データファイルをリポジトリへ追加すること。

## 【計画書に必ず含めるべきタスクごとの作業】
AIが作成する計画書（RES）のタスクリストには、個別の実装タスクの後に、以下の作業を必ず含めること。
*   コード修正完了後、JSDocコメントの記載漏れがないことを確認する（変更したメソッド・関数・定数のJSDoc（`@param`・`@returns`・`@throws`）、クラスJSDocの共通メソッド契約の列挙（14メソッド）、図形データ・描画要素の形の記述）。
*   各タスクの完了時に、プロジェクトのルートで`node --test`を実行し、全テストが成功すること（および表示された件数）をRESに記録する。
*   タスク完了後、作業レポート（本RESファイル）の詳細作業内容を記載し完成させる。
*   開発資料（`PROJECT_ARCHITECTURE.md`）の記載に影響が出る場合は、資料本体は修正せず、その旨を『開発資料の更新予定』欄に追記する。
*   実装中に判断に迷った点、目視確認を推奨する箇所、将来この箇所を修正する際に注意すべき点があれば、RESの「懸念事項・要確認ポイント」欄に記述する。

## 【計画書に必ず含めるべき固定タスク】
AIが作成する計画書（RES）のタスクリストには、全実装タスクの後に、以下のタスクを必ず含めること。
*   各タスクで記録した『開発資料の更新予定』を確認し、開発資料（`PROJECT_ARCHITECTURE.md`）へ反映する。本作業では要件7により、`PROJECT_ARCHITECTURE.md`1章・2章と`_doc/arch/12_shapes.md`・`_doc/arch/15_io.md`・`_doc/arch/16_test.md`の更新は必須と想定してタスク化すること。
    *   ※ 実装AIによる開発資料の書き換えは、本ワークフローにおいて原則禁止であるが、**この最終タスクのみ明示的な例外とする**。後続タスクが存在せず、資料の変更によって他タスクの前提が動く危険がないためである。個別の実装タスク内で資料を書き換えてはならない。

## 【計画立案時の絶対遵守ルール (Constraints)】
*   **アーキテクチャの維持** : 各図形クラスが共通メソッド契約を自律実装し共通の基底クラスを持たない設計、依存方向（`main.js → edit → io → core → shapes`の一方向。`shapes/`は`core/`・`io/`をimportしない）、図形クラス・`ShapeFactory`が`try/catch`を持たないこと（捕捉は`DocumentSerializer`の1箇所）、旧版の知識を`DocumentSerializer`の`MIGRATIONS`に閉じること（図形クラスは常に現行版の図形データのみを扱う）、幾何・検証の共通の関数を図形クラスへ複製しないこと（開発資料`_doc/arch/12_shapes.md`）を維持すること。外部フレームワーク・ライブラリを導入しない Vanilla JS の原則を維持すること。
*   **既存の振る舞いの不変** : 塗りなし・線ありの図形（これまでの図形）の描画命令・当たり判定・作成・結合・描き足しの結果、図形パレット・数字キーの並びを変えないこと。既存のエラー文は、本REQで変更を指示したもの（`strokeColor`の`null`の受理に伴う文面）以外を変えないこと。
*   **スコープの厳守** : 変更対象は、`js/shapes/ShapeDataValidation.js`・`Line.js`・`Curve.js`・`Rect.js`・`Ellipse.js`・`Path.js`・`PathJoinRules.js`、`js/io/DocumentSerializer.js`・`SpriteSerializer.js`・`CodeExporter.js`、`js/core/ShapeFactory.js`（JSDocの更新が必要な場合のみ）、`test/shapes/`・`test/io/`の既存のテストファイル、`test/io/DocumentSerializer.migration.test.js`（新設する場合のみ）とする（最終タスクの`PROJECT_ARCHITECTURE.md`・`_doc/arch/`の該当ファイルを除く）。`test/core/`・`test/edit/`・`test/check/`の既存のテストが仕様の変更で失敗する場合に限り、そのケースの書き換えを対象に含めてよい（理由を計画書に明記）。それ以外の変更が不可避と判断した場合は、計画書の「懸念事項・要確認ポイント」欄にその理由を明記すること。
*   **タスクの粒度** : 1タスク＝原則1ファイル（ソースの新設・変更は1ファイル、テストは1テストファイル。ただしソースとそのソースを直接確かめるテストを同じタスクにまとめてよい）とし、各タスクの完了時点で`node --test`が全件成功する状態を保つ順序とすること（例：検証の共通関数 → 各図形クラスとそのテスト → 結合の規則 → 作業データの版2と移行 → 書き出しの版2・`DRAW_SOURCE`・外枠 → 往復・読み込みのテスト → 開発資料の反映）。図形クラスの`fillColor`の追加と`DRAW_SOURCE`の変更の間で一致テストが失敗しない順序・まとめ方を計画時に検討すること。
*   **責務定義の明記（`PROJECT_CONSTITUTION.md` 3章）** : 新設の全`.js`ファイルの先頭行に、単一責務のJSDoc（3行以内）を記載すること。既存ファイルの責務定義を逸脱するロジックを足さないこと。
