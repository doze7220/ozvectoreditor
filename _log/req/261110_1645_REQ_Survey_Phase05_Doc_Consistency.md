## 【作業手順（厳守事項）】
本プロンプトは、Phase 5「パスの基礎」の期間に書き換えられた開発資料（`./PROJECT_ARCHITECTURE.md` と `./_doc/arch/` 配下）の記述と、現在の実コードとの整合のSurveyである。
**本作業は調査のみを目的とする。いかなる理由があっても、ソースコードおよび資料ファイルの修正・作成を行ってはならない（RESファイルの出力を除く）。**

1. ルール（`PROJECT_CONSTITUTION.md`）を熟読・把握すること。
2. 本Surveyでは、開発資料の記述そのものが調査対象である。【調査範囲】に示す差分を取得し、そこで追加・変更された記述（差分の `+` 行）を照合の対象とすること。対象の記述の前後の文脈を確かめるために、`./PROJECT_ARCHITECTURE.md` と `./_doc/arch/` 配下の該当ファイルを読んでよい（本REQでパスを指定しているため、`_doc/` 配下の読み取りを許可する。`_doc/` の他のファイルは読まない）。
3. 調査対象のコードを読み、資料の記述と実コードに相違がある場合は、その相違点を調査結果に必ず含めること（作業は中断しない）。資料に書かれていない事項がコードに存在することは相違とみなさない。
4. 【調査要件】に従って調査を行い、実コードから読み取れる事実のみを抽出すること。推測・改善提案は求めていない。推測を含める必要がある場合は、どこまでが実コードの記述でどこからが推測かを明示すること。
5. コード調査が完了したら、この時点までにソースコードおよび資料ファイルを一切変更していないことを（`git status` で）確認したうえで、Survey作業レポートテンプレート（`./_log/TEMPLATE_RES_Survey.md`）を元に、作業レポート（`./_log/res/261110_1645_RES_Survey_Phase05_Doc_Consistency.md`）を新規作成して出力すること。
6. すべての調査が完了したら、チャットにて「調査が完了しました。RESの確認をお願いします」と報告すること。

## 【調査要件】
Phase 5 の各サブフェイズの最終タスクで開発資料へ反映された記述が、Phase 5 終了時点（現在の `HEAD`）の実コードの事実と食い違っていないかを確かめる。各サブフェイズの反映時点ではそのサブフェイズの差分監査に合格しているため、特に **後のサブフェイズのコード変更によって、前のサブフェイズで書いた記述が古くなっていないか** を重点的に見る。

* **要件1: 差分で追加・変更された記述の照合**
  * 【調査範囲】の差分の `+` 行に書かれた事実の主張を、1つずつ実コードと照合する。照合するのは次のような、コードで真偽を確かめられる主張である：
    * ファイル・フォルダの存在と配置（1章のフォルダ構成図。`test/` 配下を含む）
    * import の有無・向き（1章「依存方向」、`_doc/arch/12_shapes.md`・`14_edit.md` の「importは〜のみ」「使う側」）
    * 公開メソッド・公開の関数・定数・typedef の一覧（`_doc/arch/03_VectorModel.md`・`04_CanvasManager.md`・`10_ShapeFactory.md`・`12_shapes.md`・`14_edit.md`、3章11.の「端点を指定する入口」）
    * 引数・戻り値・既定値・通知の回数など、関数の振る舞いの記述（`replaceShape` の `select`/`keepId`、`setSnapPoint`/`clearSnapPoint` の通知、`validateShapeData` の頂点数の引数、`Path.hitTestHandle` の戻り値 等）
    * 呼び出し元・呼び出し順・記録の時点（3章6.「記録する操作と時点」、3章11.・12.の「流れ」、`_doc/arch/08_HistoryManager.md` の呼び出し元）
    * `main.js` の配線（`_doc/arch/02_main.md` の配線ブロックの表・注入の表・生成順の制約・主な関数）
    * `InputTracker` の配線の場面と表示を消す箇所（3章12.「表示を消す箇所」、`_doc/arch/06_InputTracker.md`）
    * 数値（行数：`main.js` 593行・`InputTracker.js` 1310行、距離：5px・8px、表示の正方形の大きさ）。行数は `wc -l` 等で実測し、資料の値と並べて記載する。
    * `index.html` の要素・属性（`#selection-join`・`.selection-button-row`・`title` の `(J)`・`disabled` の初期状態）
    * 自動テストの記述（`_doc/arch/16_test.md`。テストファイルの存在、テストの内容の記述が実際のテストケースと合っているか。偽物と実物の使い分けの記述）
  * 「発注者の決定」「やらないこと」「注意」のように意図・方針を述べる記述は、それがコードの振る舞いとして確かめられる範囲（例：「自動で閉じない」「頂点2つの線は閉じない」）だけを照合し、方針そのものの是非は扱わない。
* **要件2: 照合の結果の整理**
  * 相違が見つかった記述は、RESの5章に「（対象：資料のファイルと節）：（資料の記述）→（実コードの実態。`ファイル:行` を添える）」の形で記載する。
  * 相違ではないが、記述があいまいで実コードと照らして複数の読み方ができるものがあれば、4章の「推測・所見」に記載する（5章には入れない）。
  * 照合した主張と結果を、資料のファイル（節）ごとに4章へまとめる（照合済みで一致したものは「一致」と短く書けばよい。照合できなかった主張があれば、その理由を書く）。
