# 設計指針書 DIR: Phase 03 : 編集基盤
* ルール: `./PROJECT_CONSTITUTION.md`
* 開発資料: `./PROJECT_ARCHITECTURE.md`

## 1. 大ゴール
Phase 2までで図形の作成・選択・移動・削除の操作基盤は整ったが、操作の取り消しができず、ブラウザを再読み込みすると作業内容が失われるため、作品を作り続けられない状態にある。本Phaseでは、図形データとJSONの相互変換（シリアライズ）を全図形の共通契約として確立し、それを基にUndo/Redo、複製・コピー＆ペースト、ブラウザ内の複数キャンバス管理（自動保存）、ファイル入出力（書き出し・開く・インポート）を実装する。後続のパス（多角形）・着色Phaseでは、新しい図形クラスや図形プロパティをこの契約に沿って追加するだけで、Undo・保存・コピー＆ペーストの対象になる状態を目指す。
* **完了の目安**: ゴール型。サブフェイズ一覧のPhase 03-01〜03-05の実装要件が、テストプレイで使い物になると発注者が判断した状態。

## 2. やらないこと（Non-goals）
* ゲームエンジン向けの書き出し形式（JS/ESM） → 書き出しPhase（ゲームエンジンの設計後に、本Phaseの作業データ形式からの変換として実装する）
* 複数キャンバスの同時表示（タブ切替・アートボード） → 未定（本Phaseでは画面に開くキャンバスは常に1枚）
* キャンバスごとのUndo履歴の保持、Undo履歴の保存 → 意図的に行わない（キャンバスを開き直すと履歴はリセットされる）
* キャンバスのサイズ・枠の設定 → 意図的に行わない（キャンバスは無限の作業領域）
* 基準点（原点）の変更機能 → 意図的に行わない（基準点は常にワールド座標の原点(0, 0)。ずらしたい場合は全図形を移動して調整する）
* 多角形パス・頂点の追加削除・パスの結合、`Curve`の制御点追加削除 → 次Phase（パス）
* 色・塗りつぶし・図形プロパティの表示と数値編集、重なり順の変更 → 着色Phase
* 拡大縮小・回転・反転、スナップ、グループ化 → 未定（変形・整理Phase候補）
* 大量の図形（数千規模）を前提とした描画・当たり判定の高速化 → 未定
* メニューバーの新設 → 意図的に行わない（本アプリの機能はすべてフロートパレットで提供し、メインのコントロールパネルがメニューバーの代替として他パレットの呼び出し口を担う。本Phase以降も同じ方針）

## 4. サブフェイズごとの実装要件

### Phase 03-01: シリアライズ契約
* **目的**: すべての図形を、図形種別を含むJSONへ変換し、JSONから同じ図形を復元できるようにする。
* **実装要件**:
  * 5種の図形（直線・曲線・弧・矩形・円）を作成・変形した状態で、キャンバス全体をJSONへ変換し、そのJSONから復元すると、見た目・頂点位置・選択やハンドル操作の挙動が変換前と同じになる（確認用の操作手段は開発者向けで構わない。REQ作成時に決める）。
  * 変換したJSONには形式のバージョン番号が含まれる。
  * 未知の図形種別を含むJSONを復元しようとした場合、アプリが停止せず、その図形を読み込めなかったことが分かる。
  * キャンバス上でワールド座標の原点(0, 0)の位置が視覚的に分かる（パン・ズームに追従する）。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章A：図形種別の一覧が`ShapeFactory`・`InputTracker`の`SHAPE_TYPES`・`PaletteController`・`index.html`に多重管理されている件（JSONの図形種別から図形クラスを引く対応表が必要になるため、ここで一本化する）。
  * `_doc/COWORK_STATUS.md` 2章A：`ShapeFactory.create()`が未知の`type`で`Error`をthrowし、呼び出し元が`try/catch`していない件。
* **メモ**: 現状、`type`プロパティを持つのは`Ellipse`のみで、`Line`は`points`配列を持たず`x1/y1/x2/y2`で頂点を保持する（`PROJECT_ARCHITECTURE.md` 2章）。全図形に図形種別を持たせるか、JSON変換時にのみ種別を付与するか、`Line`の頂点保持形式を揃えるかはREQ作成時に決める。保存形式は「エディタ独自の作業データ形式」であり、ゲームエンジン側の都合は考慮しない。後続Phaseで図形クラス・プロパティが増えるたびに形式が変わる前提で、バージョン番号による旧形式の変換（マイグレーション）の置き場所を決めておくこと。選択状態・ホバー・表示位置（ビュー変換）を保存対象に含めるかもREQ作成時に決める。

### Phase 03-02: Undo/Redo
* **目的**: 図形に対する操作を取り消し・やり直しできるようにする。
* **実装要件**:
  * 図形の作成・削除・本体移動・ハンドルによる変形を、`Ctrl`+`Z`で1操作ずつ取り消し、`Ctrl`+`Y`（および`Ctrl`+`Shift`+`Z`）でやり直せる。
  * 1回のドラッグ（移動・変形）は、途中経過を含めて1操作として取り消される。複数選択の一括移動・一括削除も1操作として扱う。
  * 選択の変更・パン・ズームは取り消しの対象にならない。
  * 取り消した後に新しい操作を行うと、やり直しの履歴は破棄される。
  * Undo/Redoはコントロールパネル等のボタンからも実行でき、取り消せない（やり直せない）ときは押せない状態になる。
* **持ち越し事項**: なし
* **メモ**: 履歴は現在開いているキャンバスに対してのみ有効で、キャンバスを開く・新規作成した時点でリセットされる（Phase 03-04・03-05で接続する）。実装方式は、Phase 03-01のシリアライズを用いて操作前後の状態を丸ごと記録するスナップショット方式を第一候補とする（変更経路ごとの逆操作を書かずに済み、後続Phaseで図形クラスが増えても追従が要らないため）。履歴の上限件数、ドラッグ中・作成途中の図形がある状態でのUndoの扱いはREQ作成時に決める。ショートカットは`KeyboardShortcuts`の対応表へのエントリ追加で実装し、テキスト入力中・IME変換中の除外は既存の受理判定に従うこと。コントロールパネル下端と図形パレットの余白が24pxしかない件（`_doc/COWORK_STATUS.md` 2章C）に注意し、ボタンの配置先をREQ作成時に決める。

### Phase 03-03: 複製・コピー＆ペースト
* **目的**: 選択中の図形を複製し、同じキャンバス内および別のキャンバスへ貼り付けられるようにする。
* **実装要件**:
  * 選択中の図形（単一・複数とも）を`Ctrl`+`C`でコピーし、`Ctrl`+`V`で貼り付けられる。貼り付けた図形は元の位置から少しずれた位置に置かれ、貼り付けた図形だけが選択状態になる。
  * `Ctrl`+`X`で切り取り、`Ctrl`+`D`で複製（コピー＆ペーストを1操作で行う）ができる。
  * 貼り付け・複製した図形は元の図形と独立しており、片方を変形・削除してももう片方に影響しない。
  * 貼り付け・切り取り・複製はそれぞれ1操作としてUndo/Redoできる。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章C：`commitDraft()`のid採番（連番文字列）が永続化・再読込を考慮していない件（貼り付け・読込時にidが既存図形と衝突しないこと）。
  * `_doc/COWORK_STATUS.md` 2章P3【03-03へ・03-02由来】：貼り付け・切り取り・複製の履歴記録（`HistoryManager`の`beginEdit()`/`commitEdit()`で囲む）と、ショートカット追加時の`ShiftRule`（3値）の指定。
* **メモ**: 別キャンバスへの貼り付けはPhase 03-04の完了後に確認できる。クリップボードをアプリ内部に持つか、OSのクリップボード（Clipboard API）を使うかはREQ作成時に決める（OSのクリップボードを使う場合、ブラウザの権限・セキュリティ制約がある）。`Ctrl`+`D`はブラウザのブックマーク追加と衝突するため`preventDefault()`が必要。`V`キー単体は選択モードのショートカットであり、`Ctrl`+`V`との区別は`KeyboardShortcuts`の修飾キー規則に従うこと。ここで作るidの振り直しと貼り付け処理は、Phase 03-05のインポートで再利用する。

### Phase 03-04: ブラウザ内のキャンバス管理
* **目的**: ブラウザ内に複数のキャンバスを保存し、切り替えて編集できるようにする。
* **実装要件**:
  * 編集中のキャンバスは自動的にブラウザ内へ保存され、ブラウザを再読み込み・再起動すると、最後に編集していたキャンバスがその状態で開かれる。
  * ブラウザ内に保存されたキャンバスの一覧を表示でき、一覧から選んで開くと、現在のキャンバスと入れ替わる（画面に開くキャンバスは常に1枚）。
  * キャンバスの新規作成・名前の変更・削除ができる。削除は確認を経てから行われる。
  * キャンバスを開く・新規作成すると、Undo/Redoの履歴はリセットされる。
  * 開いているキャンバスの名前が画面上で分かる。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章P3【03-04へ・03-02由来】：キャンバスを開く・新規作成したときの`historyManager.clear()`の呼び出し（03-02では手段の用意のみ）と、`main.js`の肥大化（03-03完了時点で418行。スナップショットの取得・適用関数の切り出しを検討。置き場所の候補は03-03で新設した`js/edit/`）。
  * `_doc/COWORK_STATUS.md` 2章P3【03-04へ・03-03由来】：Phase 03-03の実装要件のうち「別のキャンバスへの貼り付け」は、本サブフェイズ完了後にテストプレイで確認する（クリップボードはページ内のメモリに保持され、キャンバスを切り替えても消えない設計）。
* **メモ**: ファイル関連の操作（本サブフェイズのキャンバス管理とPhase 03-05のファイル入出力）は、メインのコントロールパネルとは別の専用パレットへ集約する方向とする（本サブフェイズで新設し、Phase 03-05で同じパレットに操作を追加する）。メニューバーを持たない方針（2章）のため、コントロールパネルは「操作モードの切り替え」「頻繁に使う操作（削除・Undo/Redo・倍率表示/リセット）」「他パレットの呼び出し口」を担う位置づけになり、ファイル用パレットは呼び出し口の最初の例になる（後続Phaseのプロパティパネル等も同じ形で追加される前提で、呼び出し口を増やしやすい形にしておく）。専用パレットを常時表示にするか、コントロールパネルのアイコンから開閉する形にするか、ボタンの配置などUIの詳細はREQ作成時に決める（開閉式の場合、パレットのDOMを`index.html`に静的に置いて表示を切り替えれば、`WindowManager`の動的追加ウィンドウ非対応（`_doc/COWORK_STATUS.md` 2章C）に抵触しない）。保存先（`localStorage`／`IndexedDB`）、自動保存のタイミング（変更のたび／一定間隔）、開いているキャンバス自体を削除した場合の挙動はREQ作成時に決める。`localStorage`は容量が約5MBのため、キャンバス数・図形数の増加を考えると`IndexedDB`が候補になる。自動保存の対象は図形データ（Phase 03-01の作業データ形式）であり、Undo履歴は含めない。

### Phase 03-05: ファイル入出力
* **目的**: キャンバスをファイルとして書き出し・読み込み、別ファイルの図形を現在のキャンバスへ追加できるようにする。
* **実装要件**:
  * 現在のキャンバスを、作業データ形式のファイル（JSON）としてダウンロードできる。
  * ファイルを選んで「開く」と、そのファイルがブラウザ内のキャンバス一覧に新しいキャンバスとして登録され、現在のキャンバスと入れ替わって開かれる（Undo/Redoの履歴はリセットされる）。
  * ファイルを選んで「インポート」すると、現在のキャンバスの図形はそのまま残り、ファイル内の図形が追加される。追加された図形だけが選択状態になり、インポートは1操作としてUndo/Redoできる。
  * 旧バージョンの形式のファイルも読み込める（形式が変わっていない間は、現行バージョンのファイルで確認する）。
  * 形式が壊れたファイルや本アプリの形式でないファイルを選んだ場合、アプリが停止せず、読み込めなかったことが分かる。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章P3【03-05へ・03-03由来】：インポートは`ShapeInserter.insertDocument`を再利用する（呼び出し側で進行中の入力操作の中断と選択モードへの切り替えを先に行う。図形の追加は`VectorModel.addShapesWithNewIds`を使う）。
  * `_doc/COWORK_STATUS.md` 2章P3【03-05へ】：一般利用者向けの読み込み失敗通知UIが未実装の件（03-01由来）。03-04で保存・読み込み失敗の表示（`CanvasLibrary`の`issue`・`CanvasPalette`の`ISSUE_MESSAGES`）ができたため、見直す際はここに統合する。
  * `_doc/COWORK_STATUS.md` 2章P3【03-05へ・03-04由来】：書き出し・開く・インポートの操作はキャンバスパレットに追加し、「開く」は`CanvasLibrary`の新規作成・切り替え処理（履歴のリセット・ビュー変換の初期化を含む）を再利用する。
* **メモ**: インポートはPhase 03-03の貼り付け処理（idの振り直し・選択状態の設定）を再利用する。インポート時の配置位置（元の座標のまま／ずらす）、ファイル名とキャンバス名の対応、書き出しファイルの拡張子はREQ作成時に決める。ファイル選択・ダウンロードはサーバー側の処理を必要とせず、ブラウザ内で完結する方式（`input type="file"`・`Blob`のダウンロード等）を前提とする。将来テキスト入力欄（キャンバス名の入力等）を追加する場合は、RES `261031_2121` 5章「将来テキスト入力欄を追加した際の確認項目」で誤作動がないことを確認すること（Phase 03-04も同様）。
