# 設計指針書 DIR: Phase 02 : UI・操作充実
* ルール: `./PROJECT_CONSTITUTION.md`
* 開発資料: `./PROJECT_ARCHITECTURE.md`

## 1. 大ゴール
Phase 1で5大図形（直線・曲線・弧・矩形・円/楕円）の作成・編集は可能になったが、キャンバスのパン・ズームがなく、操作モードの意味づけも曖昧なため、実用的な編集アプリとして使えない状態にある。本Phaseでは、操作モードの再設計、ビュー変換（パン・ズーム・グリッド）、複数選択、削除UI・キーボードショートカットを実装し、図形を直感的に作成・選択・移動・削除できる操作基盤を整える。ビュー変換（スクリーン座標とワールド座標の分離）を先に確立することで、後続Phase（多角形生成・着色）で座標系に起因する手戻りを避ける。
* **完了の目安**: ゴール型。サブフェイズ一覧のPhase 02-01〜02-04の実装要件が、テストプレイで使い物になると発注者が判断した状態。

## 2. やらないこと（Non-goals）
* 多角形パス（閉じたパス）の作成・頂点の追加削除 → 次Phase（多角形生成）
* 図形プロパティの表示・数値編集、色変更、塗りつぶしON/OFF、カラーピッカー → 着色Phase
* Undo/Redo → 未定
* Shiftクリックによる個別の追加選択・選択解除 → 未定（本Phaseの複数選択は範囲選択のみ）
* 複数オブジェクトのグループ化 → 未定
* レイヤーウィンドウ（オブジェクト一覧・表示非表示・ロック・Zsort） → 未定
* グリッドへのスナップ → 未定（本Phaseのグリッドは表示のみ）
* キャンバス下地色の変更 → 未定
* ベジェ曲線の制御点追加削除・moveハンドル → 多角形生成Phase
* ファイル入出力（JS形式） → 未定
* タッチ操作対応 → 未定

## 4. サブフェイズごとの実装要件

### Phase 02-01: 操作モード再設計
* **目的**: コントロールパネルを「現在の操作モード」を切り替える場所として再定義し、後続のパンモード等を追加できる構造にする。
* **実装要件**:
  * コントロールパネルに「選択」「図形作成」の操作モードボタンが並び、押したボタンだけがハイライトされる。
  * 「図形作成」モードでは、図形パレットで選んだ図形種別（直線・曲線・弧・矩形・円）でキャンバスに図形を作成できる。図形パレットのボタンとコントロールパネルのボタンが同時に同じ意味でハイライトされる状態は解消されている。
  * コントロールパネルのヘッダーをドラッグするとウィンドウが移動する。
  * 図形作成モード中でも、マウスカーソルがキャンバス上にあることが視覚的に分かる（カーソル形状の変化等）。選択モード中は、図形・ハンドルの上でカーソル形状が変わる。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章A：直感的なオブジェクト操作・作成ができない／`line`ツール中のホバー視覚フィードバックなし／コントロールパネルのヘッダードラッグ非機能（`mousedown`の`stopPropagation`との整合確認）／`InputTracker.setTool(tool)`の引数バリデーションなし・`main.js`の`createToolClickHandler`の2ボタン限定実装／`currentTool`ガード条件のJSDoc記載漏れ／操作モードボタン再設計（「直線ツール」の統合）／`toolButtons`へのボタン追加時はDOM側を先に用意する注意点。
* **メモ**: Phase 02-02で「キャンバス移動（パン）」モードボタンを同列に追加する前提で、モード種別を増やしやすい形にしておく。モード名・ボタン表記はREQ作成時に発注者と決める。

### Phase 02-02: ビュー変換（パン・ズーム・グリッド）
* **目的**: 表示位置と表示倍率を変更できるようにし、図形データ（ワールド座標）と画面表示（スクリーン座標）を分離する。
* **実装要件**:
  * マウス中ボタンでキャンバスをドラッグすると表示位置が移動する（どの操作モード中でも有効）。
  * スペースキーを押しながら左ドラッグすると表示位置が移動する（どの操作モード中でも有効、スペースキーを離すと元のモードの操作に戻る）。
  * コントロールパネルの「キャンバス移動」モードボタンを選ぶと、左ドラッグで表示位置が移動する。
  * マウスホイールで、カーソル位置を中心に表示倍率が拡大・縮小する。
  * 現在の表示倍率が画面上に表示され、リセット操作で倍率100%・初期表示位置に戻る。
  * キャンバスの背景にグリッドが表示され、パン・ズームに追従する。
  * パン・ズームした状態でも、図形の作成・選択・ハンドル操作・移動・削除がPhase 1と同じ感覚で行える（クリック位置と図形の位置がずれない）。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章A：パン機能が未実装。
  * `_doc/COWORK_STATUS.md` 2章B：`moveShape`の差分計算のDPI・CSSズーム環境下での誤差未検証（ズーム/パン実装時に本格検証）。
* **メモ**: 倍率の上限・下限、ズームの刻み幅、グリッド間隔（倍率に応じて間隔を変えるか）、ハンドル・当たり判定の許容幅や線幅を画面上の見た目で一定に保つか倍率に比例させるかは、REQ作成時に発注者と決める。スペースキー判定は、将来のテキスト入力欄との干渉（Phase 02-04で扱う誤爆対策）を考慮すること。 「キャンバス移動」モード追加時は、Phase 02-01で導入した`OperationMode`（`InputTracker.js`）・`modeButtons`（`main.js`）・`index.html`の3箇所へ追加し、カーソル形状は`InputTracker#resolveCursor`の「選択・作成以外のモード」分岐に追加する。あわせて、選択モード等で図形パレットが`.disabled`（`pointer-events: none`がウィンドウ全体に掛かる）の間はヘッダーもドラッグできない件を、`.disabled`の適用先を`.window-body`に限定する等で解消するか判断する（発注者は現状許容、2026-10-06）。

### Phase 02-03: 範囲選択・複数選択
* **目的**: 複数の図形をまとめて選択し、まとめて移動・削除できるようにする。
* **実装要件**:
  * 選択モードでキャンバスの空白部分から左ドラッグすると選択範囲の矩形が表示され、離した時点で範囲内の図形がすべて選択状態になる。
  * 複数選択中の図形のいずれかをドラッグすると、選択中の全図形が一緒に平行移動する。
  * 複数選択中に`Delete`/`Backspace`キーを押すと、選択中の全図形が削除される。
  * 空白部分をクリックすると選択がすべて解除される。
  * 縮退した楕円（`rx`または`ry`がほぼ0）も範囲選択で選択・削除できる。
  * パン・ズームした状態でも範囲選択が正しく機能する。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章A：縮退状態の`Ellipse`が`hitTest`で選択不可能になる制約への対応（範囲選択による選択手段の確保）。
* **メモ**: 現状`VectorModel`は単一の`selectedId`で選択状態を保持しているため、複数選択に対応する状態の持ち方の変更が必要になる。範囲選択の判定基準（図形全体が範囲内に収まったら選択／一部でも掛かれば選択）、複数選択中のハンドル表示の扱いはREQ作成時に発注者と決める。範囲選択の矩形は、Phase 02-02で導入したワールド/スクリーン座標の区別（`InputTracker.getWorldCoordinate`/`getScreenCoordinate`、`ViewTransform`）に従うこと。Phase 02-02でパン・ズームの入力解釈が`InputTracker`に加わり肥大化しているため、範囲選択ドラッグを追加する際にドラッグ操作の解釈（パン・範囲選択・ハンドルドラッグ）を別クラスへ分離するかをREQ作成時に検討する。

### Phase 02-04: 削除UI・キーボードショートカット
* **目的**: 削除操作の発見しやすさを上げ、主要操作をキーボードから実行できるようにする。
* **実装要件**:
  * 選択中の図形（単一・複数とも）を削除するボタンがUI上にあり、図形が未選択のときは押せない状態になる。
  * キーボードショートカットで操作モードの切り替え等の主要操作が行える。
  * テキスト入力欄にフォーカスがある間は、`Delete`/`Backspace`/スペース等のキーが図形削除・パン・ショートカットとして誤作動しない（現時点で`index.html`にテキスト入力欄は存在しないため、将来の入力欄追加に備えた判定の導入となる。確認用の入力欄を置くかはREQ作成時に決める）。
* **持ち越し事項**:
  * `_doc/COWORK_STATUS.md` 2章A：図形削除UIがなく発見しにくい／`InputTracker`の`keydown`が`document`購読のため、テキスト入力中の`Delete`/`Backspace`誤爆を除外するロジックが必要。
* **メモ**: 削除ボタンの配置先（コントロールパネル等）、ショートカットの対象操作とキー割り当ては、REQ作成時に発注者と決める。テキスト入力中の誤爆対策は、Phase 02-02で用意した`InputTracker.js`のexport関数`isTextInputElement(element)`を再利用すること（現状は`input`要素を`type`を問わずテキスト入力扱いとする保守的判定のため、`type`別の扱いが必要か再検討する）。 Phase 02-03で選択状態は選択集合（`VectorModel.getSelectedIds()`）になり、一括削除は`VectorModel.deleteShapes(ids)`で行える（`InputTracker.handleKeyDown`の`Delete`/`Backspace`は選択モード・`IDLE`状態のみ受理）。削除ボタンは同APIを再利用し、押せる/押せない状態は選択集合が空かどうかで`model.onChange`経由で同期すること。ドラッグ中（`DragTracker`のセッション中）の削除は受け付けない現行方針に揃えること。
