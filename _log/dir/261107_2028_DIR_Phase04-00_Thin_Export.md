* ルール: `./PROJECT_CONSTITUTION.md`

## 1. 大ゴール
Phase 3で図形データとJSONの相互変換（作業データ形式）と、作業データのファイル入出力が整ったが、作ったスプライトをゲーム（OZ Engine）で使う手段がない。本Phaseでは、1キャンバスを1スプライトとして、ゲームがそのまま`import`して描けるJSファイル（ESM）へ書き出す機能を作り、書き出したJSをOZ Engineで実際に表示できることを確かめる。書き出しの形は、後続Phaseで色（P5）・パス（P6）を足し、複数スプライトを組み立てるキャラ合成（P7）を行うときに、作り直さずに拡張できる形とする。
* **完了の目安**: ゴール型。エディタで描いた線画を書き出したJSを、OZ Engineの`assets/sprites/ship.js`と差し替えて表示できる（線画で可）と発注者が判断した状態。

## 2. やらないこと（Non-goals）
* 着色・塗りつぶし・線なしの表現 → P5（着色）
* 多角形パス・頂点の追加削除・結合・分割 → P6（パス）
* 組み立て用（キャラ合成）のJSの書き出しと、複数スプライトの配置を編集するモード → P7（アニメーションエディタモード）
* ベクター編集のキャンバスと組み立て側のキャンバス名によるリンク、1セット丸ごとの書き出し → P7で入れるかを決める
* パーツのファイル名を変えたときに、組み立て側の参照を自動で追いかける仕組み → 意図的に行わない（組み立てエディタで読み込み直して書き出し直す）
* 複数キャンバスをまとめて1ファイルへ書き出すこと、複数キャンバスの一括書き出し → 意図的に行わない（1キャンバス＝1スプライト＝1ファイル）
* PNG・SVG等、JS/JSON以外の形式での書き出し → 未定
* OZ Engine側の実装（スプライトの読み込み・描画処理の作成・変更）と、エンジン側の規約（`D:\ozlab\ozengine-web\PROJECT_ARCHITECTURE.md` 2.1章）の改訂 → OZ Engine側の作業（本Phaseでは、エンジン側へ渡す提案を文書にまとめるところまで）
* `Ellipse`の回転の表現 → P5（作業データ形式の版上げとあわせて判断する）
* 書き出しファイルの圧縮・最小化 → 未定
* ビルドツールの導入 → 意図的に行わない（自動テストはテストの実行のみで、ビルドは行わない）

## 4. サブフェイズごとの実装要件

### Phase 04-01: 自動テストの導入
* **目的**: ブラウザを開かずに、作業データ形式の変換（シリアライズ）と、後続の書き出しをコマンド1つで検証できるようにする。
* **実装要件**:
  * コマンド1つ（`node --test`を基本とする）で自動テストが実行され、結果（成功・失敗の件数）が表示される。
  * 5種の図形（直線・曲線・弧・矩形・円）について、作業データ形式へ変換してから復元すると同じ頂点・プロパティに戻ることを確かめるテストがある。
  * 旧バージョンの作業データ・壊れたデータ・未知の図形種別を読み込んだときの挙動（Phase 03-01・03-05で決めたもの）を確かめるテストがある。
  * 自動テストを追加しても、エディタ本体はこれまでどおり`index.html`をブラウザで開くだけで動く（ビルドの手順は増えない）。
* **持ち越し事項**: なし
* **メモ**: Node.jsをこのプロジェクトで使うのは初めてになる。`PROJECT_CONSTITUTION.md`（ビルドツールなしの方針）と照らし、テストの実行に限ることをREQで明記すること。ESモジュールをNode.jsで読むための設定（`package.json`の`"type": "module"`、またはテストファイルの拡張子）、テストファイルの置き場所、テスト対象のモジュールがDOM（`document`・`window`等）に依存していないかはREQ作成時に決める・調べる。DOMに依存しているためテストできない箇所があれば、本サブフェイズでは無理に切り離さず、懸念事項として記録する。テストの実行方法は`PROJECT_ARCHITECTURE.md`（またはその分冊）へ記載する。

### Phase 04-02: スプライトJSの書き出し
* **目的**: 現在のキャンバスを、ゲームが`import`して描けるスプライトJS（ESM）として書き出せるようにする。
* **実装要件**:
  * キャンバスパレットの操作で、現在のキャンバスをスプライトJS（`.js`）としてダウンロードできる。同じ中身をJSON（`.json`）として書き出すこともできる。
  * 書き出したJSは、他のファイルに依存せず、それ単体で`import`でき、含まれる描画関数（`draw(ctx)`）を呼ぶとキャンバスの線画がエディタと同じ見た目で描かれる。
  * 書き出したJSには、次が含まれる。
    * 書き出し形式のバージョン番号
    * 描画に使うデータ（座標はpx、基準点はワールド座標の原点(0, 0)、y軸は下向き）
    * 外枠（スプライトの縦横の範囲）
    * 作業データ（`source`。Phase 3の作業データ形式そのもの）
  * 図形の頂点の並び順は、書き出しで並べ替えられない。図形のidが書き出しに残る。
  * 書き出しの既定のファイル名が付く（ダウンロード時に変更できる範囲は、ブラウザの通常の挙動に従う）。
  * 図形が1つもないキャンバスを書き出そうとした場合、アプリが停止せず、どうなったかが分かる。
* **持ち越し事項**: なし
* **メモ**: 書き出しの形は、エンジンの都合を考えずに作る。`D:\ozlab\ozengine-web\PROJECT_ARCHITECTURE.md` 2.1章の現行の記述（`format`、`draw`、`source`）は参考にとどめ、縛りにしない（Phase 04-04でエンジン側が使えると確かめた後に、エンジン側で2.1章として正本化する）。ただし後続Phaseのため、次を守ること。
  * 複数スプライトによるキャラ合成（P7）では、組み立て用のJS（名前の頭に`_`を付ける。例：`_hero.js`）が、各パーツのJSを**ファイル名**で`import`して、原点(0, 0)を基準点として配置する。パーツのJSは名前の頭に`_`を付けない。この使われ方を妨げない形にすること（パーツのJS同士で名前が衝突しない、`import`した側でパーツを区別できる等）。
  * バージョン番号は2つを別々に持つ：書き出し形式のバージョンと、作業データ（`source`の中身）のバージョン。2つの項目名をはっきり分け、上げる条件を`PROJECT_ARCHITECTURE.md`へ書くこと（書き出し形式の版は書き出しの形＝エンジンが読む部分が変わったとき、作業データの版は保存形式が変わったとき。作業データだけ版が上がっても書き出し形式の版は上げなくてよい）。
  * 書き出しのデータは、P5の色・P6のパス等の項目を後から足せる形にすること。
  * 書き出し処理は、Phase 04-01の自動テストで検証できる形（DOMに依存しない変換部分を分ける等）にし、テストを追加すること。

  REQ作成時に決める論点：
  * 円・楕円・弧を、Canvasの楕円命令のまま出すか、頂点の並びに変換するか（薄い書き出しでは前者が最小）。
  * 外枠に線の太さを含めるか。
  * スプライトごとの変わらないIDを持たせるか（参照はファイル名で行うため必須ではない。ファイルの差し替え間違いの検出用等として残すか）。
  * 既定のファイル名をキャンバス名から作るか。ファイル名に使える文字と、使えない文字が含まれる場合の扱い。
  * 描画関数を、データを読む共通の描画処理として書き出すか、図形ごとの描画命令を並べて書き出すか（P5・P6で描き方が増えたときの追従のしやすさで判断する）。
  * 書き出しの操作をキャンバスパレットのどこに置くか、JSとJSONの選び方。

### Phase 04-03: 書き出したJSの読み込み確認
* **目的**: OZ Engineの完成を待たずに、エディタ側だけで「書き出し→読み込み→描画」を確かめられるようにし、書き出したJSをエディタで開き直せるようにする。
* **実装要件**:
  * 確認用ページ（エディタ本体とは別のページ）で、書き出したスプライトJSを選ぶと、その`draw(ctx)`で描いた結果と、原点(0, 0)の位置・外枠が表示される。
  * 書き出したJSONを選んだ場合も、同じように表示される。
  * エディタの「開く」「インポート」で書き出したスプライトJS（または同じ中身のJSON）を選ぶと、同梱の作業データ（`source`）から図形が読み込まれる。読み込みは、作業データファイルを開くときと同じ処理（旧バージョンからの変換を含む）を通る。
  * 本アプリが書き出したものではないJS・壊れたファイルを選んだ場合、確認用ページ・エディタともに停止せず、読み込めなかったことが分かる。
* **持ち越し事項**: なし
* **メモ**: 選んだJSファイルをブラウザ内で`import`する方法（`Blob`のURLを使った動的`import`等）と、JSファイルをそのまま実行することの扱いはREQ作成時に決める。エディタで開き直すときは、書き出し側で別の読み込み処理を作らず、Phase 3の作業データの読み込み（`DocumentSerializer`の版の移行を含む）を通すこと。確認用ページを`?dev`のように起動オプションで切り替えるか、別のHTMLファイルにするかもREQ作成時に決める。
  REQ作成時に決める論点：確認用ページで、手書きの組み立て用JS（パーツのJS 2枚をファイル名で`import`し、位置をずらして描く）まで試すか（P7のモードを作らずに、キャラ合成できる形かを本Phaseのうちに確かめられる）。

### Phase 04-04: OZ Engineでの表示確認と往復
* **目的**: 書き出したJSをOZ Engineで実際に表示し、エンジン側で使えない点があればエディタ側の書き出しを直す（往復を最低1回行う）。
* **実装要件**:
  * エディタで描いた線画を書き出したJSを、OZ Engineの`assets/sprites/ship.js`と差し替えると、エンジン上でその線画が表示される（線画で可）。
  * 往復で見つかったエディタ側の直し（書き出しの形の変更を含む）が反映され、Phase 04-01の自動テストとPhase 04-03の確認用ページで引き続き確かめられる。
  * エンジン側の規約（2.1章）へ入れてもらう内容（書き出し形式のバージョン番号、`source`、外枠、頂点の並び順とidの保持、座標の単位・基準点・y軸の向き、パーツの参照をファイル名で行うこと、組み立て用のファイル名の頭に`_`を付けること）が、エンジン側へ渡せる文書としてまとまっている。
* **持ち越し事項**: なし
* **メモ**: エンジン側の作業（読み込み・描画処理の変更、2.1章の改訂）はOZ Engineのプロジェクトで発注者が行い、本サブフェイズでは扱わない。エンジン側の進み具合に合わせて本サブフェイズを進める。往復で書き出しの形を変える場合は書き出し形式のバージョン番号を上げるかを判断し、変えた内容を`PROJECT_ARCHITECTURE.md`へ反映すること。エンジン側へ渡す文書の置き場所と形式はREQ作成時に決める。往復でエディタ側の直しが複数回になる場合は、本サブフェイズの中で続けるか、サブフェイズを追加するかを発注者と相談する。
