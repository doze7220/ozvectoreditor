*   **VertexHandleRules.js**：頂点の選択モードで描く頂点のハンドルの一覧の組み立て、ハンドル名が頂点のハンドルかの判定、矩形に入る頂点の収集（Phase 08-02b）、選んでいる頂点の範囲の算出（Phase 08-04）を、図形の共通メソッドだけを使う状態を持たない関数として提供する（Phase 08-02aで新設）。
    *   **公開**：`collectVertexHandles(mode, shapes, selectedIds, selectedVertices)` → `Array<{ shapeId, handles: Array<{ x, y, selected }> }>`と、`isVertexHandle(shape, handleName)` → 真偽値と、`collectVertexHandlesInRect(shapes, selectedIds, minX, minY, maxX, maxY)` → `Array<{ shapeId, handle }>`（Phase 08-02b）と、`computeVertexHandlesBounds(shapes, vertices)` → `{ minX, minY, maxX, maxY }|null`（Phase 08-04）。
    *   **`collectVertexHandles`**：`mode`が`OperationMode.VERTEX`でなければ空配列。そうでなければ`shapes`の並び（描画順）のうち`selectedIds`に含まれる図形について、`shape.getVertexHandleNames()`の順に`shape.getHandlePosition(name)`で位置を求め（`null`は飛ばす）、`selectedVertices`に同じ`{ shapeId, handle }`の組があれば`selected: true`にする。ハンドルが0個の図形（円・弧）は結果に含めない。毎回新しい配列を返し、引数を書き換えない。
    *   **`isVertexHandle`**：`shape`が`getVertexHandleNames`を持ち、その一覧に`handleName`が含まれるときだけ真（`'move'`・未知の名前・`shape`が`null`／`undefined`は偽で、例外を投げない）。
    *   **`collectVertexHandlesInRect`**（Phase 08-02b。頂点の選択モードの範囲選択が使う）：`shapes`の並び（描画順）のうち**`selectedIds`に含まれる図形（頂点が出ている図形）だけ**を対象に、`getVertexHandleNames()`の順に`getHandlePosition(name)`で位置を求め（`null`は飛ばす）、**境界の上を含めて**`minX <= x <= maxX`かつ`minY <= y <= maxY`なら`{ shapeId, handle }`を集める。並びは図形の並び→ハンドル名の順。円・弧はハンドルが無いため0件。**矩形は正規化済み（`min <= max`）の値を受け取る前提**（正規化は`InputTracker`の確定処理が1か所で行う。ここでは行わない）。図形の当たり（`intersectsRect`）は使わない（頂点の位置そのもので判定するため。`intersectsRect`は線が矩形にかかれば真になり、頂点が矩形の外でも選ばれてしまう）。毎回新しい配列を返し、引数を書き換えない。**`collectVertexHandles`と走査を共有しない**（集める条件と戻り値の形が違い、共通化すると既存の`collectVertexHandles`の本体を書き換えることになるため。将来、戻り値の形がそろう変更が入るなら括り直しを検討する）。
    *   **`computeVertexHandlesBounds`**（Phase 08-04。位置の数値入力が使う）：選んでいる頂点（`{ shapeId, handle }`の組）の**位置だけ**を囲む範囲を求める。各組について`shapes`から`id`が一致する図形を引き（無ければ飛ばす）、`getHandlePosition(handle)`で位置を求め（`null`は飛ばす）、**位置が求まった組だけ**から最小・最大を求める（頂点1つなら最小と最大が同じ値）。位置が求まる組が1つも無ければ（0件を含む）`null`。**線の太さを見ない**（図形の外枠の左上＝`ShapeExtentReader`とは別の求め方で、使い分けは`edit/PositionInputEditor`。3章20.）。ハンドル名が頂点として扱えるかの判定はしない（選択の時点で済んでいる前提）。円・弧のハンドル名が渡されても`getHandlePosition`が返す位置で求める（種別の分岐を持たない）。**既存の2関数と走査を共有しない**（集める条件と戻り値の形が違い、共通化すると既存の関数の本体を書き換えることになるため）。引数を書き換えない。
    *   **読むもの**：図形の共通メソッド`getVertexHandleNames`・`getHandlePosition`と`id`だけ（ポリモーフィックに呼ぶ。図形種別の分岐・図形固有のプロパティ名・`vertexIndex`規約を持たない）。importは`core/InputModes`の`OperationMode`のみ。
    *   **使う側**：`main.js`（`renderCurrentState`が`collectVertexHandles`の結果を`canvasManager.render`の`vertexHandles`へ渡す）と`core/InputTracker`（`#classifyPoint`が`isVertexHandle`で頂点のハンドルだけに絞り込む）と、`edit/PositionInputEditor`（`computeVertexHandlesBounds`だけ。頂点の選択モードで位置の欄に出す範囲。Phase 08-04で`edit/`から`core/`をimportする例が増えた）。`SelectionRules`と同じく、`core/`の処理と`main.js`の両方が使う位置づけ。
    *   **知らないこと**：DOM・`CanvasManager`の描き方（色・大きさ）・`VectorModel`（選択集合・頂点の選択は引数で受け取る）・表示倍率・履歴・入力の状態。
    *   **置き場所の理由**：`CanvasManager`は状態・図形を知らず位置を引数で受け取り、`main.js`は判定・計算を持たず、`InputTracker`は図形種別を知らない。この3つの制約を同時に満たす置き場所が、`core/`の状態を持たない規則だった。ハンドル名の一覧の読み取りを1か所にまとめる意味もある。`InputTracker`の再分離ではない。
    *   **注意**：頂点として扱う名前の正本は図形の`getVertexHandleNames`（`_doc/arch/12_shapes.md`のハンドル名の契約の4つ目）。表示（`collectVertexHandles`）と当たりの絞り込み（`isVertexHandle`）が同じ一覧を読むため、食い違わない。
