# OZFrameWorks AI駆動開発メソッド v2（発注者・設計AI専用マニュアル）

本ドキュメントは、人間（現場監督）と設計AI（Gemini）が、実装AI（AI-IDE）へ的確な作業指示（REQ）を出すための「発注ワークフロー」を定義したものである。

※ 実装AIのコンテキストノイズとなるため、**本ファイルは実装AIには参照させないこと**。実装AIが必要とする規範は、すべて各TEMPLATEファイル側に自己完結して記載すること（本ファイルへの参照を前提としたテンプレートを作らない）。

## 【登場人物（ロール）】

*   **発注者（頭脳）**: ユーザー（人間） ＋ 設計AI（Gemini Notebook）
*   **作業者（手足）**: AI-IDE（実装AI: Google Antigravity）

## 1. タスク規模の定義と用語

プロジェクトのタスクは、「文脈の連続性（タスク区分）」と「作業の複雑さ（アプローチ）」の2つの軸で柔軟に管理・運用される。

### 1-1. タスク区分（文脈の連続性）

*   **Phase（テーマ駆動型タスク）**
    *   **定義**: Phase全体で一つのテーマを持ち、アーキテクチャに影響を与えるような「連続した文脈」を必要とするタスク群（大規模リファクタリング、新機能群の追加、全体的なブラッシュアップなど）。
    *   **ステップ分割**: Phaseはさらにステップごとに分解し、`Phase XX-XX`（Phase番号-Step番号）といった表記で管理を行う。各ステップは「明確な単一機能の作業」に相当する。
    *   **終了条件**: Phaseの終了は常に「ユーザー（発注者）の決定」によって行われる。開発状況によっては、初期テーマの完遂を待たずにPhaseを中断（クローズ）し、次の開発へ移行することもある。中断時は必ず **5. Phaseクローズ手順** を実施する。

*   **Spot（単発・独立型タスク）** ※v1の「Hotfix」を改称
    *   **定義**: 現在のPhaseのメインテーマとは直接関係しない、文脈の連続性を必要としない「単発で完結するタスク」の総称。
    *   不具合の修正（Bugfix）だけでなく、UIの微細な調整、既存機能の小拡張、パラメータのINI化などすべてを内包する。
    *   **改称理由**: 「Hotfix」は一般に「緊急の本番障害対応」を意味し、この語をテンプレート名として実装AIに渡すと、出力が「最小限・応急処置」寄りにバイアスする。本メソッドでの実体は「単発タスク」であるため、中立語 `Spot` を用いる。

### 1-2. REQ（作業指示）/ RES（作業レポート）

本メソッドでは、すべての作業は「REQ → RES」の対で管理する。

REQは「AI-IDEに対する正式な作業指示」であり、RESは「AIの作業結果を記録する正式な作業レポート」である。以後の修正・調査・リファクタリングは、このRESを起点として行う。

#### REQ（Request）
*   発注者がAI-IDEへ渡す作業指示書。
*   作業目的、制約条件、対象ファイル、期待成果物、**受け入れ基準**を定義する。
*   AIはREQ以外の要求を推測せず、REQの範囲内でのみ作業を行う。
*   ただしREQ自体に不備がある場合は、推測で埋めずに差し戻す（**3. 実装AIの行動規範** 参照）。

#### RES（Result Report）
*   AI-IDEが作業結果をまとめた作業レポート。
*   実施内容、変更ファイル、作業方針、**検証証跡**、**未検証事項**、懸念事項、追加タスクなどを記録する。
*   Phaseでは次工程の入力資料となり、GitHubおよびNotebookLMへ蓄積される。

### 1-3. REQ/RESの必須項目（★v2追加：検証の担保）

v1最大の穴は「完了の根拠が実装AIの自己申告のみ」であった点にある。以下を全テンプレートの必須項目とし、欠落したRESは**未完了として差し戻す**。

#### REQ必須項目：受け入れ基準（完了条件）
発注時点で「何をもって完了とみなすか」を検証可能な形で明記する。

*   **満たすべき状態**: 例）「起動時に設定値がINIから読み込まれ、値変更が再起動後も保持される」
*   **確認手段**: 例）「ビルドが通ること」「該当画面を開き、値Xを入力→再起動→Xが復元されること」
*   **やってはいけないこと（禁止事項）**: 例）「Manager層への新規責務追加は禁止」「他ファイルの整形・リネームは禁止」

> 「受け入れ基準が書けないREQ」は、発注者側の要求定義が未完了である。書けるまで発注しない。

#### RES必須項目：検証証跡と未検証事項
実装AIに、**主張と検証済み事実を分離して書かせる**。

*   **参照元REQ**: REQファイル名（★逆リンク。1-4参照）
*   **REQ制約条件の要約**: 本REQで課された制約・禁止事項を実装AI自身の言葉で再記述させる（NotebookLM側で「なぜそうしたか」を追跡可能にするため）
*   **変更ファイル一覧**: パス＋変更概要＋おおよその変更規模
*   **検証証跡**:
    *   ビルド／コンパイル結果（成否と、エラーがあればその内容）
    *   実行確認（実施した手順と、観測された結果）
    *   受け入れ基準の各項目に対する充足状況（○ / × / 未検証）
*   **未検証事項**: 「実施したと言えないこと」を明示的に列挙させる。実行環境がなく確認できなかった項目、影響範囲の推測に留まる項目など。
*   **懸念事項・追加タスク**

> **厳禁**: 未実施の作業を完了として記載すること、および未検証の項目を検証済みとして記載すること。これはテンプレート内に明文で警告を置く。

### 1-4. ファイル名と相互リンク

*   **REQファイル名**: `YYYYMMDD_HHMM_(要件名).md`
    *   Phase作業中は `PhaseXX-XX_作業概要`
    *   Spotは `Spot_作業概要`、ただし特定Phaseステップに対して明確な場合は `Spot_PhaseXX-XX_作業概要`
    *   調査指示は `Survey_調査内容`
*   **RESファイル名**: `YYYYMMDD_HHMM_(REQ要件名).md`
    *   ファイル名定義はREQ内に含める
    *   基本的には、REQ要件名と同じとする
*   **相互リンク（★v2追加）**
    *   REQ → RES: REQ内に、出力すべきRESファイル名を明記する（v1から継続）
    *   RES → REQ: **RES冒頭に、参照元REQのファイル名を必ず記載させる**。タイムスタンプが異なるため、これがないと過去の追跡時に対応関係が壊れる。

### 1-5. 作業規模とアプローチの選択（運用の柔軟性）

Phase内のステップであるか、Spotであるかに関わらず、その作業の「複雑さ・規模」に応じて以下の発注アプローチを柔軟に使い分ける。

*   **大規模・複雑な作業（事前計画を伴うアプローチ）**
    *   アーキテクチャの変更を伴う場合や、修正箇所が複数にまたがりハルシネーションのリスクがある場合は、必ず事前の計画立案（`TEMPLATE_REQ_PlanMake.md`）を行わせ、タスクを分割してから順次実行させる。
*   **小規模・明確な作業（即時実行アプローチ）**
    *   修正箇所やロジックが明確であり、単一のタスクとして安全に完結できると判断した場合は、事前計画を立てず、単一の作業指示のみで即座に実行・解決させる。

## 2. 実装AIの行動規範（★v2追加）

以下は各REQテンプレートの冒頭に共通ブロックとして埋め込み、実装AIに毎回読ませる。

### 2-1. REQ差し戻し権（Reject）

「REQ以外を推測しない」原則の裏返しとして、**REQが誤っている／情報が不足している場合、実装AIは推測で埋めてはならず、着手前に差し戻す**。

差し戻すべきケース：
*   REQが指定する対象ファイル・関数・シンボルが実在しない
*   REQの前提となる状態と、現在のコードの実態が食い違っている
*   受け入れ基準が、指示された変更範囲では原理的に満たせない
*   指示が複数の解釈を許し、どちらを選ぶかで成果物が大きく変わる

差し戻し時の出力：
*   コードは**一切変更しない**
*   「実行不能」と明示し、根拠となるコード上の事実（ファイル名・該当箇所）と、不足している情報を列挙する
*   選択肢が複数ある場合は、推測で決めず、選択肢とトレードオフを提示するに留める

> 黙って推測で埋められることが、本メソッドにおける最大の事故要因である。差し戻しは失敗ではなく、正常動作として扱う。

### 2-2. スコープ規範
*   REQに明記されていないファイルは、閲覧はしてよいが**変更してはならない**。
*   「ついでの整形」「不要に見えるコードの削除」「命名の改善」は、明示指示がない限り禁止。

## 3. 作業ワークフロー

### 3-1. 【Step 0: 企画検討と要求定義（発注者のみ）】

発注者間でアーキテクチャを議論し、作業規模に応じて以下のパターンから最適なREQ/RESの組み合わせを選択する。

|       | ケース                               | 発注（REQ）                                            | 応答（RES）                                    |
| ----- | ------------------------------------ | ------------------------------------------------------ | ---------------------------------------------- |
| **A** | 複数タスクにまたがる本格的な実装     | `TEMPLATE_REQ_PlanMake.md`                             | `TEMPLATE_RES_ImplementationPlan.md`           |
| **B** | 軽微な新規作業（単一タスク規模）     | `TEMPLATE_REQ_Direct.md`                               | `TEMPLATE_RES_Spot.md`                         |
| **C** | 直前の作業のバグ修正                 | `TEMPLATE_REQ_DirectAppend.md`                         | `TEMPLATE_RES_AddSpot.md`（直前RES末尾へ追記） |
| **D** | 時系列が離れた過去のバグ修正         | `TEMPLATE_REQ_Direct.md`                               | `TEMPLATE_RES_Spot.md`（新規に単独レポート）   |
| **E** | 調査・コード監査（単一タスク規模）   | `TEMPLATE_REQ_Direct.md` ※コード修正の絶対禁止を厳命   | `TEMPLATE_RES_Survey.md`                       |
| **F** | 調査・コード監査（複数タスク規模）   | `TEMPLATE_REQ_PlanMake.md` ※コード修正の絶対禁止を厳命 | `TEMPLATE_RES_SurveyPlan.md`                   |
| **G** | 実行中の計画が破綻した場合の計画改訂 | `TEMPLATE_REQ_PlanRevise.md`                           | `TEMPLATE_RES_ImplementationPlan.md`（改訂版） |

補足：

*   **A**: 計画立案後、`TEMPLATE_REQ_TaskExecution_Lite.md` か `TEMPLATE_REQ_TaskExecution_Additional.md` を用いて、AIに「1タスク＝1チャット」で段階的にタスクを実行させ、タスクごとに作業レポートへ追記させる。
*   **D**: 過去の文脈を引きずらせないため、意図的に新規の単独レポートを立てさせる。
*   **E / F**: 目的は「AIの勝手な推測やコード改変を防ぎ、現在のコードの事実のみを抽出させる」こと。**Fは計画立案の入口をAと共通化**した（v1では別テンプレートを指定していたが、行為は同じ「計画立案」であるため統一）。Fの実行フェーズは「1タスク＝1観点」で監査させ、事実をレポートへ追記させる。
*   **G**: ★v2追加。詳細は 3-4 を参照。

### 3-2. 【Step 1: 計画立案（REQ → RES）】 ※計画立案を伴うREQのみ

発注者がAI-IDEへREQを投げ、AI-IDE自身に自分の理解度に基づいた細かなタスクリスト（RES）を構築させる。

### 3-3. 【Step 2: RES監査 → 作業実行（RES → Code）】

発注者はAI-IDEから上がってきた作業計画書（RES）に対し、必ず以下の **【RES監査項目】** をレビューする。

（※視点のぼやけや見落としを防ぐため、以下の2項目はまとめてチェックせず、**必ず1ステップずつ独立して監査を行うこと**）

1.  **ルール違反、責務違反がないか（アーキテクチャ監査）**
    *   Pull型監視の原則、Managerの巨大化、UIへの状態混入など、アーキテクチャの根幹を崩す設計になっていないか。
2.  **タスクごとの作業量は適切か、ハルシネーションを起こす危険性はないか（スコープ監査）**
    *   変更単位が極力ファイル単位に分割され、AIがコンテキストを混同しない（安全なスコープに収まっている）か。

#### 監査深度のリスク階層（★v2追加）

「全タスクに同じ深度の監査」は人間がボトルネックになり、疲弊によって監査の質そのものが落ちる。以下で深度を変える。

| Lv                           | 該当条件                                                               | 監査                                           |
| ---------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| **Lv.3（全項目）**           | アーキテクチャ変更を含む／Manager・共通基盤に触る／3ファイル以上に跨る | 上記1・2を1ステップずつ独立監査。省略不可      |
| **Lv.2（スコープのみ）**     | 単一ファイル内で完結し、責務境界を跨がない                             | 項目2のみ。項目1は「跨がないこと」の確認で代替 |
| **Lv.1（受け入れ基準のみ）** | 定数値・文言・INI化など、ロジックを変更しない                          | 受け入れ基準と証跡の整合のみ確認               |

Lvの判定は**発注者が行い、REQに明記する**（実装AIに自己申告させない）。

監査を通過した後、以下のテンプレートを用いてAI-IDEに1タスクずつ実行させる。

*   **通常時**: `TEMPLATE_REQ_TaskExecution_Lite.md`
*   **追加指示発生時**: `TEMPLATE_REQ_TaskExecution_Additional.md`

### 3-4. 【Step 2.5: 計画改訂（★v2追加）】

計画に沿ってタスクを進行中、**計画そのものの前提が崩れた**場合の経路。パターンCは「直前作業の傷を直す」ためのものであり、計画の無効化には対応できない。

発動条件（いずれか）：
*   実行中のタスクで、後続タスクの前提が成立しないことが判明した
*   実装AIから受け入れ基準を満たせない旨の差し戻しがあった（2-1）
*   RESの証跡から、既に完了扱いのタスクが実際には未達だったと判明した

手順：
1.  **進行中のタスク実行を停止する**（次のタスクを投げない）。ここで惰性で進めると、破綻した前提の上に変更が積み上がり、切り戻し不能になる。
2.  `TEMPLATE_REQ_PlanRevise.md` を発行する。REQには以下を含める：
    *   元の計画RESファイル名
    *   完了済みタスクと、その証跡上の到達点
    *   破綻した前提と、その根拠（コード上の事実）
    *   改訂後に維持すべき目的（テーマ自体を変えるのか、経路だけ変えるのか）
3.  実装AIに**残タスクのみを対象とした改訂計画**を出させる。完了済みタスクを再計画対象に含めない（やり直しの重複実行を防ぐ）。
4.  改訂計画は元RESとは別ファイルとし、元RESには「本計画はYYYYMMDD_HHMM_◯◯にて改訂」と追記させる。

> 前提が崩れた回数と原因は、Phaseクローズ時の振り返り材料として価値が高い。改訂REQは必ず残す。

### 3-5. 【Step 3: 完了監査とクリーンアップ】

最終監査を行い、コミットとアーキテクチャ資料の更新を行う。

**完了監査チェックリスト**：
*   RESの受け入れ基準が全項目 ○ になっているか（× または 未検証 が残っていれば完了ではない）
*   「未検証事項」に、看過できない項目が残っていないか
*   REQで指定していないファイルが変更されていないか
*   懸念事項・追加タスクが、次のREQまたはバックログに転記されたか

**PROJECT_ARCHITECTURE.md の更新タイミング（★v2変更）**：
*   v1では「Phase完了時（Step 3）のみ」であったが、長いPhaseの途中で実装AIが参照する資料が実態からズレ、それ自体がハルシネーション源になる。
*   **アーキテクチャに影響するステップの完了ごとに、差分を追記する**運用に変更する。全体の整形・清書はPhase完了時にまとめて行ってよい。

### 3-6. 【Step 4: 成果物の保管と知識ベース化】

*   作成されたREQ/RESファイルは、GitHubにてそれぞれフォルダに保存して管理する。
    *   REQ保存場所: `_log/req/`
    *   RES保存場所: `_log/res/`
    *   コミットメッセージは RESファイル名（拡張子抜き）で行う
    *   タスクごとの随時保存は「ファイル名＋TASK1」などをコミットメッセージにする
*   **NotebookLMへの登録（★v2変更）**
    *   RESファイルを登録する（v1から継続）
    *   **RESに含まれる「REQ制約条件の要約」（1-3）によって、設計判断の理由も知識ベース側に残る**。
    *   REQ本体の登録は任意。ノイズになると判断する場合は登録しなくてよいが、その場合でも上記の要約は必須とする。

## 4. Phaseクローズ手順（★v2追加）

Phaseは初期テーマの完遂を待たずに中断されうるため、未完タスクが宙に浮きやすい。クローズ時は必ず以下を実施する。

1.  **未完タスクの棚卸し**: 当該Phaseの各RESに残る「懸念事項・追加タスク」を全て抽出する。
2.  **仕分け**: 各項目を「次Phaseへ持ち越し」「Spotとして単発処理」「意図的に破棄」のいずれかに分類する。**破棄する場合は破棄理由を書く**（後から「なぜやらなかったのか」が分からなくなるのを防ぐ）。
3.  **クローズレポートの作成**: `YYYYMMDD_HHMM_PhaseXX_Close.md` として、達成した範囲・未達の範囲・仕分け結果・計画改訂が発生した箇所とその原因を記録する。
4.  PROJECT_ARCHITECTURE.md を実態に合わせて清書し、クローズレポートと共にコミット・NotebookLM登録する。
